处理 C++ 构建错误时，先确定问题发生在编译还是链接阶段，再检查声明、定义和最终符号是否一致。以下围绕重复定义、缺失定义和 C/C++ 入口名称展开。

构建链路：编译、链接与加载

常规 C++ 构建流程：

text
a.cpp、b.cpp
      │ 编译
      ▼
  a.o、b.o
      │ 链接
      ▼
可执行文件或动态库
      │ 加载
      ▼
  进程虚拟内存

编译器分别处理每个翻译单元，链接器再解析符号并组合目标文件与库。运行时加载器将可执行文件和需要的动态库映射进进程。

定义如何跨翻译单元组织

头文件中的普通函数定义会被每个包含者展开：

cpp
// math.h
int add(int a, int b) {
    return a + b;
}

若多个 .cpp 包含它，链接时可能出现重复符号。这违反 One Definition Rule。

常规方案是头文件只放声明，实现放在一个 .cpp：

cpp
// math.h
int add(int a, int b);
cpp
// math.cpp
int add(int a, int b) {
    return a + b;
}

或者将需要在头文件定义的函数声明为 inline：

cpp
inline int add(int a, int b) {
    return a + b;
}

inline 允许多个翻译单元中存在相同定义，并由工具链实现统一实体语义。它不保证编译器一定把函数调用展开。

根据错误阶段检查符号与语言链接

编译错误与链接错误

text
use of undeclared identifier 'add'

表示当前翻译单元没有看到有效声明，属于编译阶段问题。

text
undefined reference to 'add'

表示编译器看到了声明，但链接器找不到匹配定义。常见原因包括：

  • 实现文件没有加入构建。

  • 缺少需要链接的静态库或动态库。

  • 声明与定义签名不一致。

  • C 与 C++ 链接名称不一致。

  • 符号可见性或链接顺序错误。

名称修饰与 extern "C"

C++ 为支持重载、命名空间和成员函数，会将名称与类型信息编码进链接符号，称为 name mangling：

cpp
int add(int, int);       // 类似 _Z3addii
double add(double, double);

跨 C ABI、JNI 或 dlsym 导出稳定入口时，经常使用：

cpp
extern "C" int add(int a, int b);

它要求使用 C 语言链接规则，避免 C++ 名称修饰。C 链接入口不能依赖参数类型重载同名函数。

要点回顾

头文件可见不等于实现已参与链接。排查时先确认翻译单元能看到声明，再确认目标文件或库提供匹配定义，最后检查语言链接与符号可见性。
