智能指针与异步生命周期

从异步悬空访问推导持有策略，细化弱引用、请求代次和取消接口。

本文讨论对象销毁与异步回调执行顺序不一致时，如何选择捕获方式，并把对象存活、请求取消和资源释放落实到接口中。

任务需要延长对象生命时捕获已有的强引用；允许随对象消失而放弃时捕获弱引用，并在执行时用 lock() 取得临时强引用。 页面关闭或新请求替代旧请求，还需要单独的取消或版本判断。智能指针负责对象存活，不负责判断一项业务操作是否仍应执行。

背景：页面、播放器与任务各有生命周期

页面通过 shared_ptr 持有播放器，执行器负责保存并调度播放任务。提交任务只表示执行器接收了回调，并不表示回调已经执行；页面可以在这段等待期间关闭，播放器也可能同时被其他模块持有。

因此，页面是否存在、播放器是否存活、播放请求是否仍然有效，是三个不同的状态。任务需要在哪些状态下继续执行，决定了它应当怎样保存播放器。

问题：任务排队后，对象先销毁

一个播放任务已经提交到队列，但还没有执行。此时页面关闭，最后一个持有播放器的对象释放了引用。等到任务出队，回调里保存的 this 还能用吗？

C++ · 捕获裸 this
executor.post([this]() {
    play();
});

要分析这类故障，先把三个时刻排列出来：任务入队、对象析构、任务执行。示例中，析构发生在执行之前；若能收集实际日志，可以为对象和任务记录标识，确认它们是否属于同一次请求，不能仅凭一次崩溃位置就认定是生命周期问题。

这段代码只把对象地址交给了任务。假如对象已经销毁，再通过这个地址调用成员函数，就会访问失效对象。即使播放器原本由 shared_ptr 管理，捕获 this 也不会自动增加引用计数。

给 play() 加锁并不能单独修复这个问题：如果对象已经不存在，访问它的成员锁本身也可能失效。把 this 复制进另一个局部变量，同样只复制地址。

需要改变的是任务和对象之间的持有关系。选择之前，先确定页面关闭之后，这个任务是否还有继续执行的必要。

executor.post() 保存回调供稍后执行；Player 通过 std::make_shared<Player>() 创建，并公开继承 std::enable_shared_from_this<Player>。代码片段省略执行器与业务方法的实现。

方案比较：任务是否需要持有播放器

有几种办法能约束这个顺序，但代价不同：

做法适用条件需要付出的代价
对象销毁前取消或等待全部任务执行器能保证没有正在运行或稍后启动的回调退出可能等待；同线程等待自己队列里的任务可能无法推进
任务捕获强引用即使原调用方离开，任务仍需要这个对象对象释放取决于闭包何时销毁，还要检查引用环
任务捕获弱引用对象消失后可以放弃操作执行时可能跳过，调用方必须接受这个结果
只复制任务所需的数据操作可以脱离原对象完成需要明确输入快照与结果接收方式

下面保留以 Player 为操作对象的接口，分别实现强引用和弱引用路径。若任务只需要几个不可变参数，复制参数也可能比延长整个播放器的生命更合适。

强引用：延长对象生命周期

如果任务仍然需要访问播放器，可以让回调持有它：

C++ · 回调持有强引用
auto self = shared_from_this();
executor.post([self]() {
    self->play();
});

这里有两个持有者：原来的业务对象，以及任务里的 self。页面释放自己的引用后，任务仍持有播放器，因此播放器可以活到回调执行时。

释放时间还取决于队列什么时候销毁回调。即使回调已经执行，如果执行器继续保存这个闭包，其中的强引用也还存在。判断对象为什么没有析构时，需要沿着实际持有关系检查，不能只看函数是否返回。

这也说明，捕获强引用只解决对象存活问题。任务会不会被调度、是否超时、能否取消，仍由执行器和业务协议决定。

弱引用：执行时检查对象

如果任务只是更新已关闭页面的播放状态，继续延长对象生命周期就没有必要。可以在执行时尝试取得强引用：

C++17 · 执行时提升弱引用
std::weak_ptr<Player> weakSelf = weak_from_this();
executor.post([weakSelf]() {
    if (auto self = weakSelf.lock()) {
        self->play();
    }
});

lock() 成功时返回一个 shared_ptr，在 self 存活期间维持对象生命；对象已被销毁时返回空指针，回调跳过本次操作。这个获取过程是原子的，不应拆成“先检查 expired()，再使用裸指针”两个步骤。可核对标准中的 weak_ptr::lock() 定义。

弱引用不等于取消

页面关闭后，如果播放器仍被其他模块持有，lock() 依然可能成功。需要取消旧请求时，还应检查取消标记或请求版本。

同样，self 存活只保证对象没有被销毁。多个线程同时修改 Player 的成员时，仍需同步或将操作放在指定线程上。

实现：把存活、取消和释放分开处理

用请求代次取消过期操作

假设页面关闭后允许放弃播放，新的播放请求又会替代排队中的旧请求。弱引用已经能处理对象销毁，但如果别的模块仍持有播放器，旧任务仍能通过 lock()。于是还需要一个请求代次，记录“这个任务是否仍是当前请求”。

每次发起新请求或取消时递增代次，任务保存提交时的值，执行时再比较。下面约定发起、取消和回调都在同一个事件线程执行；跨线程调用需要先调度到该线程，或另外设计同步。此处不把非原子的成员当作线程安全方案。

C++17 · 弱引用与请求代次
class Player : public std::enable_shared_from_this<Player> {
public:
    explicit Player(Executor& executor) : executor_(executor) {}

    void requestPlay() {
        const auto generation = ++requestGeneration_;
        auto weakSelf = weak_from_this();
        executor_.post([weakSelf, generation]() {
            auto self = weakSelf.lock();
            if (!self || generation != self->requestGeneration_) {
                return;
            }
            self->play();
        });
    }

    void cancelPending() {
        ++requestGeneration_;
    }

private:
    void play(); // 具体播放行为由业务实现
    Executor& executor_;
    std::uint64_t requestGeneration_ = 0;
};

示例需要 <memory>、<cstdint>，并由执行器提供 post()。执行器应覆盖播放器使用它的整个期间；播放器仍通过 make_shared 创建，在构造完成后才调用 requestPlay()。

执行路径里有两次不同的判断：lock() 判断对象能否安全访问，代次比较判断任务是否已经过期。页面关闭但播放器仍存活时，cancelPending() 使排队中的回调成为空操作；连续两次 requestPlay() 则只保留最新一次的执行资格。

这是一种排队任务的逻辑取消，不会将回调从队列移除，也不能中断已经进入 play() 的操作。如果业务需要停止正在播放的内容，应提供单独的停止协议。执行器若因异常或容量限制无法接收任务，还需按业务要求回报提交失败。

取得强引用时复用已有控制块

强引用路径需要从当前对象取得一个持有者，这也是前面使用 shared_from_this() 的原因。若直接用 this 构造 shared_ptr，虽然地址相同，却可能另建一套负责删除对象的控制块：

C++ · 复用已有控制块
auto self = shared_from_this();     // 复用当前对象已有的共享所有权
// std::shared_ptr<Player> self(this); // 错误示意：可能建立第二套所有权

shared_ptr 通过控制块管理共享所有权。控制块通常保存强、弱引用计数，以及删除对象所需的信息。复制已有的 shared_ptr 会共享控制块；从同一个裸指针分别构造两个 shared_ptr，则会建立两套独立管理关系：

C++ · 错误示例：重复管理同一地址
User* raw = new User();

std::shared_ptr<User> first(raw);
std::shared_ptr<User> second(raw); // 错误示意：两个控制块分别尝试删除同一对象

第二个指针应当从 first 复制：

C++ · 复制共享所有权
std::shared_ptr<User> second = first;

enable_shared_from_this 提供的也是复用已有所有权的途径：

C++ · 建立共享管理关系
class Player
    : public std::enable_shared_from_this<Player> {
};

auto player = std::make_shared<Player>();
auto self = player->shared_from_this();

这里 self 与 player 共享控制块。相关行为可以对照标准中的 enable_shared_from_this。

这个关系需要先建立。栈上的对象、仅由 unique_ptr 管理的对象，以及正在构造、尚未交给 shared_ptr 管理的对象，都不能据此取得有效的共享所有权。在上述正常继承条件下，过早调用 shared_from_this() 会抛出 std::bad_weak_ptr。weak_from_this() 在关系尚未建立时得到的是空弱引用；把它提前存进回调，不会在构造结束后自动补上关联。

因此，依赖共享所有权的异步启动通常应放在对象构造完成、交给 shared_ptr 管理之后。

沿持有关系检查引用环

假设对象持有一个回调，而回调又捕获对象的 shared_ptr：

示意
Player -> 保存的回调 -> shared_ptr<Player> -> Player

外部引用全部释放后，这个环内部仍然互相持有。如果没有清除回调的路径，对象就无法正常析构。

父子对象也有同样的问题。父对象拥有子对象，子对象只需要回查父对象时，可以让回指使用弱引用：

C++ · 父子对象的拥有与回指
struct Child;

struct Parent {
    std::shared_ptr<Child> child;
};

struct Child {
    std::weak_ptr<Parent> parent;
};

在 Child 的成员函数中，使用前临时取得强引用：

C++ · 临时取得父对象
if (auto lockedParent = parent.lock()) {
    lockedParent->update();
}

片段省略了业务方法的声明。哪一条引用应当变弱，要看谁负责拥有谁。把所有回指机械地换成弱引用，可能只是把泄漏变成任务意外失效。

实现效果：对象安全与请求有效分别验证

用一个可以手动推进的执行器，先只入队、不立即运行，再控制释放、取消和执行的顺序，就能验证这里讨论的条件：

操作顺序预期结果
强引用任务入队，释放外部引用，执行任务对象在执行时仍存活；闭包释放后才能判断是否可析构
弱引用任务入队，释放最后一个强引用，执行任务lock() 失败，不调用 play()
对象继续存活，入队后调用 cancelPending()代次不匹配，任务不再调用 play()
连续提交两个播放请求，再推进队列旧任务跳过，最新任务执行
对象持有捕获自身强引用的回调清除回调或打破引用环前，对象不会仅因外部释放而析构

本地用可手动推进的执行器检查了前四类顺序，播放次数与析构标记均符合表中的预期；另外验证了取消后重新请求仍可执行。若真实执行器跨线程，还需对成员访问的同步与正在执行任务的停止协议分别验证。

这些结果对应开头的两个判断：强弱引用决定任务能否安全访问对象，请求代次决定任务是否仍有执行资格。 对象已销毁时，弱引用阻止访问；对象还活着但请求过期时，代次检查阻止执行。只换成智能指针，无法同时解决这两类问题。

补充：同步借用与局部引用

异步任务需要单独考虑生命周期；同步调用若只在调用期间访问对象，可以直接表达借用关系：

C++ · 借用和转移所有权
void inspect(const User& user);         // 调用期间只读访问
void take(std::unique_ptr<User> user);  // 接收独占所有权

常用类型可以按接口意图选择：

接口意图常用表达
借用一个可能为空的对象T* / const T*，约定不负责释放
借用一个必需存在的对象T& / const T&
接收或转移独占所有权std::unique_ptr<T>
共同维持对象生命std::shared_ptr<T>
观察对象，使用时再尝试取得所有权std::weak_ptr<T>

裸指针这个类型本身不会说明谁负责释放，需要接口约定。仅为了读几个字段就要求传入 shared_ptr，会把调用方的所有权方案带进接口。

局部变量的引用捕获

引用捕获局部变量时，也必须检查被引用对象能否活到回调执行：

C++ · 错误示例：捕获已离开作用域的变量
std::function<void()> makePrinter() {
    int value = 42;
    return [&value]() { // 错误示意：函数返回后 value 已销毁
        std::cout << value;
    };
}

如果回调只需要这个整数的值，改成值捕获即可：

C++ · 按值捕获
return [value]() {
    std::cout << value;
};

检查回调时，可以先列出它保存的地址和引用，再逐个确认对象的销毁时机。这也是 C++ Core Guidelines F.53 提醒避免在逃逸的 lambda 中捕获局部引用的原因。

补充：对象析构与存储释放

使用 make_shared 时，还需要区分对象生命和底层存储：

C++ · 两种分配方式
std::shared_ptr<User>(new User()); // 常见实现分别分配对象和控制块
std::make_shared<User>();         // 常见实现将两者放进一次分配

合并分配通常能减少分配次数，但会影响弱引用残留时的内存释放时机。最后一个强引用释放后，User 已经析构；如果仍有弱引用，控制块还要保留。在对象与控制块合并分配的实现中，整块存储也要继续保留，直到最后一个弱引用释放。

对于较大的对象，如果弱引用会长期留在注册表或缓存中，这个差别值得检查。看到一块内存尚未归还，不能直接推断对象析构函数没有执行。

这项补充影响的是存储何时归还。排查时将它与对象析构、任务取消分开记录，才能判断延迟释放发生在哪一层。
