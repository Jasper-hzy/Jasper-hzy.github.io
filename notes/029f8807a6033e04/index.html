本文通过多宿主示例说明 Dagger2 的对象创建与组装机制，以及 @Inject、Module、Component、Binding 和 Scope 的关系。

依赖注入要解决的问题

依赖注入解决什么问题

如果业务对象自己创建具体依赖：

kotlin
class InteractiveContainer {
    private val hostAbility = DouyinHostAbility(Logger())
}

它会同时负责业务逻辑和对象组装，并且直接依赖某个宿主实现。迁移到另一个宿主时，只能修改公共代码、增加宿主判断，或者复制一套实现。

改成从外部传入依赖：

kotlin
class InteractiveContainer(
    private val hostAbility: HostAbility,
)

公共业务只依赖接口，具体实现由外部组装。Dagger2 帮助完成的就是这部分重复工作：

示意
业务对象：声明需要什么
Dagger2：确定使用哪个实现，并创建、组装对象

依赖注入没有消除依赖，而是将“直接创建具体实现”改为“声明对抽象能力的依赖”。

先建立一个心智模型

Dagger2 可以理解为一个编译期生成的对象工厂。

业务代码只声明自己依赖什么：

kotlin
class InteractiveContainer @Inject constructor(
    private val hostAbility: HostAbility,
)

Dagger2 根据构造函数、Module 和 Component 建立依赖图，并生成普通的对象创建代码：

示意
InteractiveContainer
  └─ HostAbility
       └─ DouyinHostAbility
            └─ Logger

运行时仍然会创建这些对象；“编译期依赖注入”指的是依赖图校验和组装代码生成发生在编译期，不是编译时就创建业务对象。

六个核心概念

概念含义
Dependency一个对象需要使用的其他对象，例如容器依赖 HostAbility
Binding如何获得某个类型的规则，例如 HostAbility -> DouyinHostAbility
@Inject声明可使用的构造函数，或者标记需要成员注入的位置
Module集中声明不能仅靠构造函数推导的 Binding
Component依赖图的边界、入口和生成代码的载体
Scope指定某个 Binding 在同一 Component 实例中的复用范围

最小示例与 Binding 声明方式

跑通一个最小示例

1. 配置编译器

Kotlin 工程常见的 KAPT 配置如下，版本号以项目实际使用版本为准：

kotlin
plugins {
    kotlin("kapt")
}

dependencies {
    implementation("com.google.dagger:dagger:<version>")
    kapt("com.google.dagger:dagger-compiler:<version>")
}

Java 工程可以使用 annotationProcessor。已有工程选择 KSP 后端时，需要按所用 Dagger 版本及其他代码生成器的兼容情况判断。

2. 定义公共能力

kotlin
interface HostAbility {
    fun openRoom()
}

3. 声明具体对象如何构造

kotlin
class Logger @Inject constructor() {
    fun log(message: String) = Unit
}

class DouyinHostAbility @Inject constructor(
    private val logger: Logger,
) : HostAbility {

    override fun openRoom() {
        logger.log("open room")
    }
}

构造函数上的 @Inject 告诉 Dagger：需要这个类时，可以调用这个构造函数；构造参数则会继续成为依赖图中的节点。

4. 将接口绑定到实现

接口没有构造函数，Dagger 不知道 HostAbility 应该使用哪个实现，因此需要 Module：

kotlin
@Module
interface HostModule {

    @Binds
    fun bindHostAbility(
        implementation: DouyinHostAbility,
    ): HostAbility
}

这条 Binding 表示：

示意
需要 HostAbility
  → 使用 DouyinHostAbility

5. 声明依赖图入口

kotlin
class InteractiveContainer @Inject constructor(
    private val hostAbility: HostAbility,
) {
    fun start() {
        hostAbility.openRoom()
    }
}

@Component(modules = [HostModule::class])
interface AppComponent {
    fun interactiveContainer(): InteractiveContainer
}

Component 的返回值方法叫 Provision Method，表示调用者可以从依赖图获取这个对象。

6. 使用生成的 Component

编译后，Dagger 会生成以 Dagger 为前缀的实现：

kotlin
val component = DaggerAppComponent.create()
val container = component.interactiveContainer()
container.start()

生成代码完成的工作大致是：

示意
创建 Logger
  → 创建 DouyinHostAbility
  → 作为 HostAbility
  → 创建 InteractiveContainer

@Inject 的两种常见用法

构造函数注入

kotlin
class RoomManager @Inject constructor(
    private val logger: Logger,
)

优先使用构造函数注入，因为依赖在对象创建时就完整，测试时也可以直接传入 Fake 对象。

成员注入

Activity 等由 Android 系统创建的对象不能直接由 Dagger 调用构造函数，可以使用成员注入：

kotlin
class MainActivity : Activity() {
    @Inject lateinit var roomManager: RoomManager
}

@Component
interface AppComponent {
    fun inject(activity: MainActivity)
}

调用者需要显式执行：

kotlin
component.inject(activity)

成员注入完成前字段不可用，因此普通业务类仍然优先使用构造函数注入。

@Binds 与 @Provides 怎么选择

使用 @Binds 声明接口映射

kotlin
@Module
interface HostModule {
    @Binds
    fun bindHostAbility(
        implementation: DouyinHostAbility,
    ): HostAbility
}

@Binds 方法是抽象方法，没有方法体。参数是已有实现，返回值是对外暴露的类型。

使用 @Provides 执行创建逻辑

kotlin
data class AppConfig(
    val debug: Boolean,
)

@Module
object ConfigModule {
    @Provides
    fun provideAppConfig(): AppConfig {
        return AppConfig(debug = BuildConfig.DEBUG)
    }
}

@Provides 适合以下场景：

  • 第三方类无法添加 @Inject；

  • 对象需要配置参数或工厂方法；

  • 创建过程包含条件或额外逻辑；

  • 需要提供系统对象。

简单判断：

示意
接口绑定到已有实现 → @Binds
需要执行代码创建对象 → @Provides
具体类构造函数可直接控制 → @Inject constructor

Component、Scope 与实例生命周期

Component 到底管理什么

Component 主要承担三类职责：

  1. 确定当前依赖图包含哪些 Module 和 Binding。

  2. 对外提供获取对象或注入现有对象的入口。

  3. 持有当前依赖图中 Scoped Binding 的缓存。

Component 不是全局容器的同义词。可以按业务生命周期拆成多级依赖图：

示意
AppComponent
  └─ RoomComponent
       └─ PageComponent

子组件可以使用父组件中的 Binding；父组件不能反向依赖子组件，兄弟子组件之间也不能直接依赖彼此。

Scope 如何与 Component 关联

1. 定义自定义 Scope

kotlin
@Scope
@Retention(AnnotationRetention.RUNTIME)
annotation class RoomScope

2. 标记 Component

kotlin
@RoomScope
@Component
interface RoomComponent {
    fun roomManager(): RoomManager
}

3. 标记 Binding

kotlin
@RoomScope
class RoomManager @Inject constructor() {
    fun release() = Unit
}

Dagger 编译器看到 Component 和 Binding 使用相同的 Scope 注解后，将这个 Binding 的 Provider 缓存在生成的 Component 实例中。生成代码的核心逻辑可以近似理解为：

kotlin
class GeneratedRoomComponent {
    private val roomManager: RoomManager by lazy {
        RoomManager()
    }
}

因此：

kotlin
val roomA = DaggerRoomComponent.create()
val roomB = DaggerRoomComponent.create()

roomA.roomManager() === roomA.roomManager() // true
roomA.roomManager() === roomB.roomManager() // false

Scope 的含义是“同一个 Component 实例内复用”，不是“所有使用同一 Scope 注解的 Component 共享对象”。

Scope 什么时候结束

Scope 本身只是注解，没有 release()。真正持有对象的是生成的 Component：

示意
RoomOwner
  → RoomComponent
       → Provider
            → RoomManager

业务退出时需要：

  1. 主动反注册监听、取消任务和释放播放器等资源；

  2. 清除业务层对 Component 的引用；

  3. 清除其他对象对 Scoped 对象的外部引用；

  4. 等待 JVM 在合适时机回收对象。

kotlin
fun leaveRoom() {
    roomComponent?.roomManager()?.release()
    roomComponent = null
}

Dagger 不会自动调用 release()，Scope 也不保证业务对象内部线程安全。

@Singleton 不一定是进程全局单例

@Singleton 仍然遵循“每个 Component 实例缓存一次”的规则：

kotlin
@Singleton
@Component
interface AppComponent

只有应用全程只创建一个 AppComponent，它才表现为进程级单例。创建两个 AppComponent，仍然会有两组 @Singleton 对象。

多宿主下的依赖图组合

在多宿主迁移中，两者解决的问题不同：

示意
Gradle Flavor：决定当前构建包含哪套代码、资源和依赖
Dagger2：将当前构建中的宿主实现绑定并注入公共业务

工程结构可以抽象为：

示意
src/main
  ├─ HostAbility
  └─ InteractiveContainer

src/douyin
  ├─ DouyinHostAbility
  └─ HostModule

src/volcano
  ├─ VolcanoHostAbility
  └─ HostModule

公共业务：

kotlin
class InteractiveContainer @Inject constructor(
    private val hostAbility: HostAbility,
)

不同 Flavor 分别把自己的实现绑定为 HostAbility。最终链路是：

示意
选择构建 Flavor
  → 只编译对应宿主实现与资源
  → Dagger 为当前 Variant 生成依赖图
  → 公共容器获得当前宿主实现

Dagger2 不是在运行时动态判断宿主，宿主实现已经由 Flavor 在编译阶段确定。

编译错误与定位方法

错误常见原因处理方向
MissingBinding接口没有 @Binds/@Provides，或者构造函数没有 @Inject沿错误中的依赖链补充 Binding
DuplicateBindings同一个类型存在多个未区分的实现删除重复 Binding，或使用 Qualifier 区分
IncompatiblyScopedBindingsScoped Binding 与管理它的 Component Scope 不匹配调整 Binding 所在组件或 Scope
Dependency cycleA 直接依赖 B，B 又直接依赖 A重新划分职责；必要时通过 Provider/Lazy 延迟一侧，但不要掩盖设计问题
生成的 Component 不存在编译器依赖未接入，或前面已有 Dagger 编译错误检查 KAPT/KSP/annotationProcessor 配置和首个报错

如果同一类型存在多个合法实现，可以通过 Qualifier 区分：

kotlin
@Qualifier
annotation class DebugLogger

@Qualifier
annotation class ReleaseLogger
