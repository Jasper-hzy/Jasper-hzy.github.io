Input 系统负责把事件送到正确的 Window；事件进入 App 后，View 事件分发机制负责在当前窗口的 View 树中找到处理者。

下图先固定一条正常点击主线：父容器不拦截、OnTouchListener 不消费、目标 View 始终保持有效点击状态。

事件进入窗口后的入口

text
目标 Window 的 InputChannel
  -> InputEventReceiver
  -> ViewRootImpl.enqueueInputEvent
  -> InputStage
  -> DecorView.dispatchPointerEvent
  -> DecorView.dispatchTouchEvent
  -> Activity.dispatchTouchEvent
  -> PhoneWindow.superDispatchTouchEvent
  -> DecorView.superDispatchTouchEvent
  -> ViewGroup.dispatchTouchEvent

DecorView 先通过 Window.Callback 把事件交给 Activity；Activity 再调用 Window，把事件送回 DecorView 的父类实现，正式进入 View 树。Activity 是窗口回调，不是 View 树的父节点。

窗口选择、InputChannel 和 VSYNC 对齐过程见 Input 输入系统流程。

回调职责与触摸目标的建立

五个关键回调

方法所属对象职责
dispatchTouchEventView / ViewGroup分发入口，返回本节点或后代是否处理了事件
onInterceptTouchEventViewGroup决定当前事件是否从子 View 手中截走
OnTouchListener.onTouchView业务监听器，先于 onTouchEvent 执行，可直接消费 MotionEvent
onTouchEventView / ViewGroup当前节点真正处理事件；返回 true 表示愿意接管手势
OnClickListener.onClickView点击语义回调，由 onTouchEvent 在有效点击完成后通过 performClick 触发

View.dispatchTouchEvent 中，已启用且可用的 OnTouchListener.onTouch 先于 onTouchEvent 执行；监听器返回 true 后不会再调用该 View 的 onTouchEvent。

ViewGroup 如何确定触摸目标

每一层 ViewGroup.dispatchTouchEvent 都负责“是否拦截、交给哪个子节点、是否记录触摸目标”三个决策：

text
父 ViewGroup.dispatchTouchEvent
  -> DOWN：清理旧状态
  -> onInterceptTouchEvent
     -> true：父容器接管；已有子目标收到 CANCEL
     -> false：按坐标和层级命中子节点
        -> child.dispatchTouchEvent
           -> true：记录 child 为 TouchTarget
           -> false：继续尝试其他子节点
  -> 没有子节点消费：父容器按普通 View 执行自己的 onTouchEvent

后续 MOVE/UP 优先沿 TouchTarget 发送，不会每次重新遍历整棵 View 树。消费结果沿递归调用栈向上返回，不是 DOM 那种独立的冒泡阶段。

DOWN 如何确定整条手势链

一次手势通常是 DOWN -> MOVE... -> UP/CANCEL：

  1. DOWN 从根 ViewGroup 向下命中子节点。

  2. 子节点消费 DOWN 后，父 ViewGroup 用 TouchTarget 记录该子节点。

  3. 后续 MOVE/UP 沿已记录的 TouchTarget 继续发送，不再重新完整命中 View 树。

  4. 如果父容器在 MOVE 阶段开始拦截，子节点收到由当前事件转换出的 CANCEL，之后的事件改由父容器处理。

因此自定义 View 若想持续收到后续事件，通常必须消费 DOWN。子 View 可以调用 requestDisallowInterceptTouchEvent(true)，要求祖先暂时不要拦截后续事件，但新的 DOWN 会重置这一状态。

从触摸序列生成点击

onClick 不直接接收 MotionEvent，也不参与 ViewGroup 的路由。默认点击由 View.onTouchEvent 根据一整段手势状态合成：

text
DOWN：进入 pressed 状态，安排长按检测，onTouchEvent 返回 true
MOVE：仍在触摸范围内则保持；移出 touchSlop 则清除 pressed
UP：仍处于有效点击状态
  -> post PerformClick
  -> performClickInternal
  -> performClick
  -> OnClickListener.onClick
CANCEL / 父容器中途拦截 / MOVE 移出范围：清理状态，不触发 onClick

因此：

  • OnTouchListener.onTouch 返回 false：继续执行 onTouchEvent，默认点击逻辑仍有机会触发。

  • OnTouchListener.onTouch 返回 true：本次事件不会进入 onTouchEvent；如果整段手势都被监听器消费，默认 onClick 不会自动产生，需要在合适时机调用 performClick()。

  • onTouchEvent 消费 DOWN 的意义不只是处理这一次事件，还会让父容器记录 TouchTarget，使该 View 继续收到后续事件。

父子滚动协作与模型边界

为什么这样设计

  • 子 View 优先：点击坐标命中的具体控件通常最了解如何处理事件。

  • 父容器可夺取：ScrollView、ViewPager 等容器可以观察位移，在确认是滚动手势后中途拦截。

  • 手势保持连续：DOWN 建立 TouchTarget，避免手指移动时处理对象不断变化。

  • 无人处理时兜底：子节点返回 false，父节点仍有机会在自己的 onTouchEvent 中处理。

它解决的是“子控件点击”和“父容器滚动”之间的仲裁，而不只是把一次点击广播给所有节点。

NestedScrolling 如何协调父子滚动

requestDisallowInterceptTouchEvent 控制的是父容器能否接管 MotionEvent；NestedScrolling 不改变 TouchTarget，而是让当前 Child 把每次滚动的 dx/dy 与 Parent 分段消费。

一次嵌套滚动分为四步：

  1. Child 调用 startNestedScroll，沿父链找到愿意接受对应滚动轴和类型的 NestedScrolling Parent。

  2. 每次滚动前调用 dispatchNestedPreScroll，Parent 通过 consumed[] 先消费一部分距离。

  3. Child 消费剩余距离，再通过 dispatchNestedScroll 报告已消费量和未消费量，Parent 可以继续处理剩余部分。

  4. UP/CANCEL 后调用 stopNestedScroll；fling 则使用 dispatchNestedPreFling/dispatchNestedFling 协商速度归属。

这条协作链传递的是滚动距离和速度，不是重新分发 MotionEvent，也不经过 Binder；调用发生在同一 View 树的普通 Java 方法之间。onNestedPreScroll/onNestedScroll 不等于 onInterceptTouchEvent，不会自动转移 TouchTarget 或向 Child 发送 CANCEL。AndroidX 通过 NestedScrollingChildHelper、NestedScrollingChild3 和 NestedScrollingParent3 补充了 TYPE_TOUCH/TYPE_NON_TOUCH 以及多级消费能力。

与 DOM / React 的区别

模型向下阶段向上阶段目标如何保持
Android ViewdispatchTouchEvent 递归 + onInterceptTouchEvent 仲裁子调用返回 false 后父节点兜底，不是独立冒泡回调DOWN 建立 TouchTarget，覆盖连续手势
DOMcapture 从祖先到 targetbubble 从 target 到祖先，祖先监听器依次执行每个事件按 DOM 命中和传播路径处理
React DOM以组件事件处理器表达 capture / bubble，可停止传播子组件处理器执行后继续到父组件处理器主要面向 click 等语义事件传播

Android 更强调连续手势所有权和父子手势冲突；DOM/React 更强调同一个离散事件在祖先链上的传播。两者图形上都像“下去再上来”，但“向上”的语义不同。

另一种常见设计是“集中命中测试 + 手势竞争”：根节点先生成命中路径，再让点击、滑动、缩放等识别器竞争手势所有权。它把仲裁从 ViewGroup 拦截改成独立的手势识别层，Flutter 和游戏 UI 常采用这种思路。

源码入口与结论

源码入口

  • ViewRootImpl.java：ViewPostImeInputStage、processPointerEvent。

  • DecorView.java 与 Activity.java：Window.Callback 往返链路。

  • ViewGroup.java：dispatchTouchEvent、TouchTarget、拦截和 CANCEL。

  • View.java：dispatchTouchEvent、onTouchEvent、performClick。

  • NestedScrollingChildHelper.java：查找协作 Parent、预消费、剩余距离和停止协作。

  • NestedScrollingParent3.java：Parent 对已消费量和未消费量的处理协议。

关键结论

  1. InputDispatcher 只选中 Window，ViewRootImpl 才是事件进入该窗口 View 树的入口。

  2. Activity 是 Window.Callback，不是 View 树父节点。

  3. Android 的向上过程本质是消费结果沿递归调用栈返回，不等同于 DOM 冒泡。

  4. DOWN 决定 TouchTarget；父容器中途拦截时，原目标收到 CANCEL。

  5. 触摸路径中的 onClick 不是分发方法，而是 View.onTouchEvent 对有效点击手势生成的语义回调。

  6. requestDisallowInterceptTouchEvent 协调 MotionEvent 归属；NestedScrolling 协调父子对滚动距离的共同消费。
