mmap() 的核心不是“复制一块内存”，而是在进程虚拟地址空间中创建一段 VMA，规定这段虚拟地址背后由文件页、匿名页或共享内存对象提供物理页。

示意
虚拟地址
   ↓ 查当前进程页表
PTE
   ↓
RAM 物理页

mmap() 能减少复制，是因为它可以让进程页表直接指向已经存在的文件页或共享页，而不必先把数据复制到进程私有 Buffer。

地址空间与映射的基本概念

物理页

物理页是 RAM 的固定大小分块，常见大小为 4 KB。堆、栈、匿名内存和文件缓存最终占用的都是 RAM 物理页。

VMA

VMA（Virtual Memory Area）属于某个进程的虚拟地址空间，描述一段连续虚拟地址的来源和权限：

示意
虚拟地址起止范围
读 / 写 / 执行权限
MAP_SHARED / MAP_PRIVATE
关联的文件或匿名内存对象
文件 offset

调用 mmap() 时通常先创建 VMA，物理页和 PTE 可以等首次访问时再按需建立。

页表与 PTE

页表属于进程地址空间。PTE 记录某个虚拟页映射到哪个物理页，以及该页是否可读、可写、可执行、可由用户态访问。

不同进程的页表彼此独立，但内核可以让它们的 PTE 指向同一个物理页：

示意
进程 A：VA 0x1000 → PTE A ─┐
                             ├→ RAM 物理页 100
进程 B：VA 0x8000 → PTE B ─┘

共享的是物理页，不是页表，也不要求两边虚拟地址相同。

Page Cache

Page Cache 不是 CPU 的 L1/L2/L3 Cache，也不是一块独立硬件内存。它是 Linux 用 RAM 物理页缓存文件内容的全局机制：

示意
(文件 inode, 文件页索引)
          ↓
Page Cache 文件页：RAM 物理页
          ↓
Clean / Dirty / Writeback / 回收状态

同一个文件、同一个偏移通常对应同一份 Page Cache 页面。不同进程可以复用它，但进程通过 read() 得到的私有 Buffer 不是 Page Cache。

文件映射、私有映射与匿名映射

普通 read/write 与文件 mmap

普通 read/write

假设进程 A、B 读取同一个文件页面：

示意
SSD 文件
   ↓ 首次读取
Page Cache 文件页 F
   ├── copy_to_user() → A 的私有 Buffer 页
   └── copy_to_user() → B 的私有 Buffer 页

Page Cache 是全局共享的，但 A、B 的用户 Buffer 属于各自进程。A 修改自己的 Buffer 不会自动修改 Page Cache；只有调用 write() 时，内核才复制指定范围：

示意
A 私有 Buffer
   ↓ write() / copy_from_user()
Page Cache 文件页，标记 Dirty
   ↓ 内核回写或 fsync()
SSD 文件

B 已经读取出来的旧 Buffer 也不会自动更新。B 再次调用 read()，才会从当前 Page Cache 复制新内容。

文件 mmap

C++
void* address = mmap(
    nullptr,
    length,
    PROT_READ | PROT_WRITE,
    MAP_SHARED,
    fd,
    offset
);

调用成功后，进程获得一段虚拟地址。首次访问的主线是：

示意
访问映射虚拟地址
   ↓ PTE 尚未建立
文件映射缺页异常
   ↓
根据 VMA 找到文件和 offset
   ↓
查找 Page Cache
   ├── 命中：复用现有文件物理页
   └── 未命中：从文件读入 Page Cache
   ↓
建立 PTE → Page Cache 物理页
   ↓
重新执行内存访问

文件 mmap 省掉的是 Page Cache 到进程私有 Buffer 的复制：

示意
read：Page Cache → 复制 → 进程 Buffer
mmap：进程 PTE   → 直接指向 Page Cache

它不是绝对零开销：首次访问仍可能产生缺页处理、磁盘 I/O、页表建立和 TLB 开销。

以上描述针对普通 buffered I/O。O_DIRECT、DAX 和设备内存映射等特殊路径可能绕过普通 Page Cache，不直接套用这条主线。

MAP_SHARED 与 MAP_PRIVATE

prot 决定当前进程能否读写，flags 决定写入后修改共享对象还是生成私有副本。

映射方式读取时写入时是否修改文件
文件 MAP_SHARED映射 Page Cache修改 Page Cache 并形成脏页会，具体落盘时机需控制
文件 MAP_PRIVATE可复用 Page Cache首次写入触发 COW，生成匿名私有页不会
匿名 MAP_PRIVATE匿名页修改当前进程匿名页无文件
匿名 MAP_SHARED共享匿名页修改共享匿名页无普通磁盘文件

文件 MAP_PRIVATE 的写时复制：

示意
写入前：进程 PTE → Page Cache 文件页

首次写入：
  写保护缺页
     ↓
  复制出匿名物理页
     ↓
  当前进程 PTE → 匿名私有页

它在只读阶段复用文件页，只有进程需要私有修改时才付出复制成本。

匿名 mmap 不经过普通文件 Page Cache

C++
void* address = mmap(
    nullptr,
    length,
    PROT_READ | PROT_WRITE,
    MAP_PRIVATE | MAP_ANONYMOUS,
    -1,
    0
);

匿名映射没有普通文件、inode 和文件 offset：

示意
mmap(MAP_ANONYMOUS)
   ↓
创建匿名 VMA
   ↓ 首次写入触发缺页异常
内核分配清零的 RAM 物理页
   ↓
建立 PTE → 匿名物理页

因此，申请 1 GB 匿名映射通常只是先预留 1 GB 虚拟地址范围，实际触碰哪些页，再按需为哪些页分配 RAM。

首次只读时，Linux 还可能先映射全局只读 Zero Page；真正写入时才为当前映射分配匿名物理页。

匿名页没有文件可以重新读取。内存紧张时，它必须继续留在 RAM，或者在启用 Swap 时被换出；不能像干净文件页一样直接丢弃后从原文件恢复。

匿名映射何时共享

  • MAP_PRIVATE | MAP_ANONYMOUS：普通情况下属于当前地址空间；fork() 后父子初始通过 COW 共享，写入后分离。

  • MAP_SHARED | MAP_ANONYMOUS：先映射再 fork()，父子进程可以持续共享底层页面。

  • 两个无关进程各自调用一次匿名 mmap()：创建的是两个不同匿名对象，不会自动共享。

Linux 内部可能使用 shmem/tmpfs 机制管理共享匿名页，但它没有普通磁盘文件，也不走普通文件的持久化回写流程。

跨进程共享：建图、交换数据与同步协议

两个独立进程如何建立共享 mmap

两个无关进程需要先引用同一个共享内存对象，常用 memfd_create() 或 shm_open()：

示意
进程 A memfd_create()
   ↓
内核创建共享内存对象，返回 fdA
   ↓ Unix Domain Socket / Binder 传递 fd
进程 B 获得 fdB
   ↓
A、B 分别 mmap(MAP_SHARED)

fd 数字只在所属进程内有效，fdA 和 fdB 可以不同，但它们引用同一个内核对象。

物理页通常在首次访问时按需生成：

示意
A 首次访问共享对象第 0 页
   ↓ 缺页异常
查询（共享对象，第 0 页）
   ↓ 尚不存在
从 RAM 分配物理页 100，并登记到共享对象
   ↓
A 的 PTE → 物理页 100

B 首次访问共享对象第 0 页
   ↓ 缺页异常
查询（同一共享对象，第 0 页）
   ↓ 已存在物理页 100
B 的 PTE → 物理页 100

最终关系：

示意
A 的 VMA / PTE ─┐
                  ├→ 共享物理页 100
B 的 VMA / PTE ─┘

“物理页 100”只是便于理解的示意。更严谨地说，双方引用同一个共享 backing page/folio；具体 PFN 不是用户态可依赖的稳定身份。

进程间交换数据的两种方式

方式一：不 mmap，通过共享 fd 读写

memfd 等共享对象也可以像文件一样调用 read/write：

示意
A 私有物理页
   ↓ write() / copy_from_user()
共享对象物理页
   ↓ read() / copy_to_user()
B 私有物理页

这种方式能够交换数据，但每次传输仍需要系统调用，并可能同时存在 A 私有副本、共享对象副本和 B 私有副本。

方式二：双方 mmap 同一个共享对象

示意
A 虚拟地址 ─┐
              ├→ 同一个共享物理页
B 虚拟地址 ─┘

A 的 CPU Store 和 B 的 CPU Load 直接作用于同一个物理页，不再需要内核把数据从 A 复制到共享对象，再复制给 B。

“零拷贝”的边界

如果数据已经在 A 的私有堆中生成：

示意
A 私有对象
   ↓ memcpy()
共享映射页
   ← B 原地读取

仍然存在一次应用层复制。只有从一开始就在共享映射区域中构造数据，才能消除 IPC Payload 的内存副本：

示意
A 直接在共享页生成数据
   ↓
B 直接在共享页读取

因此应区分：

数据产生方式IPC 数据复制次数
write() 共享 fd，B 再 read()两次
A 私有对象 memcpy() 到共享 mmap，B 原地读一次
A 直接在共享 mmap 中构造，B 原地读零次 Payload 复制

这里的“零拷贝”只描述进程间 Payload 不再搬家，CPU 写数据、缺页、页表和缓存一致性仍然有成本。

共享内存不等于完整 IPC 协议

mmap 只解决双方访问同一物理页，不负责通知、消息边界和并发控制。实际结构通常是：

示意
共享内存：承载大块数据
eventfd / futex / Unix Socket：通知状态变化
原子变量 / 进程共享锁：保证读写顺序

共享区可设计为：

示意
┌──────────────┐
│ state        │ EMPTY / WRITING / READY
├──────────────┤
│ length       │
├──────────────┤
│ payload      │
└──────────────┘

生产者应先写 Payload，再以正确的内存顺序发布 READY；消费者确认 READY 后读取，不能把 mmap 当成自动同步机制。

两个进程的映射虚拟地址可能不同，因此共享区不能保存只对某个进程有效的裸指针。应保存相对映射起点的 offset，或使用专门的共享内存数据结构。

可见性、持久化与 Binder 的边界

可见性与持久化是两回事

文件 MAP_SHARED 的写入会修改 Page Cache 并形成脏页，其他共享映射可以观察到内存修改；但“另一个进程可见”不代表“已经写入 SSD”。

示意
进程间可见
   ↓
Page Cache 已更新
   ≠
存储设备已持久化

需要控制映射范围回写时使用 msync(MS_SYNC)。如果持久化协议还涉及文件大小、其他元数据或目录项，还要按文件系统语义配合相应的 fsync/fdatasync。突然掉电时，尚未完成持久化的脏页仍可能丢失。

memfd_create() 创建的是以易失性内存为 backing 的匿名文件对象，页面可被换入换出，但不对应持久化磁盘文件。所有引用释放后对象自动消失。

与 Binder mmap 的边界

Binder 的接收进程使用 mmap() 映射驱动管理的接收缓冲区，但发送端 Parcel 仍要通过 copy_from_user() 复制一次到目标 Binder buffer。因此 Binder 通常称为“一次拷贝”，不是两个进程共同直接读写同一 Payload 页。
