适用范围与页面监控模型

资料边界

本篇根据 Lynx 运行机制、首屏指标和资源加载排查资料整理，只保留通用指标口径，不记录内部文档入口、平台名称、业务标识和具体看板样本。

结论先行

Lynx 容器监控不能只讲“埋了几个指标”，更准确的口径是：围绕一次 Lynx 页面打开，把链路拆成容器初始化、资源准备、模板加载、首次绘制、业务数据更新、关键内容上屏，并分别建设资源稳定性、页面性能、运行时异常和业务结果指标。

Mermaid · 流程图源码
flowchart TD
  A[Lynx 容器监控] --> B[性能指标]
  A --> C[资源指标]
  A --> D[异常指标]
  A --> E[业务首帧]

  B --> B1[TotalFCP / FCP / LynxFCP]
  B --> B2[ActualFMP / TotalFMP / TTI]
  C --> C1[主模板加载成功率]
  C --> C2[离线化率 / CDN 成功率 / 缓存命中率]
  D --> D1[白屏率 / JS 错误率 / JSB 错误率]
  E --> E1[关键数据 update 后真实上屏]

  1. FCP、LynxFCP、FMP 的差异在“起点”和“终点”不同。

    • TotalFCP 从用户打开或容器 open_time 算到首次 DrawEnd，更接近用户体感。

    • FCP 从 PrepareTemplateStart 算到首次 DrawEnd，更偏模板准备后的首绘。

    • LynxFCP 从 LoadTemplateStart 算到首次 DrawEnd，更偏 Lynx 引擎自身首屏渲染。

    • ActualFMP/FMP 要靠业务标记关键 setState/updateData，表示核心业务内容真正完成渲染。

  2. “首帧”要分清楚是引擎首帧还是业务首帧。

    • 引擎首帧通常对应 LoadTemplate 后第一次 DrawEnd。

    • 业务首帧应以关键数据更新后的实际绘制完成为准，不能简单用接口返回或 setState 触发点替代。

  3. 容器耗时是 Lynx 渲染前的 Native/容器准备成本。

    • 典型包括 schema 解析、容器创建、LynxView 创建、JSB 注册、GlobalProps/initData 注入、业务插件初始化等。

    • 如果 TotalFCP 高但 LynxFCP 正常，问题更可能在容器初始化、资源加载或前置业务链路。

  4. 资源加载监控要能解释“从哪里加载、为什么失败、fallback 到哪里”。

    • 主模板 template.js 是核心资源；其加载成功率、错误率、加载耗时、离线化率是 P0/P1 指标。

    • 资源链路要看 pipeline、error_message、res_from、res_version、is_memory、is_request_reused 等字段。

  5. 白屏率是结果指标，不是原因指标。

    • 白屏可能由模板加载失败、离线资源/CDN 失败、JS 异常、JSB 失败、接口失败、渲染失败等导致。

    • 白屏监控必须和资源、JS、JSB、接口、Timing 数据一起看，才能归因。

一次 Lynx 页面打开的监控模型

可以把一次页面打开抽象成这条链路：

Mermaid · 流程图源码
flowchart LR
  A[open_time] --> B[schema / router]
  B --> C[容器初始化]
  C --> D[PrepareTemplate]
  D --> E[主模板 template.js]
  E --> F[LoadTemplate]
  F --> G[Decode / Lepus]
  G --> H[VDOM / Diff]
  H --> I[Layout / UI flush]
  I --> J[首次 DrawEnd]
  J --> K[JSRuntime 业务逻辑]
  K --> L[接口请求 / prefetch]
  L --> M[setState / updateData]
  M --> N[Update DrawEnd]
  N --> O[关键内容上屏<br/>ActualFMP / 业务首帧]

对应监控分层：

层次关注问题典型指标
容器层页面有没有进入容器、初始化是否慢容器初始化耗时、ContainerInited、页面加载成功率
资源层template.js 和子资源有没有拿到、从哪里拿、慢在哪里主模板资源加载成功率、错误率、离线化率、缓存命中率、CDN 成功率、资源下载耗时
Lynx 渲染层模板加载后首绘是否慢LynxFCP、FCP、TTI、Decode、VDOM、Layout、UI flush 耗时
JS/业务更新层数据回来后核心内容是否上屏ActualFMP、TotalActualFMP、业务首帧、接口耗时、WaitingUpdateDuration
异常层页面为什么不可用白屏率、JS 错误率、JSB 错误率、引擎错误率、静态资源错误率、接口请求错误率

内容可见性：FCP、LynxFCP 与 FMP

FCP 的实现口径

FCP 是 First Contentful Paint，表示页面从开始加载到任意内容首次完成绘制的耗时。这里的“内容”可以是文本、图片、SVG、非白色 canvas 等，不一定是业务真正关心的核心内容。

在 Lynx Timing 里，FCP 常见有两个起点：

Mermaid · 流程图源码
flowchart LR
  A[open_time] --> B[PrepareTemplateStart]
  B --> C[LoadTemplateStart]
  C --> D[首次 DrawEnd]

  A -. TotalFCP .-> D
  B -. FCP .-> D
  C -. LynxFCP .-> D
示意
FCP = Setup.DrawEnd - Setup.PrepareTemplateStart
TotalFCP = Setup.DrawEnd - open_time
LynxFCP = Setup.DrawEnd - Setup.LoadTemplateStart

两者区别：

指标起点终点说明
FCPPrepareTemplateStartLoadTemplate 后首次 DrawEnd衡量模板准备开始后的首次内容绘制
TotalFCPopen_timeLoadTemplate 后首次 DrawEnd包含用户打开到容器/资源准备/首绘的完整耗时，更贴近用户体感

实现方式：

  1. 容器或业务入口记录 open_time。

  2. 容器开始准备模板时记录 PrepareTemplateStart。

  3. Lynx SDK 内部记录 LoadTemplateStart/End、DrawEnd 等 timing。

  4. 容器监控模块收集 timing 并上报。

  5. 指标看板按页面、版本、系统、资源来源等维度消费。

LynxFCP 的实现口径

LynxFCP 更偏 Lynx 引擎内部指标，目的是排除容器初始化、资源下载、业务前置流程等干扰，只看模板进入 Lynx 后到首次绘制完成的耗时。

示意
LynxFCP = Setup.DrawEnd - Setup.LoadTemplateStart

它覆盖的主要阶段包括：

Mermaid · 流程图源码
flowchart LR
  A[LoadTemplateStart] --> B[template decode]
  B --> C[lepus 执行]
  C --> D[create VDOM]
  D --> E[dispatch DOM]
  E --> F[layout]
  F --> G[ui_operation_flush]
  G --> H[DrawEnd]

  A -. LynxFCP .-> H

归因方式：

  • TotalFCP 高、LynxFCP 正常：问题更可能在容器初始化、资源加载、CDN/离线资源、业务前置逻辑。

  • LynxFCP 高：问题更可能在模板复杂度、节点数量、布局计算、UI flush、Lynx 渲染链路。

FMP / ActualFMP 的实现口径

FMP 是 First Meaningful Paint，表示用户真正关心的关键内容完成渲染。它和 FCP 最大的区别是：FCP 可能只是 loading 或占位内容出现，FMP 必须是核心业务内容可见。

Lynx SDK 无法天然知道哪个内容对业务“有意义”，所以需要业务侧主动标记。

典型实现：

Mermaid · 流程图源码
flowchart LR
  A[请求关键业务数据] --> B[数据返回并解析]
  B --> C[setState / setData / updateData]
  C --> D[携带 __lynx_timing_actual_fmp]
  D --> E[Update 后首次 DrawEnd]
  E --> F[ActualFMP / TotalActualFMP]

常见计算：

示意
ActualFMP = Update.DrawEnd - Setup.PrepareTemplateStart
TotalActualFMP = Update.DrawEnd - open_time
FMP = MAX(ActualFMP, FCP)
TotalFMP = MAX(TotalActualFMP, TotalFCP)

如果业务没有标记 ActualFMP，监控侧通常只能退化使用 FCP 或无法产出真实业务 FMP。因此对业务页面来说，关键不是“有没有 FMP 指标”，而是有没有把真正关键的 setState/updateData 标出来。

业务页面可以这样定义：

  • loading 或骨架屏出现：最多算 FCP。

  • 标题、封面、主按钮、价格/权益/状态等关键内容基于接口数据展示完成：算业务 FMP 或业务首帧。

链路分解：容器、首帧与资源加载

容器耗时的实现口径

容器耗时是进入 Lynx 渲染前，Native 容器和业务框架的准备成本，可以通过 ContainerInited 这类自定义指标记录容器准备业务数据或组件的时间。

可以按下面方式理解：

Mermaid · 流程图源码
flowchart LR
  A[open_time] --> B[schema / router 解析]
  B --> C[容器实例创建]
  C --> D[LynxView 创建]
  D --> E[业务上下文准备]
  E --> F[JSB / NativeModule 注册]
  F --> G[GlobalProps / initData 注入]
  G --> H[插件初始化]
  H --> I[container_inited]

  A -. ContainerInited .-> I

常见计算：

示意
ContainerInited = container_init_end - open_time
container_create_cost = container_create_end - container_create_start

实际项目里不一定只有一个容器耗时指标，可能会继续拆成 schema 解析、LynxView 创建、插件初始化、GlobalProps 注入等子阶段。是否要拆到这么细，取决于线上归因需要。

首帧的实现口径

“首帧”要先定义清楚，否则很容易和 FCP/FMP 混在一起。

引擎首帧

引擎首帧通常就是 LoadTemplate 后第一次 DrawEnd，对应 LynxFCP 的结束点。

示意
引擎首帧 = first DrawEnd after LoadTemplate

它说明 Lynx 模板是否已经画出第一帧，但不保证关键业务数据已经展示。

业务首帧

业务首帧是关键业务内容真正上屏。它应该由业务定义关键模块，而不是由 SDK 自动猜。

典型实现：

Mermaid · 流程图源码
flowchart LR
  A[页面启动] --> B[请求关键接口]
  B --> C[数据解析]
  C --> D[setState / updateData]
  D --> E[等待 2-4 帧<br/>或监听绘制完成]
  E --> F{关键 View 是否可见?}
  F -- attach / visible / size / alpha 正常 --> G[上报业务首帧]
  F -- 不满足 --> H[继续等待或上报异常]

为什么不能把接口返回或 setState 当成首帧：

  • 接口返回只代表数据到了，不代表 UI 已经更新。

  • setState/updateData 只代表触发更新，不代表 Draw/Layout/Flush 已完成。

  • Android/iOS 真正显示还要经过后续渲染管线。

资源加载指标的实现口径

资源层是 Lynx 稳定性和首屏性能的前置条件，尤其是主模板 template.js。

Mermaid · 流程图源码
flowchart LR
  A[请求 template.js / 子资源] --> B{Memory 命中?}
  B -- 是 --> Z[返回资源]
  B -- 否 --> C{离线资源命中?}
  C -- 是 --> Z
  C -- 否 --> D{Builtin 命中?}
  D -- 是 --> Z
  D -- 否 --> E{CDN 请求成功?}
  E -- 是 --> Z
  E -- 否 --> F[资源加载失败]

  F --> G[error_message]
  A --> H[pipeline 记录尝试路径]
  Z --> I[res_from / res_version / 耗时上报]

核心指标：

指标口径说明
主模板资源加载成功率资源加载成功 PV / 成功失败总 PV判断 template.js 是否能成功获取
主模板资源加载错误率资源加载失败 PV / 资源加载总 PV和成功率互补，用于报警
主模板资源加载耗时资源从触发请求到返回的总耗时影响 FCP/TotalFCP
主模板资源离线化率离线化资源数 / 总资源数判断是否能走离线资源
静态资源错误率发生静态资源错误的页面 PV / 页面总 PV关注图片、样式、子资源等
CDN 成功率CDN 请求成功次数 / CDN 请求总次数离线未命中后的 fallback 能力
缓存命中率memory/offline/request reuse 命中次数 / 请求总次数影响资源下载和首屏速度

排查时重点看：

示意
pipeline：这次资源请求依次尝试了哪些加载方式
error_message：每一层加载方式为什么失败
res_from：最终资源来自哪里
res_version：资源版本
is_memory：是否命中内存缓存
is_request_reused：是否命中请求复用
res_load_perf：资源加载性能数据
res_load_error：资源加载错误数据

异常指标与性能归因

白屏率和异常率的实现口径

白屏率是结果指标，通常由 watchdog 或容器监控能力发现，但归因要依赖前面几层数据。

Mermaid · 流程图源码
flowchart TD
  A[白屏 / 首屏超时] --> B{主模板加载成功?}
  B -- 否 --> B1[资源问题<br/>Memory / 离线资源 / CDN]
  B -- 是 --> C{JS 是否异常?}
  C -- 是 --> C1[JS Error / Promise Reject]
  C -- 否 --> D{关键 JSB 是否失败?}
  D -- 是 --> D1[JSB 错误 / 能力不兼容]
  D -- 否 --> E{关键接口是否成功?}
  E -- 否 --> E1[接口失败 / 数据解析失败]
  E -- 是 --> F{Update 后是否绘制?}
  F -- 否 --> F1[setState 未触发 / 渲染失败]
  F -- 是 --> G[检查可见性判断或白屏检测误差]

白屏可能原因：

  • 主模板加载失败；

  • CDN 或离线资源失败；

  • JS 初始化失败；

  • JS 运行异常；

  • JSB 关键能力失败；

  • 接口请求失败或数据解析失败；

  • setState/updateData 没触发；

  • 触发了更新但渲染失败；

  • 容器 attach/show 生命周期异常。

业务 Lynx 监控中常见的质量指标包括：

指标口径
JS 错误率发生 JS 错误的页面 PV / 页面总 PV
引擎错误率发生引擎错误的页面 PV / 页面总 PV
JSB 错误率发生 JSB 错误的页面 PV / 页面总 PV
静态资源错误率发生静态资源错误的页面 PV / 页面总 PV
接口请求错误率发生接口请求错误的页面 PV / 页面总 PV

需要注意：这些页面级错误率常以页面 PV 为分母，不等于某个 JSB、某个接口、某个资源自身的调用成功率。如果要定位具体方法或 URL，需要额外按 method/url/resource 维度上报。

如何用这些指标做归因

常见归因可以按下面判断：

Mermaid · 流程图源码
flowchart TD
  A[线上指标异常] --> B{TotalFCP 高?}
  B -- 是 --> C{LynxFCP 高?}
  C -- 否 --> C1[容器 / 资源 / 前置业务慢]
  C -- 是 --> C2[模板复杂 / VDOM / Layout / UI flush 慢]
  B -- 否 --> D{FCP 正常但 FMP 高?}
  D -- 是 --> D1[接口慢 / prefetch 失效 / update 慢]
  D -- 否 --> E{白屏率高?}
  E -- 是 --> E1[结合资源 / JS / JSB / 接口错误归因]
  E -- 否 --> F{JSB 错误率高?}
  F -- 是 --> F1[Native 能力不可用 / 低版本不兼容 / 参数错误]
  F -- 否 --> G[继续看页面维度和单点日志]
现象更可能的问题
TotalFCP 高，LynxFCP 正常容器初始化、资源加载、CDN/离线资源、前置业务逻辑慢
LynxFCP 高模板复杂、节点过多、VDOM 创建、Layout、UI flush 慢
FCP 正常，ActualFMP/TotalFMP 高loading 出来了，但关键接口慢、prefetch 失效、setState/update 慢
资源加载耗时高离线未命中走 CDN、模板包过大、CDN 慢、缓存策略异常
白屏率高结合资源错误、JS 错误、JSB 错误、接口错误、容器生命周期继续拆因
JSB 错误率高Native 能力不可用、参数不兼容、低版本缺方法、权限/登录态问题
