Lynx 页面加载监控与异常定位

Lynx 页面加载涉及容器准备、资源加载和页面渲染。监控需要记录各阶段耗时，并关联同一次页面打开中的异常，才能定位加载慢或白屏的原因。

实现上，由宿主记录页面入口和资源请求，Lynx 提供渲染事件，业务标记关键内容。三类数据按页面打开记录关联，避免把接口返回、首次绘制和内容可见混为一个指标。

1. 页面加载过程与监控目标

以详情页为例：容器创建后加载页面包，页面先显示骨架屏，业务数据返回后再显示正文。容器准备、页面包请求和数据请求可能重叠，不能把各阶段耗时直接相加。

观察目标需要记录的证据能定位的范围
页面迟迟没有显示页面入口、容器就绪、页面包就绪、首次渲染事件容器准备、资源等待或首次渲染
骨架屏显示后等待较久关键数据返回、更新提交、关键内容渲染事件数据请求、更新调度或更新渲染
页面持续空白页面前后台状态、容器可见性、资源和运行时异常加载失败、渲染失败或可见性异常

页面包与容器

页面包是构建工具生成的 Lynx 加载产物。容器是宿主应用中负责创建页面、加载资源和管理生命周期的代码；它的耗时也属于用户打开页面后的等待时间。

2. 采集方案对比与整体架构

2.1 三类数据的分工

对比维度框架性能事件宿主与业务埋点性能追踪
主要覆盖包加载、渲染过程、框架指标打开入口、资源请求、业务内容条件线程调度与细分执行阶段
判断依据框架定义的时间点业务约定的开始、结束条件执行片段及时间关系
接入工作注册回调，适配 SDK 字段接入容器、资源层和关键组件录制、关联标记、分析轨迹
数据成本按需订阅事件控制字段数量和上报频率单次记录体积较大
主要限制无法自动识别全部业务条件容易漏埋或误用回调时间不适合替代全部页面的常规统计

常规监控组合前两类数据；阶段耗时异常时，再用性能追踪细查。这样既能知道哪些页面变慢，也能继续定位到具体执行过程。

2.2 整体架构

每次打开页面创建一条记录；同一容器重新加载页面包时，再创建新的加载编号。采集时保留加载上下文，并用事件中的加载或渲染标识确认归属，防止旧页面事件写入新页面。无法区分重载事件时，使用独立页面实例采集。

上报只保留定位需要的信息：页面类型、宿主版本、SDK 版本、页面包版本、资源来源和错误类别。请求地址去除用户参数，正文与接口响应内容不进入性能记录。

SDK 接口

下文使用 Lynx 3.5 的 Performance API 命名。它提供首次加载、渲染过程和指标事件；客户端回调在异步线程执行，采集时读取事件自身的时间戳，不用回调到达时间代替渲染完成时间，也不在回调中直接操作界面。接口说明

3. 阶段耗时与关键内容标记

3.1 统一指标的起点和终点

先确定业务要观察的区间，再将 SDK 事件映射到区间端点。下表中的中文名称属于容器监控定义。

指标起点终点数据来源
容器准备耗时开始创建容器容器具备加载条件宿主埋点
页面包获取耗时本次请求发出得到可用页面包资源加载器
首次渲染耗时开始向 Lynx 加载页面包对应首次渲染完成点加载埋点与框架事件
打开至首次内容耗时页面打开入口对应首次内容完成点入口埋点与框架事件
打开至关键内容耗时页面打开入口全部必需内容满足展示条件入口、业务标记及渲染事件
数据更新渲染耗时关键数据更新提交对应更新渲染完成点业务埋点与关联的渲染事件

框架指标保留原始名称与定义。看板中的“打开至首次内容”单独计算，避免把起点不同的指标放进同一条曲线。

指标与事件对应

FCP 表示首次内容绘制，LynxFCP 侧重框架内的首绘区间，ActualFMP 对应业务标记的关键内容渲染。首次加载用 LoadBundleEntry 查看过程，标记后的更新用 PipelineEntry 关联；具体起止字段按 SDK 版本读取。

时间戳

区间两端必须使用同一单调时钟和单位。SDK 时间戳、宿主时钟及服务端时间不能未经转换直接相减。预加载可能早于页面打开，应单独记录预加载成本和打开后的剩余等待。

3.2 关键内容的完成条件

详情页可以把“标题、价格和购买按钮已按业务数据显示”定义为关键内容完成。骨架屏、空容器和请求成功都不能满足这个条件。

实现时，数据就绪后再为关键节点设置渲染标记，采集对应的完成事件。多个必需模块分别标记，全部完成后才结束业务首屏计时；合法的空数据页面则使用约定的空态展示条件。

渲染标记

Lynx 3.5 使用节点属性 __lynx_timing_flag 关联渲染过程；值为 __lynx_timing_actual_fmp 时还会产生 ActualFMP 事件。同一个标记只记录首次命中，多个模块需要不同标记，不能给标题和图片复用同一个值。标记规则

如果封面图属于必需内容，还要关联图片资源完成状态及其实际展示事件。文本容器完成渲染不能证明图片已经显示。遮挡、退到后台或容器脱离窗口，也需要结合宿主生命周期判断。

固定等待两三帧无法判断内容是否加载成功，不作为完成条件。普通布局回调、更新提交回调与性能事件也要分别处理。

3.3 页面记录与终态处理

页面记录在打开时创建，在成功、失败、超时或用户离开时结束。所有状态更新放到同一个串行处理队列中，结束后拒绝再次结算。

示意
收到事件：
  查找事件绑定的页面记录和加载编号
  记录不存在、已经结束或编号不符：忽略
  按事件标识去重，保存事件时间与结果
  出现确定的加载失败：结束为失败
  全部必需内容完成且页面处于可见状态：结束为成功

到达截止时间：仍未结束的记录标记为超时
用户离开页面：仍未结束的记录标记为取消

进入后台时停止本次前台首屏统计，并记录为中断；恢复前台后按恢复展示单独计时。超时后的迟到事件可以补充诊断信息，但不把原超时记录改写成成功。

注册与释放

观察器在加载前注册，页面销毁时释放。重新加载需要重置业务完成条件和事件归属；复用容器时只看容器实例无法区分前后两次加载。

4. 资源失败、白屏与错误率

4.1 资源请求保留每次尝试

一次页面包请求可能先读缓存，失败后再下载。请求记录需要保存每次尝试的来源、开始时间、结果和错误码，同时记录最终来源及页面包版本。

“缓存读取失败后下载成功”属于一次成功的页面包获取，同时包含一次失败的缓存尝试。只保留最终结果会丢失等待原因；把每次尝试都算作页面加载失败，又会高估失败率。

统计项分子分母
页面包获取成功率最终获取成功的逻辑请求数已完成的成功与失败逻辑请求数
网络下载成功率成功的网络尝试数已完成的成功与失败网络尝试数
内存缓存命中率直接由内存缓存返回的逻辑请求数纳入缓存策略的逻辑请求数
离线包使用占比最终由离线包返回的逻辑请求数成功获取的逻辑请求数

取消和超时另列；这些指标使用不同分母，不能互相补成 100%。共享进行中的请求属于请求复用，也不计为内存缓存命中。

4.2 区分白屏与首屏超时

首屏超时表示截止时间内没有收到有效的完成信号。它可能来自加载慢，也可能来自埋点遗漏。只有同时获得页面可见且内容为空的检测证据，才能进一步标记为疑似白屏。

运行时错误、原生能力调用失败和接口失败要关联到页面记录，但不能仅凭同时发生就认定因果。例如非关键埋点调用失败，不应直接归因为白屏。

加载期间的页面级错误率按页面去重：加载期间发生某类错误的页面打开数，除以同一批页面打开总数。接口调用失败率按调用次数统计；一次页面连续失败三次，对前者计一次，对后者计三次。

采样在页面打开时决定，并让该页面的阶段和结果事件沿用同一决定。若异常记录另行全量收集，错误率应使用独立完整计数或正确的加权统计，不能直接除以已采样的正常页面数。

5. 定位示例与实现验证

5.1 从总耗时定位到资源等待

下面是一组用于演示计算的时间点，单位为毫秒：

事件相对页面打开的时间
页面打开、页面包请求发出0
容器准备完成40
关键业务数据就绪120
页面包获取完成、提交 Lynx 加载300
首次内容完成340
关键内容完成360

打开至首次内容耗时为 340 ms，其中页面包在 300 ms 才就绪，提交后渲染耗时为 40 ms。优先检查资源请求的尝试记录，确认是缓存未命中、下载慢还是读取失败后重试。

容器准备和数据请求都与资源等待重叠，因此不能再把 40 ms 和 120 ms 加到 340 ms 上。若总耗时下降，也要确认关键内容完成时间和失败率没有变差。

5.2 验证采集结果

验证场景应观察到的结果
人为延迟页面包返回资源区间增长，渲染区间不应等量增长
人为延迟业务数据骨架屏可先完成，关键内容完成点后移
页面包获取失败产生失败终态，保留尝试记录与错误码
打开后立即退出或切后台记录取消或中断，不进入成功首屏耗时样本
快速连续重载不串用旧回调，每次加载最多结算一次
故意遗漏关键标记产生超时，不能仅凭缺少回调判定白屏

验收时同时检查耗时分布、失败率、取消占比和事件完整率。阶段记录完整后，总耗时才能用于发现问题，分段耗时才能用于选择排查方向。
