卡顿与丢帧排查

卡顿排查的目标不是找到一个“超过 16.6ms 的函数”，而是确认哪一帧没有按计划显示，以及延误发生在 App、系统调度、SurfaceFlinger、GPU、DisplayHAL 还是输入链路。

Android 一帧的生产和上屏机制见 渲染流程 与 Android 渲染上屏流程。本文只保留定位丢帧所需的系统边界和排查方法。

一、什么才算丢帧

显示系统会为每一帧预测一个呈现时间。现代 Android 的 FrameTimeline 将一帧判定为 Jank，核心依据是实际呈现是否符合调度器预测的呈现时间，而不只是某个函数是否超过固定时长。

刷新率名义刷新周期
60 Hz16.67ms
90 Hz11.11ms
120 Hz8.33ms

刷新周期只是理解帧预算的起点。真正的 deadline 还受 VSYNC 调度、应用提交、GPU Fence、SurfaceFlinger 合成和显示设备呈现时机影响。

text
某次 doFrame 超过 16.6ms
  ≠ 必然能直接证明最终屏幕掉帧

某次 doFrame 没超过 16.6ms
  ≠ 必然能证明最终按时上屏

需要区分三种现象：

  1. 呈现 Jank：新帧没有在预测时间显示，屏幕延迟显示或重复旧内容。

  2. 高延迟：画面可能仍然保持均匀，但 Buffer 排队使输入到显示的延迟变大。

  3. 逻辑卡顿：每帧都按时上屏，但动画位移、数据时间戳或手势采样不均匀，肉眼仍然感觉跳变。

平均 FPS 会掩盖连续卡顿和帧率波动。监控应同时观察 Jank 率、连续丢帧、最大超期时间和 P50/P90/P95/P99 分布。

二、从输入到屏幕的责任链

Mermaid · 流程图源码
flowchart LR
    I[InputReader /<br/>InputDispatcher] --> U[App UI Thread<br/>Choreographer / ViewRootImpl]
    U --> R[RenderThread / HWUI]
    R --> G[GPU 绘制]
    G --> B[Surface / BufferQueue]
    B --> S[SurfaceFlinger]
    S --> C[HWC 或 GPU 合成]
    C --> D[DisplayHAL / 显示设备]

    CPU[CPU 调度 / 频率 / Thermal] -.影响.-> U
    CPU -.影响.-> R
    MEM[内存压力 / 回收 / I/O] -.影响.-> U
    MEM -.影响.-> S
    SYS[system_server<br/>Binder / 锁] -.阻塞.-> U

App 负责按时生成和提交自己的 buffer；SurfaceFlinger 负责收集各 Layer、完成合成并提交显示设备。任何一段错过 deadline，最终都可能表现成前台 App 卡顿。

因此“前台 App 卡了”只描述现象，不能直接把责任归给 App。

三、FrameTimeline 如何归因

Android 12 及以上的 Perfetto FrameTimeline 同时提供 App 和 SurfaceFlinger 的 Expected Timeline、Actual Timeline，并用 token 把 App 帧关联到最终 DisplayFrame。

text
App Expected / Actual Frame
       │ frame token
       ▼
SurfaceFlinger Expected / Actual Frame
       │ display frame
       ▼
最终呈现
Jank 类型含义优先检查
AppDeadlineMissedApp 的 CPU、RenderThread 或 GPU 工作未按 deadline 完成doFrame、traversal、RenderThread、GPU completion
BufferStuffingApp 持续提交过快，BufferQueue 中积压未呈现 bufferqueue/dequeue、生产速率、输入到显示延迟
SurfaceFlingerCpuDeadlineMissedSurfaceFlinger 主线程未按时完成Layer 计算、事务处理、设备合成阻塞
SurfaceFlingerGpuDeadlineMissedSurfaceFlinger CPU 阶段完成，但 GPU 合成未按时完成GPU 负载、Client Composition、Fence
DisplayHALSurfaceFlinger 已提交，但显示 HAL 没有按预期 VSYNC 呈现HWC、DisplayHAL、Fence、面板链路
PredictionError调度器预测时间和硬件 VSYNC 发生偏移刷新率切换、调度预测；孤立事件不一定可感知
Unknown已出现 deadline 异常，但现有证据不能完整归因补充调度、Fence、Binder 和厂商轨道

FrameTimeline 当前对部分 SurfaceView 场景存在覆盖限制。游戏、视频等独立 Surface 需要结合对应 Layer、生产者渲染线程、SurfaceFlinger 和显示轨道判断，不能只依赖 View 体系的帧指标。

四、系统侧常见根因

1. CPU 调度和频率

线程状态能区分“代码执行慢”和“没有被调度”：

Trace 现象说明
长时间 Running线程真实占用 CPU，检查计算、布局、绘制或序列化
长时间 Runnable线程已经可运行，但拿不到 CPU，检查系统负载、优先级和 CPU 亲和性
Sleeping / futex可能在等待锁、条件变量、Binder 或其他线程
Uninterruptible Sleep常见于块设备 I/O 等不可中断等待

系统层面的典型原因包括：

  • UI Thread 或 RenderThread 被调度到性能不足的小核。

  • 关键线程优先级不足，长时间处于 Runnable。

  • 被实时线程或大量后台线程抢占。

  • CPU 频率未及时提升，或被错误限制在低频。

  • 设备过热触发 Thermal 限频，CPU/GPU 可用性能下降。

单看进程 CPU 使用率无法证明主线程卡在哪里。必须结合 sched_wakeup、sched_switch、线程状态、CPU frequency 和 Thermal 轨道。

2. system_server、Binder 和锁

App 在主线程同步调用系统服务时，可能等待：

text
App 主线程 Binder 调用
  -> system_server Binder 线程排队
  -> 等待 AMS / ATMS / WMS 等关键锁
  -> 系统服务处理
  -> Binder 返回
  -> App 继续当前帧

如果 App 主线程处于 Sleeping，且 Binder flow 指向 system_server，应继续检查：

  • Binder 线程池是否繁忙。

  • 服务端是否在等待全局或关键锁。

  • 锁持有者是否执行磁盘 I/O、跨进程调用或复杂计算。

  • 窗口事务、Activity 切换和输入焦点更新是否被同一锁链阻塞。

“主线程没有执行耗时 Java 方法”不能排除 App 帧超时，它可能一直在等待系统服务返回。

3. SurfaceFlinger 和显示链路

系统篇文章中的 SurfaceFlinger、HWC、CRTC 问题，可以在现代链路中归纳为：

text
SurfaceFlinger 主线程
  -> 处理 Layer / Transaction
  -> 选择 HWC Device Composition 或 GPU Client Composition
  -> 等待 GPU / Acquire Fence
  -> 提交 DisplayHAL
  -> Present Fence 完成

常见问题包括：

  • Layer 或事务过多，Layer 树计算和合成决策耗时。

  • 复杂透明、缩放、旋转或格式不受 HWC 支持，回退 GPU 合成。

  • SurfaceFlinger 主线程执行过久，或者被调度延迟。

  • App、GPU、HWC 之间的 Fence 长时间未 signal。

  • DisplayHAL/HWC 提交耗时，最终错过硬件 VSYNC。

  • 刷新率切换或 VSYNC 预测异常，造成帧节奏不稳定。

App 的 queueBuffer() 或 dequeueBuffer() 阻塞，有时只是下游 SurfaceFlinger、GPU 或 BufferQueue 拥塞向上游传播的结果，不能看到调用点就直接归因于 App。

4. 内存压力和 I/O

现代 Android 主要由 userspace lmkd 监控内存压力，Android 10 及以上可使用 PSI 描述任务因为 CPU、内存或 I/O 资源不足而被阻塞的时间。

Mermaid · 流程图源码
flowchart LR
    A[可用内存不足] --> B[直接回收 / kswapd<br/>swap / page cache refault]
    B --> C[CPU 与磁盘 I/O 竞争]
    C --> D[UI / RenderThread<br/>调度或缺页变慢]
    D --> E[错过帧 deadline]

    A --> F[lmkd 杀后台进程]
    F --> G[进程被业务重新拉起]
    G --> C

排查低内存不能只看 MemFree。还要结合：

  • MemAvailable、swap/ZRAM 使用情况。

  • /proc/pressure/memory 与 /proc/pressure/io。

  • kswapd、direct reclaim、major page fault 和 page cache refault。

  • lmkd kill 记录以及进程反复死亡、重启。

  • App GC 和系统后台回收任务的 CPU 占用。

低内存引发的卡顿通常是 CPU、I/O、缺页和进程重启共同作用，不是 lmkd 单点耗时。

5. Input 链路不均匀

连续滑动时，如果 InputReader 报点不均匀、InputDispatcher 调度延迟、目标窗口切换或 Accessibility 处理过重，App 收到的输入本身就可能出现空洞。

这类问题不一定是“画面渲染失败”，而可能是没有新的输入状态可供动画或手势更新，用户同样会感到画面停顿。应同时检查：

text
EventHub / InputReader 报点
  -> InputDispatcher 选窗与派发
  -> InputChannel
  -> App InputEventReceiver
  -> Choreographer CALLBACK_INPUT
  -> 动画与绘制

完整输入链路见 Input 输入系统流程。

五、先判断 App 还是系统

Mermaid · 流程图源码
flowchart TD
    A[用户感知卡顿] --> B[定位具体场景和问题帧]
    B --> C{FrameTimeline 归因}
    C -->|AppDeadlineMissed| D[检查 UI Thread<br/>RenderThread / GPU]
    C -->|SF CPU / GPU| E[检查 SurfaceFlinger<br/>Layer / Fence / 合成]
    C -->|DisplayHAL| F[检查 HWC / DisplayHAL<br/>硬件 VSYNC]
    C -->|无明确归因| G[检查调度、Binder、锁<br/>内存、I/O、Input]

    D --> H{线程为何超时}
    H -->|Running| I[业务计算 / 布局 / 绘制]
    H -->|Runnable| J[CPU 竞争 / 优先级 / 频率]
    H -->|Sleeping| K[锁 / Binder / 条件等待]
    H -->|D 状态| L[块 I/O / 内存回收]

排查顺序应从问题帧向两端展开，而不是先抓一个主线程堆栈就开始优化：

  1. 明确操作、页面、Window/Layer、刷新率和问题时间点。

  2. 用 FrameTimeline 判断 App 帧还是 SurfaceFlinger/DisplayFrame 延误。

  3. 关联 App UI Thread、RenderThread、GPU completion 和 SurfaceFlinger 帧 token。

  4. 根据线程状态判断是执行、调度、锁、Binder 还是 I/O。

  5. 检查 CPU 频率、Thermal、内存压力和后台负载等系统条件。

  6. 回到源码或业务 TraceSection，确认具体函数和依赖关系。

六、不同工具分别能证明什么

工具适用场景能证明什么主要边界
Choreographer.FrameCallbackApp 内轻量趋势监控主线程帧回调间隔、回调是否延迟看不到最终呈现，不能区分 RenderThread、SF 和 DisplayHAL
FrameMetricsAPI 24+ Window 帧阶段统计Window 每帧多个阶段的耗时回调运行在注册时指定的 Handler；仍不是完整系统归因
JankStats线上 Window 级 Jank 与场景聚合帧耗时、Jank 判断、业务 UI State每个 Window 单独注册；回调必须轻量，数据对象需要及时复制
dumpsys gfxinfo ... framestats本地快速查看View 体系近期帧统计信息有限，不足以还原跨进程根因
Perfetto FrameTimelineAndroid 12+ 单次问题定位App 与 SF 的 Expected/Actual Timeline、Jank 类型和关联帧需要复现或命中采样；部分 SurfaceView 场景覆盖有限
Android Studio System Trace开发阶段交互分析UI Thread、RenderThread、GPU、调度和 FrameTimeline不适合作为长期线上全量监控
Macrobenchmark FrameTimingMetric固定场景回归测试frameOverrunMs、frameDurationCpuMs 的分位数证明测试场景回归，不代表全部线上设备

Window.addOnFrameMetricsAvailableListener() 的回调在传入的 Handler 所在线程执行，不必占用主线程；但回调本身仍应只复制和聚合数据，不能做日志格式化、磁盘 I/O 或网络上报。

Choreographer 更适合发现“主线程帧回调出现了多大间隔”，不能把它统计的 FPS 当作最终屏幕真实 FPS。最终呈现归因优先看 FrameTimeline。

七、线上监控到线下定位

text
JankStats / FrameMetrics / 自研监控
  -> 聚合页面、操作、设备、刷新率、版本、温度和内存状态
  -> 识别高频场景与连续卡顿
  -> Macrobenchmark 或本地脚本稳定复现
  -> Perfetto 捕获问题帧
  -> FrameTimeline 确定责任层
  -> 调度 / Binder / 锁 / 内存 / GPU 继续下钻
  -> 修复后做同场景回归和线上分层验证

线上事件建议至少包含：

  • 页面、操作、动画阶段和 Window 标识。

  • 当前刷新率、帧开始时间、帧耗时和超期时间。

  • 单帧/连续 Jank 数量及最大连续时长。

  • 前后台、冷启动/普通交互、设备等级和系统版本。

  • CPU/内存压力、Thermal 状态和 GC 计数的轻量快照。

  • 命中采样时的主线程堆栈或 Perfetto trace 标识。

不要每帧上传原始数据。线上先按一次交互、一次滑动或固定时间窗聚合，只对严重和高价值场景提高采样率。

八、按责任层优化

责任层常见优化方向
UI Thread拆分长 Message，移除同步 I/O/Binder，减少重复 measure/layout、对象分配和图片解码
RenderThread/GPU降低过度绘制、纹理上传、复杂阴影与模糊，复用纹理，控制离屏渲染
BufferQueue控制 producer 节奏，避免 BufferStuffing；低延迟场景限制无意义排队
SurfaceFlinger减少不必要 Layer 和事务，降低透明混合、复杂变换及 GPU 合成压力
CPU 调度控制后台并发，避免线程爆炸；系统侧再检查优先级、核分配和频率策略
内存降低峰值和抖动，减少 page cache thrashing、频繁 GC 与进程杀死重启
Thermal降低持续 CPU/GPU 功耗，避免优化只在冷机短测中成立
Input检查报点、派发和消费节奏，避免把输入空洞误判为渲染耗时

IdleHandler、线程池和异步化都不是无成本方案。Idle 可能长期得不到执行机会，后台任务也会争抢 CPU、I/O 和内存带宽。是否移出关键帧，要以 trace 中的 deadline 和资源竞争结果验证。

九、常见误判

  1. 主线程超过 16.6ms 就一定掉帧：刷新率和实际 deadline 会变化，还要看 RenderThread、GPU、SurfaceFlinger 和最终呈现。

  2. 主线程没耗时就是系统问题：主线程可能在 Runnable、Binder、锁或 I/O 等待中。

  3. 三缓冲能解决掉帧：它能降低 producer 阻塞、改善吞吐，也可能带来 BufferStuffing 和额外输入延迟。

  4. 平均 FPS 高就足够流畅：连续两三帧超期通常比零散慢帧更明显，帧间隔方差也很重要。

  5. Choreographer 回调就是屏幕帧：它只看到 App 侧 Looper 的帧调度，不能证明最终显示时间。

  6. 看到 queueBuffer/dequeueBuffer 慢就是 App 问题：可能是下游 buffer、Fence、SurfaceFlinger 或显示链路反压。

  7. 低内存只会导致 LMK 杀进程：回收、swap、缺页、I/O 和重启风暴在 kill 前后都可能造成卡顿。

  8. 所有卡顿都能在 FrameTimeline 里解释：输入不均、逻辑动画跳变和部分独立 Surface 场景还需要其他证据。
