Android 插件化

插件化是模块级动态化：插件 APK 没有被系统真正安装，但宿主要让它在宿主进程里像正常 Android 包一样运行。

前置知识：

  • Activity 启动与显示流程

一、实现原理

1. 插件化要解决的问题

  • 组件入口：系统怎么允许启动插件 Activity / Service / Provider。

  • 类加载：ActivityThread 怎么找到插件 dex 里的类。

  • 资源加载：插件 layout、string、drawable、theme 怎么可用。

  • 运行环境：LoadedApk、ApplicationInfo、so、PackageManager 查询怎么补齐。

2. 如何启动插件内的 Activity

2.1 启动限制

Activity 启动会先经过 ATMS/AMS。系统校验主要看已安装 APK 的 Manifest，例如 Activity 是否声明、launchMode、task、process、exported、permission 等。插件 APK 没有被系统安装，所以插件 Activity 不能直接被 ATMS/AMS 识别。

插件化要分两段处理：

  • 系统校验阶段：让系统看到宿主已声明的 Activity 或 StubActivity。

  • App 创建阶段：把启动记录还原成插件真实 Activity。

2.2 启动方案

常见方案按 Activity 语义保真度分三类：

  • 宿主 Manifest 预声明：系统直接校验宿主声明，创建类时再由 Mira ClassLoader 从插件 dex 找实现。适合 launchMode、taskAffinity、windowSoftInputMode 等系统语义要求高的页面；缺点是不能动态新增未声明 Activity。

  • StubActivity 换壳：宿主 Manifest 预埋 StubActivity，启动前把插件 Intent 替换成 StubIntent；回到 App 进程后再还原 targetIntent 和 targetActivityInfo。适合动态新增 Activity。

  • ProxyActivity 容器：宿主只启动一个 ProxyActivity，插件页面由 ProxyActivity 内部分发生命周期。实现稳定，但业务模型不再完全等价原生 Activity。

宿主预声明示例：

xml
<activity
    android:name="com.game.plugin.GameActivity"
    android:launchMode="singleTask"
    android:theme="@style/HostPluginActivityTheme" />

2.3 Mira 透明启动流程

Mira 选择 Hook 系统启动链路，是为了让业务 Activity 尽量保持原生写法。

text
Mira.init
  -> 初始化插件配置、ClassLoader、Resources、LoadedApk Map

Mira.start
  -> Hook Instrumentation / ActivityThread.H / AM-ATMS / PM

startActivity(pluginIntent)
  -> 宿主 Manifest 已声明：原 Intent 放行
  -> 未声明：插件 ActivityInfo -> 选择 StubActivity -> 构造 StubIntent

ATMS/AMS
  -> 看到宿主 Activity 或 StubActivity，校验通过

ActivityThread.H
  -> 从 StubIntent extras 取出 targetIntent / targetActivityInfo
  -> 创建前把启动记录还原成插件 Activity

Instrumentation.newActivity
  -> Mira ClassLoader 找到插件类并创建实例

StubIntent 的 extras 里会带：

  • target_intent

  • target_activityinfo

  • stub_activityinfo

2.4 Mira 透明方案的 Hook 点

Mira 的 Hook 不是 Xposed 这类外部框架，而是反射改字段 + JDK 动态代理 + 委托对象替换。

Hook 点插入位置作用
InstrumentationActivityThread.mInstrumentation拦 execStartActivity / newActivity
ActivityThread.HActivityThread.mH.mCallback创建前把 Stub 还原成插件 Activity
IActivityManager / IActivityTaskManager系统 Singleton 的 mInstance兜底 startActivity，处理 Service / Provider / Receiver
IPackageManagerActivityThread.sPackageManager / PackageManager.mPM让插件组件能被 query / resolve / getInfo
ClassLoaderPathClassLoader.parent 或 LoadedApk.mClassLoader宿主找不到类时路由到插件
LoadedApkActivityThread.mPackages给插件构造包运行环境
ResourcesAssetManager / Resources / ResourcesManager让插件资源和 theme 可用

3. ClassLoader 和 LoadedApk 设计

3.1 总 ClassLoader 负责路由

Mira 分两层：

  • 总 ClassLoader：MiraClassLoader / DyMiraClassLoader，负责路由。

  • 插件 ClassLoader：PluginClassLoader，每个插件一个，加载自己的 plugin.apk。

查类流程：

  1. 先查宿主 PathClassLoader。

  2. 再查已加载插件 PluginClassLoader。

  3. 如果未加载，根据类名前缀判断属于哪个插件。

  4. 触发 PluginManager.loadPlugin。

  5. 从 sCachedPluginClassLoader[pluginPackageName] 查类。

为什么需要总 ClassLoader：宿主 Manifest 预声明、Stub 还原、Context.getClassLoader、LayoutInflater、自定义 View、Bundle 反序列化都可能拿到宿主 loader。只改插件 LoadedApk.mClassLoader 不够。

3.2 LoadedApk 提供包运行环境

LoadedApk 是 APK 在当前 App 进程里的运行态对象，不是 APK 文件。它缓存在 ActivityThread.mPackages。

它提供：ClassLoader、Resources、Application、ApplicationInfo、nativeLibraryDir 等运行环境。插件 APK 没有被系统真正安装，所以框架要自己创建或改造插件 LoadedApk。

4. Resources 设计

Resources 分两条链路：先在构建期把资源 ID 做稳定，再在运行期把插件资源路径注入 Resources 系统。

资源 ID 固定：

  • 插件自己的资源：package-id.json 给每个插件登记固定 package id，miraPlugin.packageId 传给 Mira Gradle 插件。底层对应 aapt2 的 --package-id，使用 0x30~0x7e 这类 reserved id 时需要 --allow-reserved-package-id 或等价处理。

  • 插件引用宿主资源：public.xml 固定宿主公共资源 ID；没有 openMira 的场景会生成 stable ids 文件，并通过 aaptOptions.additionalParameters = ["--stable-ids", file] 传给 aapt2。

  • 防 shrink：根据 public.xml 或 plugin-stable-res-ids.txt 生成 _keep_public.xml，避免插件需要的宿主资源被 shrinkResources 删除。

  • 兜底改写：MiraResMapping + modifyRes 记录旧 ID 到资源名的映射，加载时用当前宿主 Resources.getIdentifier 找真实 ID，再改写 Manifest、res XML 和 resources.arsc。

资源路径注入：

  • 插件加载时拿到 pluginAppInfo.sourceDir。

  • NewMiraResourcesManager.addAssetPath(pluginPkg, pluginSourceDir) 更新 mSplitPathMaps。

  • ResourcesManagerExt.appendSplitAsset(allPaths) 把插件路径追加到 ResourcesManager 管理的资源实现。

  • installLoadedApk(pluginLoadedApk) 注入 host LoadedApk 的资源基础信息，构建插件 Resources，并安装 host + plugin 路径。

  • Activity 创建前后再修正 Activity、ContextImpl、Theme、AppCompat/Tint 缓存、Configuration、DisplayMetrics。

最底层会打到这些系统 API 或私有字段：AssetManager.addAssetPath、旧版本 addAssetPathNative + StringBlock、Resources.getImpl/setImpl、ResourcesManager.findOrCreateResourcesImplForKeyLocked、ResourcesKey、LoadedApk.getResources、LoadedApk.mResDir/mSplitResDirs。

5. Native so 设计

插件私有 so 解压到插件目录，由 PluginClassLoader 的 nativeLibraryPath 查找。公共 so 要单独治理，尤其是 Android 8+ linker namespace。

二、业务使用中的真实问题

1. 动态页面和系统 Manifest 语义不一致

业务把页面插件化后，容易忽略有些 Activity 属性在 ATMS/AMS 阶段就已经生效，例如 launchMode、taskAffinity、processName、screenOrientation、windowSoftInputMode、透明/全屏。StubActivity 如果和真实页面语义不一致，可能表现为任务栈、窗口、输入法、横竖屏异常。

实际处理：核心页面优先宿主 Manifest 预声明；动态页面按能力分组 Stub；插件 Manifest 做准入，不支持的系统属性不要放任业务随意使用。

2. ClassLoader 冲突和隐式依赖

风险：宿主和插件同名类、插件间同名类、三方库版本不一致、公共 API 版本不兼容、插件间隐式依赖。

治理：插件只依赖宿主稳定 API；插件间依赖显式声明；公共库版本收敛。

3. 多进程环境没有共享 LoadedApk

ActivityThread.mPackages 是 App 进程内缓存。主进程加载过插件，不代表其他进程可用。多进程插件要分别初始化和加载。

4. 资源 ID 冲突和宿主资源漂移

资源 ID 是 0xPPTTEEEE。宿主和插件独立编译时都可能使用 0x7f，导致同一个 int ID 命中错误资源。

这类问题分两种：插件自己的资源和宿主/其他插件撞 ID；插件引用宿主资源后，宿主升级导致资源 ID 漂移。处理方式见 Resources 设计里的资源 ID 固定链路。业务侧需要记住：不要只依赖 AssetManager 路径顺序，必须有 package id / stable ids / mapping 兜底。

5. Resources / Theme 缓存不一致

常见问题：Activity 拿到宿主 Resources、ContextImpl.mResources 没更新、AppCompat/Tint 缓存旧 Resources、横竖屏/夜间模式/大字体导致 Configuration 不一致。

6. Android 8+ linker namespace 和共享 so

一插件一个 PluginClassLoader 后，native 层也可能一插件一个 namespace。多个插件共享 libcommon.so 时可能：A 加载过 common，B 仍因 namespace 不可见而 dlopen failed；A/B 各自加载一份同名 so，native 全局状态拆裂；DT_NEEDED 依赖在当前 namespace 不可见。

解法：加载 so 时手动为共享 so 指定或绑定到预期 namespace。公共 so 放宿主或公共 namespace；插件 namespace 和公共 namespace 建立可见关系；插件私有 so 仍留在插件 namespace。

7. 插件升级和旧 Intent

旧启动请求可能持有旧插件 sourceDir。插件升级删除旧文件后，ActivityThread 回来创建会 ClassNotFound。还原 targetActivityInfo 时要检查 sourceDir 是否存在。

8. Intent extras 的 ClassLoader

StubIntent 经过 Binder 传输后，取 extras 前要设置正确 ClassLoader，否则可能 BadParcelableException。

9. 安全校验不能省

extras 里的 stubActivityInfo 必须和系统返回的 stubActivityInfo 一致；targetActivityInfo 必须来自插件 Manifest；插件包签名、hash、宿主版本范围必须校验。

10. 线上归因要按插件维度

上报至少包含 pluginId、pluginVersion、hostVersion、sourceDir、classLoader、resource path、stubActivity、targetActivity、native namespace、so path、dlopen error、load result。
