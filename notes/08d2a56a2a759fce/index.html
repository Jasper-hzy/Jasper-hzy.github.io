PackageManagerService 包扫描与安装流程

PackageManagerService，简称 PMS，是 Android 的包与组件索引中心。它让系统知道设备上有哪些应用、每个应用声明了哪些组件、组件能响应什么 Intent，以及包对应的 uid、签名、权限和安装状态。

一句话概括：

示意
PMS 告诉系统“有什么”，AMS/ATMS 决定这些组件“怎么运行”。

PMS 的职责范围

PMS 主要维护静态包信息和组件信息。系统里很多运行时动作都要先问 PMS：

  • Launcher 要显示桌面图标，需要查询哪些 Activity 声明了 CATEGORY_LAUNCHER。

  • AMS/ATMS 要启动 Activity，需要 PMS 返回目标 ActivityInfo。

  • 权限系统要判断调用方能力，需要 PMS 提供包、uid、签名和权限声明。

  • 安装、更新、卸载应用时，需要 PMS 更新包状态和持久化记录。

所以 PMS 不是只管理 APK 文件，而是管理“包在系统里的结构化信息”。

开机如何建立包与组件视图

开机扫描：系统有哪些包

PMS 启动时会扫描系统分区和数据分区里的包。常见目录包括：

示意
/system/app
/system/priv-app
/system_ext/app
/system_ext/priv-app
/product/app
/product/priv-app
/vendor/app
/vendor/priv-app
/odm/app
/odm/priv-app
/oem/app
/oem/priv-app
/data/app

可以先按两大类理解：

来源典型路径含义
系统分区/system、/product、/vendor、/system_ext 等系统预装应用、特权应用、厂商应用
数据分区/data/app用户安装应用、系统应用更新包

安装 APK 时，APK 本体通常进入 /data/app；/data/data/<package> 或 /data/user/0/<package> 是应用运行数据目录，不是 PMS 扫描 APK 的主要位置。

包状态：不只是扫描 APK

开机扫描不是简单遍历 APK。PMS 还会读取历史包状态，并和磁盘扫描结果合并。常见状态文件包括：

示意
/data/system/packages.xml
/data/system/packages.list
/data/system/users/<userId>/package-restrictions.xml

可以这样区分：

示意
APK / Manifest：说明包本身声明了什么
packages.xml：说明系统记录的包状态是什么

包状态里会包含：

  • appId / uid。

  • 签名信息。

  • 权限授予状态。

  • enabled / disabled 状态。

  • 安装用户和多用户状态。

  • 版本、安装路径、系统 App 更新状态。

因此 PMS 启动时做的是：

示意
扫描磁盘 APK
  -> 解析 Manifest
  -> 读取历史 package state
  -> 合并成当前系统的包数据库

Manifest 解析：系统有哪些组件

PMS 解析 APK 里的 AndroidManifest.xml 后，会建立一组组件和权限索引。

核心信息包括：

示意
PackageInfo / ApplicationInfo
ActivityInfo / ServiceInfo / ProviderInfo / Receiver 信息
IntentFilter -> 可匹配组件
权限声明和 uses-permission
签名信息
uid / appId
版本号和安装路径
enabled / disabled 状态
多用户安装状态

例如一个 Activity 声明：

xml
<activity android:name=".MainActivity">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

PMS 解析后就知道：这个 Activity 可以作为桌面入口，被 Launcher 查询并展示。

如果某个 Activity 声明 CATEGORY_HOME，PMS 就会把它纳入 HOME Activity 候选，供 AMS/ATMS 启动 Launcher 时解析。

安装流程如何更新包状态

安装不是单纯复制 APK。典型链路可以概括为：

示意
PackageInstaller
  -> PMS / PackageInstallerService
  -> 校验 APK
  -> 拷贝 APK 到 /data/app
  -> 解析 Manifest
  -> 校验签名和版本
  -> 分配或复用 uid / appId
  -> 更新 package state / packages.xml
  -> 发送 PACKAGE_ADDED / PACKAGE_REPLACED

安装完成后，新包进入 PMS 的内存索引和持久化状态。下次开机时，PMS 通过扫描 /data/app 并读取 packages.xml 恢复这个应用。

系统 App 更新也会走 PMS 状态管理：系统分区里的原始 APK 仍在，只读不可删；更新包可以放在 /data/app，PMS 根据版本、签名和状态决定当前使用哪个版本。

PMS、Installer 与 installd

安装流程里的 Installer 不是应用商店，也不是 App 侧提交安装会话使用的 PackageInstaller。它是 system_server 中访问 native installd 服务的 Java 封装。

示意
PackageInstaller
  -> 接收并组织安装请求
  -> PMS 校验包并更新包状态
  -> Installer 通过 Binder 调用 installd
  -> installd 执行文件、应用数据和 dex 相关操作

几者的职责可以这样区分：

对象职责
PackageInstaller创建和提交安装会话，把安装请求交给系统
PMS解析 APK、校验签名和版本，管理 uid、权限、组件及包状态
Installersystem_server 中调用 installd 的 Java 接口封装
installdnative daemon，执行应用目录、缓存、dexopt、profile 等底层操作

例如安装过程中需要准备应用数据时，概念链路是：

示意
PMS
  -> Installer
  -> Binder
  -> installd
  -> 创建 /data/user/<userId>/<package>
  -> 设置 uid / gid、权限和安全上下文

因此 PMS 负责“这个包在系统里是什么状态”，installd 负责“把相应的文件和数据操作真正落到磁盘”。

应用启动中的协作与结论

PMS 如何支撑 Launcher 和 App 启动

系统启动 Launcher 时：

示意
AMS/ATMS 构造 HOME Intent
  -> PMS resolveActivity
  -> 返回 Launcher ActivityInfo
  -> AMS/ATMS 启动 Launcher Activity

Launcher 展示桌面图标时：

示意
Launcher 构造 ACTION_MAIN + CATEGORY_LAUNCHER Intent
  -> PMS queryIntentActivities
  -> 返回所有桌面入口 Activity

用户点击图标启动普通 App 时：

示意
Launcher.startActivity
  -> AMS/ATMS
  -> PMS 解析目标 ActivityInfo
  -> AMS/ATMS 判断进程、Task 和生命周期
  -> 必要时请求 Zygote fork
  -> ActivityThread 创建目标 Activity

PMS 在这里负责提供静态信息：

  • 目标 Activity 是否存在。

  • 它属于哪个 package。

  • 它的 processName、uid、targetSdk 是什么。

  • exported、权限和签名状态是否满足。

AMS/ATMS 则负责运行时调度：进程、任务栈、生命周期和前后台状态。

关键结论

  1. PMS 是系统的包与组件索引中心。

  2. 开机时，PMS 扫描系统分区和 /data/app，并结合 packages.xml 恢复包状态。

  3. 安装时，APK 本体进入 /data/app；/data/data 或 /data/user/0 是应用数据目录。

  4. PMS 解析 Manifest 后建立组件、IntentFilter、权限、签名、uid 等索引。

  5. Launcher 的 HOME 入口和桌面图标列表都依赖 PMS 的 Intent 解析结果。

  6. PMS 负责“有什么”，AMS/ATMS 负责“怎么运行”。
