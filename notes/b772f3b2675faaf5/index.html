C++ 容器：对象存储、地址失效与选型

容器选择需要同时考虑元素的所有权、访问方式和句柄稳定性。本文比较 vector、map 与 unordered_map，并说明插入或扩容对对象地址和迭代器的影响。

先明确容器保存的是对象还是指针

Java 的 ArrayList<User> 通常保存 GC 引用；C++ 容器保存模板参数指定的类型本身：

C++
std::vector<User>                  // 保存对象
std::vector<std::unique_ptr<User>> // 保存独占所有权指针
std::vector<std::shared_ptr<User>> // 保存共享所有权指针
std::vector<User*>                 // 保存不管理生命周期的裸指针

按值存储具有连续内存、缓存局部性和较少独立分配等优势，代价是扩容时需要处理拷贝、移动和地址失效。

顺序容器：内存布局、插入与地址失效

vector 按值连续保存元素

C++
std::vector<User> users;

User 对象直接连续构造在 vector 的存储中。扩容时容器申请更大的连续内存，移动或复制旧元素，再释放旧内存：

示意
旧内存：[A][B][C]
新内存：[A][B][C][新元素]

发生扩容后，旧元素的指针、引用和迭代器全部失效。长期定位元素时可以保存下标并在使用时重新访问，或者根据所有权需求存储智能指针：

C++
std::vector<std::unique_ptr<User>> users;

后者扩容时移动的是 unique_ptr，其管理的堆对象通常保持原地址，但对象被删除或替换时，借用指针仍会悬空。

reserve(n) 可以减少达到预期规模前的扩容次数，但超过容量后仍可能扩容。

push_back 与 emplace_back

push_back 接收已经构造好的元素：

C++
users.push_back(User("Alice", 18));

emplace_back 接收构造参数，在新元素位置直接构造：

C++
users.emplace_back("Alice", 18);

它可能避免新元素临时对象的一次移动或拷贝，但并不总是更快：

  • 已经持有完整对象时，两者都需要拷贝或移动。

  • 简单类型通常没有明显区别。

  • 扩容时旧元素仍然需要搬迁。

关联容器：顺序、复杂度与哈希行为

项目std::mapstd::unordered_map
常见实现平衡搜索树哈希表
查询、插入、删除O(log n)平均 O(1)，最坏 O(n)
顺序按 key 排序无稳定顺序
范围查询支持不适合

map 插入通常不使已有迭代器、指针和引用失效，删除只使被删除元素相关句柄失效。

unordered_map 常使用桶数组处理哈希结果。冲突元素可能进入同一个桶的节点结构：

示意
桶 2：A -> C -> F

负载因子是：

示意
size() / bucket_count()

超过阈值时，容器申请更多桶并重新分配元素，称为 rehash。rehash 会使迭代器失效；元素指针和引用通常仍有效。单个桶冲突严重并不等于负载因子高，也不保证自动触发 rehash。

C++
users.reserve(10000);

可以降低容量增长引发的 rehash 次数，但不能改善劣质哈希函数造成的集中冲突。

选择原则：

  • 需要排序遍历、范围查询或稳定最坏复杂度：map。

  • 高频单 key 查找、无顺序要求且哈希可靠：unordered_map。

要点回顾

连续存储有利于局部性，但扩容会影响地址稳定性；树与哈希表则在排序、范围查询和复杂度上各有取舍。reserve 与 emplace_back 只能优化特定成本，不能代替对元素生命周期和访问模式的判断。
