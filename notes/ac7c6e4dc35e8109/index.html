会话系统由多个业务模块组成，各模块可能并发读写同一条会话数据，带来重复查询、频繁写入和数据一致性问题。

各模块通过同一个数据访问层读写会话，减少重复查询和写入。消息与草稿保存成功后，才向页面确认。

示例

两个模块同时查询同一会话，只查一次数据库，结果分别返回。连续收到多条消息时，消息全部保存，尚未执行的列表写入可以合并。

1. 业务场景与数据访问问题

会话列表根据新消息更新内容、未读数和排列顺序。多个模块独立查询同一条会话记录，会产生重复访问。

会话摘要

指列表展示所需的数据，如最后一条消息、未读数和排序时间。摘要可以重新计算，消息和草稿必须可靠保存。

连续收到消息还会多次修改摘要。优化时需要区分查询、摘要和原始记录：

数据或操作处理要求
多个模块读取同一份会话记录可以共享一次查询结果
同一会话连续产生多个待写摘要可以只保存最新摘要
每条消息、草稿、已读位置和删除记录按业务操作可靠保存，不能随摘要合并而丢弃
查询或摘要计算期间发生新更新拒绝用旧结果覆盖当前状态

未发送消息和草稿可能只有本地副本，因此不能等缓存批量写入时才保存，也不能依赖服务端重新同步来恢复。

2. 方案对比与整体架构

2.1 三种读写方案对比

对比维度先写缓存，定时保存各模块直接读写数据库统一读写，分类保存
消息与草稿保存写入数据库前可能丢失提交后确认保存提交后确认保存
相同并发查询有缓存时复用，未命中时仍可能重复各模块分别查询有缓存则复用，否则共享一次查询
摘要写入次数可合并尚未执行的写入每次更新分别写入同一会话只保留最新待写摘要
保存确认耗时需等待定时保存完成等待本次事务完成等待事务完成，消息与草稿优先
并发一致性需处理缓存与数据库的先后关系数据库处理事务，页面仍需防止旧回调覆盖新值统一检查数据版本和回调归属
进程退出后恢复只能恢复已写入数据库的内容从已提交记录恢复恢复原始记录，重建摘要，继续待发任务
实现与维护需要定时保存和失败重试初始实现简单，访问逻辑分散集中维护缓存、任务队列与版本，复杂度较高

选择第三种方案：集中处理重复访问，分别安排消息保存和摘要更新。代价是增加任务调度与版本管理。

保存确认

页面回显只表示内容已显示，数据库提交成功才表示保存完成。三种方案都需要处理发送重试和草稿保护。

2.2 整体架构

业务模块通过数据访问层访问本地数据库。读取请求共用缓存和查询任务；消息、草稿优先保存；摘要按会话合并写入。发送模块只处理已保存的待发任务。

图中边界

数据库事务保证一组修改全部成功或全部撤销；数据访问层负责查询合并、写入调度和版本检查。网络请求在事务外执行，发送前先保存消息与待发任务。发送结果和同步消息也通过保存路径入库，再更新缓存和页面。

3. 并发查询合并与缓存更新

3.1 多个模块共享查询结果

数据访问层按“账号 ID + 会话 ID”查找缓存。缓存有效则直接返回；否则发起一次查询，其余相同请求等待结果。

查询结束后，每个等待者分别收到结果或错误。

合并条件

查询范围和返回内容必须相同。不同消息页、不同筛选条件不能只按会话 ID 合并。

3.2 旧查询结果的回填校验

查询返回时，先检查会话是否已更新。若已有新数据，就丢弃旧结果。

会话更新或删除时递增本地版本。查询开始时记录版本，返回时比较版本。

并发处理

缓存检查、查询登记和版本记录在同一锁内完成；版本比较与缓存更新也需持锁，避免检查后又插入新更新。图中的查询始于 v10，返回时已是 v11，因此不能覆盖缓存。

示意
读取会话（账号 ID，会话 ID）：
  在锁内检查缓存：
    缓存有效 → 返回当前快照
    已有相同查询 → 登记等待者
    否则 → 记录登录批次和本地版本，登记查询任务
  仅新登记的查询任务在锁外访问数据库，其余请求等待结果
  查询返回后，在锁内检查：
    登录批次已失效 → 结束旧请求
    版本相同且未删除 → 更新缓存，准备返回结果
    已有更新或删除 → 准备返回当前状态，丢弃旧结果
    无有效状态或查询失败 → 限次重试或返回错误
    只移除本次查询的任务登记
  在锁外通知等待者

“登录批次”是每次登录生成的标识，用来区分同一账号退出后重新登录的两次会话。旧请求不能更新新登录的页面。删除标记和本地版本至少保留到旧查询结束，不能随缓存一起清除，否则旧结果可能恢复已删除的会话。

页面订阅会话变化时，也要在同一锁内完成订阅登记和当前快照读取，再按版本顺序通知后续更新，避免首次显示与订阅之间漏掉消息。服务端消息乱序仍按业务序号处理，本地版本仅用于判断本地异步结果是否过期。

4. 会话摘要的写入合并

4.1 只合并尚未执行的摘要

连续消息会改变最后一条消息、未读数和排序时间。数据访问层按会话保留最新待写摘要，新的摘要替换队列中尚未执行的旧版本，消息记录仍完整保存。

只替换尚未开始写入的摘要。批次结束时，只移除已提交的版本，保留执行期间新增的摘要。

合并示例

收到 A、B、C 三条消息，三条消息全部保存。若对应摘要都未开始写入，只提交 C 对应的最新摘要，未读数仍计入三条消息；若 A 已开始写入，只能合并后续 B、C 的摘要。

4.2 摘要计算期间的数据更新

原始记录更新时，在同一事务中递增会话的数据修订号，标记摘要需要重建。摘要写入前检查修订号；数据已变，则重新计算。

计算时，从同一数据库快照读取记录和修订号；提交时，在事务中重新校验。摘要同时保存计算依据的修订号，重启后据此判断是否过期。摘要更新不修改原始消息或草稿。

两类版本

本地版本用于检查旧查询能否更新缓存。数据库修订号表示原始记录已更新到哪一版，用于检查摘要是否过期。

4.3 批次大小与保存优先级

合并写入减少同一会话的摘要更新次数；批量提交则把多个待写操作放进一个事务，减少事务次数。两者可以配合，但批次过大会延迟消息与草稿保存。

调度器限制每批摘要数量，优先处理正在等待保存确认的消息和草稿。待发任务保留在数据库，内存只领取有限批次。容量不足时拒绝新操作并保留输入，已接受的任务不能被丢弃。

5. 消息保存、发送与异常恢复

5.1 消息与待发任务同时保存

消息保存成功后，进程可能在网络请求发出前退出。因此，数据库还需保存一条待发任务，记录这条消息尚未发送。消息与任务在同一事务中提交，重启后就能找到需要继续发送的内容。

网络请求在本地提交成功后执行，防止服务端已经接收、本地却没有记录。提交成功只表示内容已在本地保存；“已发送”还需要服务端确认，并完成本地状态提交。

示意
提交消息（账号、消息标识、内容、草稿版本）：
  在后台事务中：
    相同账号与消息标识已存在 → 校验内容一致，复用结果
    否则 → 保存消息和待发任务
    草稿版本仍相同 → 写入更高版本的清空标记
    递增会话数据修订号，标记摘要需要重建
  提交成功 → 更新或失效缓存，返回“已接受”，唤醒发送模块
  提交失败 → 保留输入，返回失败，不发送网络请求

清空编辑器前也要校验草稿版本，避免删掉提交期间的新输入。附件先保存到应用管理的稳定路径，再在事务中登记引用；清理文件前需检查是否仍被数据库记录引用。提交后即使未能唤醒发送模块，重启扫描待发任务也能恢复发送。

5.2 超时重试与重复消息处理

网络超时不能证明服务端没有收到消息。重试必须沿用原消息标识和内容，服务端按“账号 + 消息标识”去重，让多次请求对应同一条消息。不同内容不能复用标识，服务端的去重保留时间需覆盖重试周期；超过期限后，先查询处理结果。

发送模块只领取当前账号的已提交任务。领取时，在短事务中登记本次发送编号和占用期限，再执行网络请求；到期仍未完成的任务可重新领取。有会话内顺序要求时，按本地序号等待前序任务完成。

结果本地处理
服务端确认成功在同一事务中关联服务端消息 ID、将消息标为已发送、将任务标为已确认，提交后更新页面
断网或超时保存重试次数和下次执行时间，逐步延长间隔后重试
自动重试耗尽暂停自动发送，保留消息与任务，支持手动重试
旧发送尝试返回失败校验发送编号，不覆盖新尝试或已发送状态

旧尝试返回有效成功确认时，仍可完成同一条消息；服务端同步到的消息也按原消息标识归并。本地确认事务失败时保留待发记录，重试取得同一结果后再次提交确认。

5.3 草稿保存与版本控制

草稿连续编辑时，较早的保存任务可能晚于新任务完成。数据访问层为每次编辑串行分配递增版本，立即调度文本与附件引用的保存，数据库只接受更新版本。清空也要保存一个更高版本的删除标记，防止旧任务恢复已清空内容。

保存过程页面与数据行为
编辑到版本 41，事务未完成即时显示输入，标记“保存中”
版本 41 提交成功，当前仍为 41显示“已保存”
版本 41 返回时已编辑到 42保留新输入，等待版本 42 的保存结果
磁盘满或写入失败保留输入并提示失败
保存期间进程退出重启后读取最新已提交版本，版本号继续递增

保存由编辑触发，不依赖页面退出或后台切换。多个保存操作可以共用短事务，但“已保存”必须在相应事务提交后确认。

5.4 进程重启与账号切换

进程退出会丢失内存状态，恢复需以数据库已提交记录为准。图 6 按发送中断的位置区分恢复操作。

启动时根据数据库修订号重建过期摘要；账号鉴权有效后领取待发任务，并从已保存的同步位置继续拉取消息。每批服务端消息的保存与同步位置更新必须在同一事务提交，避免重启后跳过尚未保存的数据。

全量同步仅替换服务端管理的字段，保留本地草稿、待发消息与操作。普通退出登录保留这些记录，暂停任务领取并解除页面订阅。在途请求仍可能到达服务端，其结果只归属原账号，旧登录回调不得更新当前页面；再次登录后从数据库恢复任务。

6. 验证方法与预期效果

用相同消息负载比较优化前后的数据库访问，并在图 6 的各个中断点终止进程、重新打开数据库，检查保存和恢复行为。

起初的问题验证方法与预期结果
相同查询重复执行同时请求同一会话，对比业务请求数与实际查询数，确认有效缓存或进行中的查询被共享
摘要中间版本频繁写入连续接收消息，确认原始记录完整，尚未执行的摘要只提交最新版本，未读数和排序正确
旧结果覆盖新数据延迟返回查询与草稿保存回调，确认数据不倒退、已删除内容不恢复
已接受的内容丢失提交后终止进程，重启后能恢复消息、草稿和待发任务
超时后重复发送丢弃确认响应，再用原标识重试，服务端仍返回同一条消息

并发验证还需覆盖订阅登记与更新同时发生、账号切换时返回旧请求，以及全量同步时存在本地未发送内容。异常验证覆盖磁盘满、确认事务失败和服务端去重期限到期。

性能记录包括查询次数、摘要写入次数、事务次数，以及消息和草稿提交延迟、待发积压与列表更新延迟。事务减少但保存变慢时，应检查摘要批次是否长期占用写队列，调整批次大小或优先级后复测。

方案的预期效果是减少相同查询和摘要中间版本的写入，同时保持消息与草稿可恢复、列表状态不倒退。验收需要同时满足这两组条件。
