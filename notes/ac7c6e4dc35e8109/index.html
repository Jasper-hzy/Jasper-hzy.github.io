IM 会话缓存与数据访问调度设计

1. 文档边界

这份文档用于复盘 IM 会话存储重构中的缓存与读写调度设计，重点回答两个问题：

  1. 如何降低高频并发读写 ObjectBox 带来的事务竞争和锁等待。

  2. 如何通过缓存、请求合并和批量持久化优化会话读写速度。

本文根据当时的实现思路和当前复盘整理，未对原始工程源码和性能数据进行重新校验。因此，容器、版本校验和失败处理部分记录的是可防守的设计语义；简历不写未验证的耗时或收益数字。

2. 原有问题

会话列表、未读数、最后一条消息摘要等数据会被多个业务模块频繁读取和更新。如果每个 CRUD 都独立提交线程池，会出现：

  • 同一会话被重复查询，增加数据库访问次数。

  • 多个写线程同时提交，底层仍需要争用写事务或锁。

  • 中间状态被逐次持久化，事务次数高于业务实际需求。

  • 频繁的任务提交、阻塞、唤醒和线程切换增加调度开销。

  • 数据库异步读取可能在缓存更新之后返回旧数据，造成状态回退。

本设计的优化目标是收敛数据库访问，不是让业务为了强一致性等待整个写队列。

3. 整体架构

Mermaid · 流程图源码
flowchart TD
    B["会话列表 / 业务模块"] --> R["SessionRepository"]
    R --> C["会话内存缓存<br/>UID + SessionID / Snapshot / Version"]
    C -->|"命中：返回快照"| B
    C -->|"未命中"| RP["读管道<br/>去重 / 合并 / 批量查询"]
    RP --> DB["ObjectBox"]
    DB -->|"版本校验后回填"| C
    R -->|"写入：先更新缓存"| C
    C --> N["按 Key 通知观察者"]
    C --> WP["单写管道<br/>状态合并 / 批量事务"]
    WP --> DB
    DB -->|"失败：版本校验 / 重试 / 失效"| C

服务端是可同步会话事实的最终来源，ObjectBox 保存本地持久化投影，内存缓存则保存进程内最新会话快照。

4. 缓存数据结构

内存会话可按以下语义组织：

java
record SessionKey(long uid, String conversationId) {}

record CacheEntry<T>(
        T snapshot,
        long version,
        PersistState persistState
) {}

ConcurrentHashMap<SessionKey, CacheEntry<SessionSnapshot>> sessionCache;

  • UID + conversationId 作为组合 Key，使不同账号和会话在缓存、待写任务和订阅关系中保持隔离。

  • ConcurrentHashMap 保证并发容器访问，使用 compute() 收敛同 Key 的读-改-写。它不是“每个 Key 一把锁”；JDK 8 以后主要使用 CAS 和桶粒度并发控制。

  • SessionSnapshot 对外不可变，业务不能直接修改对象，必须通过 Repository 更新，以便统一增加版本、触发持久化和发送通知。

  • 对 compute() 的回调只执行快速内存计算，不在其中访问数据库、请求网络或通知业务。

5. 读管道

5.1 缓存优先

text
读取会话
→ 命中内存缓存
→ 直接返回当前不可变快照

读取接口返回的是调用时刻的快照。读取后发生新写入时，已返回的快照不需要追溯修改，由按 Key 订阅通知后续变化。

5.2 缓存未命中合并

同一 Key 的并发查询可共享一次数据库任务：

text
get(A) + get(A) + get(A)
→ 一次 ObjectBox 查询
→ 将结果分发给所有等待者

短时间内多个 Key 的读取也可聚合为批量查询，但需要限制聚合窗口，避免为了批处理反而增加首次读取延迟。

5.3 数据库回填校验

查询发起后，缓存可能已被写管道更新：

text
发起查询 A(v10)
→ 缓存更新为 B(v11)
→ 数据库返回 A(v10)
→ 禁止用 A 覆盖 B

数据库结果仅用于回填空缓存，或在版本校验通过后回填；旧结果不得造成缓存和 UI 状态回退。

6. 写管道

6.1 先更新缓存

text
业务写入
→ 生成新快照
→ 原子更新缓存并增加版本
→ 通知该 Key 的观察者
→ 提交数据库写任务

因为后续读取优先访问缓存，所以正常路径不需要等待同 Key 的数据库写任务。读写之间保留的是同 Key 的状态时序，不是读管道对整个写队列的结构依赖。

6.2 单写队列

数据准备可以并行，只将最终的数据库写入临界区收敛到单写队列。队列的价值是主动安排底层本就需要协调的写事务，减少多线程争锁、阻塞和唤醒。

队列中不应执行网络请求、复杂计算或长时间回调，否则会形成队头阻塞。

6.3 写任务合并

合并必须根据业务语义进行，不能笼统地将所有读写任务合并。

数据类型合并策略示例
最新状态只保留同 Key 的最新快照未读数 1 -> 2 -> 3 只持久化 3
可累加状态按明确规则累加计数增量在合并后一次提交
事件型数据不覆盖，仅批量提交消息 M1/M2/M3 全部保留，同一事务写入
删除或撤回保留顺序和幂等语义不能被后续普通更新无条件覆盖

7. 按 Key 订阅会话更新

一次读取只能返回当前时刻的快照。写入发生后，缓存层按 Key 通知对应观察者：

text
读取 A(v10)
→ 业务写入 B(v11)
→ 缓存更新为 B(v11)
→ 通知观察者
→ UI 使用 B(v11) 刷新

“读取当前值”和“注册监听”应形成一个完整语义，避免两步之间发生更新而丢失通知。可由 observe(key, listener) 在注册后立即回放当前最新快照，或注册后再次检查版本并补发。

通知应满足：

  • 同 Key 的版本顺序不倒退。

  • 在缓存内部锁或 compute() 之外执行业务回调。

  • 观察者按页面或账号生命周期解除订阅，避免泄漏。

  • 账号切换后，旧 UID 任务可继续落到旧数据命名空间，但不能通知新账号页面。

8. 持久化失败与恢复

缓存写入后会触发一次异步数据库同步。缓存项可区分：

text
DIRTY -> PERSISTING -> CLEAN
                    -> FAILED / INVALID

  • 持久化失败后进行有上限的重试，并保存下次重试时间，不让单个异常任务永久阻塞写队列。

  • 失败回调必须校验任务版本。v11 写入失败时，如果缓存已经到达 v12，不能清除或失效 v12。

  • 状态型数据重试时可持久化当前最新快照，不必重复写入已被替代的中间版本。

  • 重试耗尽后，对应版本可标记为失败或无效，再由服务端增量同步修复。

会话缓存保存的是服务端可重建投影，因此允许 App 被终止时丢失尚未持久化的最近更新。App 重启后按上次成功位点拉取增量会话记录并幂等更新本地数据。

恢复位点不能先于数据落盘：如果同步游标或时间位点已经推进，但对应会话数据未持久化就被终止，重启后可能永久跳过该部分数据。因此，最好将会话数据和新位点放在同一事务提交，或仅在数据写入成功后推进位点。只有时间戳时，需使用重叠窗口和服务端唯一 ID 幂等去重，避免边界漏数。

9. 为什么不自己用 mmap 保证可靠性

mmap 只是文件映射机制，不自动提供事务原子性和掉电持久性。如果要自己保证可靠落盘，还需要实现刷盘时序、提交标记、校验、部分写恢复和多项修改的原子性，本质上是再实现一套 WAL 或数据库。

对于本设计中可从服务端恢复的会话投影，无需额外引入 mmap 文件；继续使用 ObjectBox 事务保证已进入数据库修改的原子性，未进入事务的内存任务则依赖重启后增量同步恢复。

10. 性能收益来源

优化点减少的开销
缓存优先读取减少热点会话的 ObjectBox 查询
同 Key 读取合并减少缓存冷启或失效时的重复查询
写队列串行化减少并发写事务的锁竞争、阻塞和唤醒
同 Key 状态合并减少中间状态的落盘次数
批量事务减少事务启动和提交次数
统一读写调度减少每次 CRUD 独立创建任务带来的线程调度和上下文切换
按 Key 通知业务可直接消费最新内存快照，无需为刷新 UI 再查一次数据库

不将上述优化笼统表述为“降低 iowait”。在没有系统级指标前，只能直接宣称减少数据库访问、事务次数、锁等待和线程调度开销。

11. 风险和边界

风险处理原则
单写队列队头阻塞仅串行化短数据库临界区，限制单批任务量，不在队列中执行网络或复杂计算
队列长期积压记录队列长度和最长等待时间，对可覆盖状态执行合并和背压
读取旧值后发生写入读取是时点快照，写后通过按 Key 订阅发送新版本
旧查询晚于新写入返回回填前校验版本，禁止状态倒退
读取和注册监听之间丢更新使用订阅并回放最新快照的统一接口
旧写任务失败后清除新缓存失败和重试操作必须校验任务版本
账号切换串数据任务创建时固化 UID，所有容器、查询和订阅使用组合 Key
进程退出丢失待写投影仅对服务端可重建会话数据允许丢失，通过持久化位点增量恢复
增量位点提前推进会话数据与位点同事务提交，或数据落盘成功后再推进

12. 验证方法

要证明方案真正改善了原始问题，应在相同业务负载下对比：

  • 每秒会话读请求数与实际 ObjectBox 查询数，得到缓存命中率和读合并率。

  • 业务写请求数与数据库实际写入数，得到状态合并率。

  • 数据库事务次数、单事务耗时以及 P50/P95/P99 写入延迟。

  • 写队列平均长度、最大长度和最长等待时间。

  • 数据库锁等待、阻塞线程数、线程唤醒和上下文切换。

  • 会话列表首次加载、刷新及高频消息到达场景的端到端延迟。

  • 故障测试：查询返回乱序、写入失败、重试期间出现新版本、账号切换、进程被终止后增量恢复。
