ATMS 和 AMS 都运行在 system_server 中，但管理对象不同：

示意
ATMS：管理 Activity 和 Task
AMS：管理应用进程以及 Service、Broadcast、Provider 等运行态

一次 Activity 冷启动以 ATMS 为主线。ATMS 会先判断目标进程是否已经完成 attach，并向 system_server 提供了可用的 ApplicationThread Binder；如果还不能通知 App 主线程创建 Activity，就请求 AMS 确保目标进程可用。AMS 再根据真实进程状态决定复用正在启动的进程，还是请求 Zygote fork 新进程。

职责边界：任务管理与进程管理

为什么同时有 ATMS 和 AMS

早期 Android 的 Activity、Task 和进程调度大量集中在 ActivityManagerService 中。随着窗口和多显示等能力变复杂，Activity 与 Task 相关逻辑逐步拆到 ActivityTaskManagerService。

因此旧版本资料经常把 Activity 启动统称为 AMS 流程；在较新的 Android 中，需要区分：

示意
Activity / Task 调度 -> ATMS
进程和其他组件运行态 -> AMS

ATMS 的主要作用

ATMS 全称是 ActivityTaskManagerService，主要管理 Activity 和 Task。

1. Activity 启动

ATMS 接收 App 发起的 startActivity 请求，然后处理：

  • Intent 对应哪个目标 Activity。

  • 调用方是否允许启动目标组件。

  • 目标 Activity 是否已经存在。

  • 当前顶部 Activity 是否需要 pause。

  • 新 Activity 应该何时创建和 resume。

ATMS 不直接解析 APK，而是使用 PMS 提供的 ActivityInfo、ApplicationInfo 等静态包信息。

2. Task 管理

ATMS 根据以下信息决定 Activity 放入哪个 Task：

  • launchMode。

  • Intent flags，例如 NEW_TASK、CLEAR_TOP。

  • taskAffinity。

  • 当前已有 Task 和 Activity 状态。

常见管理对象包括：

示意
ActivityRecord：system_server 中一个 Activity 的运行记录
Task：一组按照返回关系组织的 Activity
RootWindowContainer：Activity 和 Task 层级的根管理对象

3. Activity 生命周期调度

ATMS 维护的不是 App 中真实的 Activity 对象，而是 ActivityRecord。它根据系统全局状态决定：

示意
哪个 Activity 启动
哪个 Activity pause
哪个 Activity resume
哪个 Activity stop 或 destroy

真正的生命周期方法仍然在 App 主线程中执行。ATMS 通过 Binder 事务通知 App 进程完成相应操作。

AMS 的主要作用

AMS 全称是 ActivityManagerService。它的核心职责是管理应用进程和 Android 组件的运行状态。

1. 应用进程管理

AMS 负责：

  • 判断目标进程是否已经存在。

  • 目标进程不存在时请求 Zygote fork。

  • 保存 pid、uid、进程名和组件状态。

  • 维护进程优先级和 OOM 调整值。

  • 处理进程死亡以及组件后续恢复。

主要记录对象是：

示意
ProcessRecord：system_server 中一个 App 进程的运行记录

进程启动链路可以简化为：

示意
AMS
  -> ProcessList
  -> ZygoteProcess
  -> Zygote fork
  -> ActivityThread.main

2. App 进程 attach

Zygote fork 后，子分支已经是目标 App 进程。App 主线程进入：

示意
ActivityThread.main
  -> new ActivityThread
  -> ActivityThread.attach
  -> AMS.attachApplication

App 会把 ApplicationThread Binder 对象交给 AMS。之后 system_server 可以通过这个 Binder 通道通知 App：

  • 创建 Application。

  • 调度 Activity 生命周期。

  • 创建 Service。

  • 分发 Receiver。

  • 处理配置和内存状态变化。

ActivityThread 不是 Java Thread，而是 App 主线程的组件和事务管理对象。

3. Service、Broadcast、Provider

除了进程管理，AMS 还负责这些组件的运行态调度：

示意
Service：启动、绑定、前台服务和生命周期
Broadcast：广播分发、接收顺序和超时
Provider：发布、查找和进程依赖

PMS 保存这些组件在 Manifest 中的静态声明；AMS 负责它们运行时如何启动、连接和结束。

4. 进程优先级

AMS 会根据进程当前承载的组件和用户可感知程度计算进程状态，例如：

示意
前台进程
可见进程
服务进程
缓存进程

随后调整 oom_adj 等状态，内存不足时由 LMKD 和内核优先回收重要性较低的进程。Activity 退出后进程不一定立即结束，保留缓存进程可以加快下次启动。

一次启动中的跨进程协作

ApplicationThread：system_server 如何反向调用 App

system_server 和普通 App 都由 Zygote fork，但 fork 后是彼此独立的进程。App 可以通过 IActivityManager、IActivityTaskManager 等 Binder Proxy 调用系统服务；系统服务要反向调度 App，则需要 App 主动提供一个 Binder 回调接口。

App 进程启动后会创建：

Java
final ApplicationThread mAppThread = new ApplicationThread();

ApplicationThread 继承 IApplicationThread.Stub。它不是 Java 线程，而是 App 进程中的 Binder Stub：

示意
ActivityThread.attach
  -> AMS.attachApplication(mAppThread)
  -> App 把 ApplicationThread Binder 交给 AMS
  -> AMS 保存到 ProcessRecord.thread

跨进程后，两端看到的对象不同：

示意
App 进程：ApplicationThread Stub
        ↓ Binder driver
system_server：IApplicationThread Proxy

ATMS/AMS 后续可以通过这个 Proxy 通知 App：

示意
system_server
  -> IApplicationThread.scheduleTransaction
  -> Binder driver
  -> App 的 ApplicationThread Stub
  -> ActivityThread 主线程 Handler
  -> TransactionExecutor
  -> 执行 Activity 生命周期

Binder 事务到达 App 时可能先由 Binder 线程接收，ApplicationThread 会把 Activity 事务投递到主线程 Looper，所以 Activity.onCreate()、onResume() 等生命周期仍然在 App 主线程执行。

两条调用方向可以对照理解：

示意
App 请求 system_server：
Activity -> IActivityTaskManager Proxy -> Binder -> ATMS

system_server 通知 App：
ATMS/AMS -> IApplicationThread Proxy -> Binder
         -> ApplicationThread Stub -> ActivityThread 主线程

这也是系统服务实现跨进程回调的通用方式：App 注册一个 Binder Callback Stub，系统服务保存对应的远程 Binder 引用，事件发生后再通过它回调 App。例如广播分发使用 IIntentReceiver，bindService 的连接结果使用 IServiceConnection。

ATMS 和 AMS 怎么协作

Activity 冷启动的关键交接关系是：

示意
App 调用 startActivity
  -> ATMS 接收启动请求
  -> ATMS 使用 PMS 信息确定目标 Activity
  -> ATMS 处理 Task 和 Activity 状态
  -> ATMS 检查目标进程是否已 attach，并提供 ApplicationThread Binder
  -> 当前不能直接调度时，请求 AMS 确保进程可用
  -> AMS 检查 ProcessRecord、pid 和启动中状态
      -> 进程正在启动：复用并等待 attach
      -> 确实不存在：请求 Zygote fork
  -> App 进程 ActivityThread.attach
  -> AMS 记录 ApplicationThread
  -> 创建 Application
  -> ATMS 通知 App 创建 Activity

这里是两阶段判断，不是 ATMS 取代 AMS 管理进程：

示意
ATMS 判断：
当前能否通过 ApplicationThread Binder 通知 App 主线程创建 Activity

AMS 判断：
进程是否已存在、正在启动、已经死亡，最终是否需要 Zygote fork

ATMS 之所以需要先看一次，是因为 Activity 对象要在目标 App 的主线程中创建。目标进程完成 attach 后，ATMS 才能通过 ApplicationThread Binder 把 LaunchActivityItem 等事务发送给 App。ATMS 关心的是“现在能不能通知 App 创建 Activity”，不是完整的进程生命周期。

如果进程已经 attach，ATMS 可以直接下发 Activity 事务：

示意
ATMS 找到现有进程
  -> 跳过 AMS 请求 Zygote fork
  -> 直接通知 App 调度目标 Activity

因此可以记成：

示意
ATMS 做 Activity 启动决策
AMS 对进程状态做权威检查，并保证承载 Activity 的进程可用

Application 与 Activity 的创建顺序

冷启动时不是 fork 后立刻创建 Activity，而是：

示意
Zygote fork
  -> ActivityThread.main
  -> ActivityThread.attach
  -> AMS.attachApplication
  -> bindApplication
  -> Application.attachBaseContext
  -> 安装 ContentProvider
  -> Application.onCreate
  -> 创建 Activity
  -> Activity.onCreate

这一顺序能解释两个常见问题：

  1. Application 每个进程只创建一次，Activity 可以创建多次。

  2. 通过 ContentProvider 自动初始化的三方库可能早于 Application.onCreate() 执行。

性能分析需要继续拆分进程初始化、组件创建和首帧显示的耗时，避免仅用总启动耗时判断瓶颈。

不同启动状态下的链路差异

示意
冷启动：
进程不存在，需要 Zygote fork、attach、创建 Application 和 Activity

温启动：
进程存在，但 Activity 需要重新创建，不再创建 Application

热启动：
进程和 Activity 都存在，主要进行 Task 切换和生命周期恢复

进程是否存在由 AMS 管理；Activity 和 Task 是否存在由 ATMS 管理，所以判断冷、温、热启动时需要同时看两边状态。
