资源管理需要同时回答三个问题：资源由谁持有、何时释放，以及对象复制或移动时如何转移这些责任。以下从对象生命周期进入，再讨论 RAII、移动与多态销毁。

对象构造、资源分配与销毁

先明确对象与资源的生命周期

C++ 的引用和裸指针只是借用关系，不延长普通对象的生命周期：

cpp
const User* saved = nullptr;

void save(const User* user) {
    saved = user;
}

void init() {
    User user;
    save(&user);
} // user 析构，saved 悬空

悬空引用或指针指向已经销毁的对象，继续访问属于未定义行为。它与内存泄漏不同：泄漏是资源仍未释放但失去了可靠的释放路径。

malloc/free 与 new/delete

malloc/free 只管理原始内存，new/delete 同时负责对象生命周期：

行为malloc/freenew/delete
构造和析构不调用调用
返回类型void*对应类型指针
默认失败行为返回 nullptr抛出 std::bad_alloc
数组配对手动计算字节new[] 配对 delete[]

不要混用分配与释放方式。现代业务代码优先使用标准容器和智能指针。

用 RAII 与 Rule of Zero 管理资源

RAII 管理所有成对资源

RAII 将资源的获取与局部对象构造绑定，将释放与析构绑定。正常返回、中途 return 和异常栈展开都会执行局部对象析构。

cpp
using FilePtr = std::unique_ptr<FILE, decltype(&fclose)>;

void writeLog() {
    FilePtr file(fopen("log.txt", "w"), &fclose);
    if (!file) {
        return;
    }

    writeHeader(file.get());
    if (!writeContent(file.get())) {
        return;
    }
}

RAII 不只用于内存，还适用于文件、锁、socket、JNI 引用和事务等资源：

cpp
void update() {
    std::lock_guard<std::mutex> lock(mutex);
    modify();
} // 自动解锁

Rule of Zero 优先于手动管理

持有裸堆内存的类如果使用编译器生成的拷贝操作，可能发生浅拷贝和重复释放：

cpp
class Buffer {
public:
    explicit Buffer(std::size_t size)
        : data_(new char[size]) {}

    ~Buffer() {
        delete[] data_;
    }

private:
    char* data_;
};

Buffer first(100);
Buffer second = first; // 两个 data_ 指向同一块内存

需要手动管理资源时，应考虑析构、拷贝构造、拷贝赋值、移动构造和移动赋值，即 Rule of Five。更好的选择是让标准库成员管理资源：

cpp
class Buffer {
public:
    explicit Buffer(std::size_t size)
        : data_(size) {}

private:
    std::vector<char> data_;
};

编译器生成的 Buffer 拷贝和移动操作会继续调用 vector 对应的安全操作，这就是 Rule of Zero。

移动语义与异常保证

std::move 只改变值类别

cpp
Buffer second = first;            // 拷贝构造
Buffer third = std::move(first);  // 有可用移动构造时调用移动构造

std::move 本身不移动资源，只将表达式转换为右值类别。移动后的对象仍然有效，可以析构和重新赋值，但其具体内容通常处于未指定状态。

std::move 不会移除 const：

cpp
const Buffer source(100);
Buffer target = std::move(source); // 通常调用拷贝构造

此时表达式类型是 const Buffer&&，不能绑定到需要修改源对象的 Buffer&&。

noexcept 让容器敢于移动

cpp
Buffer(Buffer&& other) noexcept;

noexcept 承诺异常不会逃出函数；如果异常仍逃出，程序调用 std::terminate()。只有移动过程确实不抛异常时才能作此承诺。

vector 扩容时通常使用接近 std::move_if_noexcept 的策略：

text
移动构造不抛异常             → 移动旧元素
移动可能抛异常且类型可复制   → 优先复制旧元素
类型不可复制                 → 只能尝试移动

这样可以在搬迁失败时尽量保持原容器不变。

多态销毁的边界

cpp
class Base {
public:
    virtual ~Base() = default;
};

如果通过 Base* 删除实际的 Derived 对象，而 Base 析构不是虚函数，行为未定义。正确析构顺序是先 Derived，再 Base。

不参与继承或声明为 final 的类不需要虚析构。基类设计通常选择：

  • 允许通过基类指针删除：public virtual 析构。

  • 不允许通过基类指针删除：protected 非虚析构。

构造和析构期间，虚函数只派发到当前正在构造或析构的类。基类构造时派生部分尚未完成，基类析构时派生部分已经销毁。

要点回顾

优先让类型和成员表达所有权；用 RAII 保证成对释放，用 Rule of Zero 减少手写特殊成员函数。移动语义不等于资源自动转移，多态销毁也需要单独检查析构约定。
