SystemServer 启动服务流程

SystemServer 是 system_server 进程里的 Java 入口类，负责把 Android Framework 的系统服务按依赖顺序启动起来。它本身不是具体业务能力的实现，真正的系统逻辑分散在 AMS、PMS、WMS、Power、Display、Input 等服务里。

一、整体主线

text
Zygote fork system_server
  -> SystemServer.main()
  -> SystemServer.run()
  -> 创建 SystemContext
  -> 创建 SystemServiceManager
  -> startBootstrapServices()
  -> startCoreServices()
  -> startOtherServices()
  -> 各阶段穿插 startBootPhase(...)
  -> AMS.systemReady(...)
  -> 启动 SystemUI / Launcher / 第三方 App

这条主线解决的是：system_server 进程启动后，Framework 服务体系如何从无到有地建立起来。

不同 Android 版本会增删服务或调整局部位置。这里重点理解 bootstrap、core、other、ready 四个阶段，不把服务列表当作需要背诵的严格逐行顺序。

二、SystemContext 和 SystemServiceManager

SystemContext 是 system_server 内部服务使用的系统级 Context，后续服务访问资源、包信息、配置、ContentResolver 等能力时会依赖它。

SystemServiceManager 是服务生命周期管理器，负责启动继承 SystemService 的服务，并在系统启动阶段变化时通知它们。

text
SystemServiceManager.startService(...)
  -> 创建服务对象
  -> 调用 service.onStart()
  -> 后续 boot phase 到来时调用 service.onBootPhase(...)

它和 servicemanager 不是一个东西：

名称位置职责
SystemServiceManagersystem_server 进程内 Java 对象管理 Framework Service 生命周期
servicemanagerinit 启动的 native 进程保存 Binder 服务名到 Binder 引用的映射
ServiceManagerJava 工具类通过 Binder 调用 native servicemanager

三、startBootstrapServices：启动系统底座

startBootstrapServices() 启动后续服务依赖的基础能力，典型包括：

text
ActivityTaskManagerService / ActivityManagerService
PowerManagerService / DisplayManagerService
PackageManagerService / UserManagerService

这一阶段可以理解为：先把后续服务普遍依赖的进程、包、用户、电源和显示等底座建立起来。具体服务之间仍会按照源码依赖穿插初始化。

比如：

  • PMS 提供已安装包、Manifest、组件和权限基础信息。

  • AMS/ATMS 提供进程、Activity、Task、Service、Broadcast 的调度能力。

  • Power 和 Display 提供启动期间的电源与显示基础状态。

如果这些底座没起来，后续服务就无法安全地查包、查权限、启动组件或接入显示。

四、startCoreServices：启动核心运行态服务

startCoreServices() 启动少量系统运行态核心服务。它们很重要，但通常不是最底层的启动依赖。

常见服务包括：

text
BatteryService
UsageStatsService
WebViewUpdateService
CachedDeviceStateService
BinderCallsStatsService

这一阶段可以理解为：系统基础调度能力已建立，开始补齐运行态统计、状态感知和核心组件管理能力。

五、startOtherServices：启动功能型服务

startOtherServices() 是最大的一段，会启动大量面向系统功能的服务。典型包括：

text
WindowManagerService / InputManagerService
Network / Connectivity
NotificationManagerService
LocationManagerService
AudioService
AlarmManagerService
JobSchedulerService
StorageManagerService
DevicePolicyManagerService

这些服务数量多、依赖广，所以通常放在 bootstrap/core 之后启动。

这里知道 WMS 需要与 ATMS/AMS、Display 和 Input 建立协作关系即可，不需要在总览文档里背它们相互注入的每一行调用。

其他服务的依赖例如：

  • Notification 需要包、权限、用户状态。

  • Connectivity 依赖底层网络服务和系统网络状态。

  • Location 依赖权限、AppOps、用户和后台限制。

六、boot phase：服务启动后的阶段通知

服务 onStart() 执行完，不代表它已经可以做所有事情。Android 还会用 boot phase 通知服务当前系统启动到了哪个阶段。

常见阶段包括：

text
PHASE_WAIT_FOR_DEFAULT_DISPLAY
PHASE_LOCK_SETTINGS_READY
PHASE_SYSTEM_SERVICES_READY
PHASE_ACTIVITY_MANAGER_READY
PHASE_THIRD_PARTY_APPS_CAN_START
PHASE_BOOT_COMPLETED

boot phase 的意义是把“创建服务对象”和“依赖 ready 后继续初始化”拆开，避免服务在依赖还没准备好时做过早操作。

boot phase 不是等 startOtherServices() 全部结束后一次性发送。SystemServer 会在启动过程中按依赖穿插推进，例如 PMS 前等待默认 Display，核心服务完成后再进入 ActivityManager Ready 和允许第三方 App 启动等阶段。

七、AMS.systemReady：从服务初始化进入应用运行

当 PMS、WMS、Input、Display 等核心链路准备完成后，SystemServer 会显式调用：

text
SystemServer.startOtherServices()
  -> AMS.systemReady(callback)

这一步不是创建 AMS，而是告诉 AMS：核心系统服务已经准备完成，可以进入启动系统应用和普通应用的阶段。

text
SystemServer
  -> AMS.systemReady(...)
  -> 推进 ActivityManager Ready 等 boot phase
  -> 启动 SystemUI、persistent App 和 Launcher
  -> 允许第三方 App 运行

因此只需区分：服务对象创建、服务 ready、允许应用启动是三个不同阶段。

八、为什么这样设计

Framework 服务之间依赖复杂，不能无序启动。SystemServer 通过分阶段启动解决三个问题：

  1. 依赖顺序：先建立进程和 Activity 调度底座，再补齐电源、显示、包、窗口和输入，最后启动依赖它们的功能服务。

  2. 生命周期统一：继承 SystemService 的服务由 SystemServiceManager 统一启动和分发 boot phase。

  3. 对外可用时机：服务创建、Binder 注册、系统 ready、三方 App 可启动是不同阶段，不能混成一步。

一句话概括：

text
SystemServer 负责按依赖顺序搭建 Framework 服务体系；具体系统能力不在 SystemServer 里实现，而在各个 Framework Service 内部实现。
