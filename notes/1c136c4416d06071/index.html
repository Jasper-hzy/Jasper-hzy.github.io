系统启动流程

本篇目录 4 节

  2. Zygote：建立 Java 进程运行基础
  3. 系统服务的启动、管理与发现

Android 启动链路可以先抓住一条主线：Linux 内核启动 init，init 拉起 Android 用户空间的基础进程，Zygote fork 出 system_server 和普通 App 进程，system_server 启动 Framework 系统服务，最后启动 Launcher 让系统进入可交互状态。

text
Bootloader
  -> Linux Kernel
  -> init
  -> native daemons / servicemanager / SurfaceFlinger / Zygote
  -> Zygote fork system_server
  -> SystemServer.main
  -> SystemServiceManager 启动 Framework Services
  -> AMS / ATMS 启动 Launcher

从内核进入 Android 用户空间

Bootloader 和 Kernel

Bootloader 负责初始化基础硬件、校验并加载系统镜像，然后把控制权交给 Linux Kernel。Kernel 启动后初始化进程调度、内存管理、文件系统、网络、设备驱动，以及 Android 依赖的 Binder、input、display 等驱动能力。

Kernel 准备好用户空间后，会启动第一个用户空间进程：

text
PID 1: init

所以 init 是 Android 用户空间的起点。

init：Android 用户空间起点

init 会解析 init.rc、init.zygote*.rc 和厂商相关 rc 文件，拉起 Android 用户空间的基础 native 进程。

典型进程包括：

text
servicemanager
hwservicemanager
vold
netd
surfaceflinger
audioserver
media 相关服务
zygote / zygote64

这里要区分两类服务：

类型谁启动例子
native service多由 init 直接启动servicemanager、surfaceflinger、audioserver、netd
Framework service多由 system_server 启动AMS/ATMS、PMS、WMS、PowerManagerService

servicemanager 是 Binder 服务目录，负责保存系统全局服务名到 Binder 引用的映射；surfaceflinger 是独立 native 进程，负责图层合成。它们不是 system_server 内部的 Java 服务。

Zygote：建立 Java 进程运行基础

init 启动 Zygote 后，Zygote 进入 Java 世界的初始化流程：

text
app_process
  -> ZygoteInit.main
  -> preload classes / resources
  -> startSystemServer
  -> runSelectLoop

Zygote 内部已经初始化 ART Runtime，并预加载 Framework 常用类和系统资源。后续 Java 进程通过 fork Zygote 创建，可以复用这些预加载结果，减少启动耗时和内存占用。

Zygote 会 fork 两类重要进程：

子进程fork 时机入口职责
system_serverZygote 启动早期主动 forkSystemServer.main()启动和承载 Framework 系统服务
普通 App 进程AMS 请求启动应用时 forkActivityThread.main()运行 App 组件

fork 后不会“连带复制”之前已经 fork 出去的进程。system_server 和普通 App 都是 Zygote 的子进程，但它们彼此是独立进程。

text
zygote
  ├── system_server
  ├── app_process A
  ├── app_process B
  └── app_process C

系统服务的启动、管理与发现

系统服务的承载进程、进程内生命周期管理器和跨进程服务目录承担不同职责。

system_server：Framework 服务进程

system_server 是 Zygote fork 出来的 Java/ART 进程，入口是：

text
SystemServer.main()
  -> new SystemServer()
  -> SystemServer.run()

它承载大量 Java Framework 系统服务，例如：

text
ActivityManagerService / ActivityTaskManagerService
PackageManagerService
WindowManagerService
PowerManagerService
DisplayManagerService
InputManagerService
NotificationManagerService
ConnectivityService
PermissionManagerService / AppOpsService

system_server 维护的是系统全局状态和系统策略，例如进程状态、Activity/Task、安装包信息、窗口层级、焦点窗口、权限、电源和网络状态。App 不能直接访问这些对象，只能通过 Binder 调用对应系统服务。

典型访问链路是：

text
App 进程
  -> Framework Manager / API
  -> Binder Proxy
  -> Binder driver
  -> system_server 中的 Framework Service

SystemServiceManager：system_server 内部服务管理器

SystemServiceManager 不是进程，也不是 Binder 服务。它是 system_server 进程内由 SystemServer.run() 创建的 Java 对象，用来管理继承 SystemService 的服务生命周期。

text
SystemServer.run()
  -> new SystemServiceManager(systemContext)
  -> startBootstrapServices()
  -> startCoreServices()
  -> startOtherServices()

mSystemServiceManager.startService(...) 的含义是启动并管理一个 Framework Service：创建服务对象、调用 onStart()、后续按启动阶段调用 onBootPhase()。

服务是否注册 Binder，要看具体服务自己的 onStart()：

text
SystemServiceManager.startService(PowerManagerService.class)
  -> new PowerManagerService
  -> PowerManagerService.onStart()
  -> publishBinderService("power", binder)
  -> ServiceManager.addService("power", binder)

所以：

text
SystemServiceManager 负责服务生命周期
ServiceManager / servicemanager 负责 Binder 服务名发现
具体 Framework Service 负责维护状态和执行策略

ServiceManager 和 Binder 服务发现

servicemanager 是 native 进程，是 Binder 世界里的系统服务目录。普通进程通过 Binder driver 的特殊入口找到它，概念上可以理解为：

text
handle 0 -> servicemanager

系统服务注册时：

text
system_server
  -> ServiceManager.addService("activity", AMS Binder)
  -> Binder 调用 servicemanager
  -> servicemanager 保存 "activity" -> AMS Binder 引用

App 查系统服务时：

text
App
  -> ServiceManager.getService("activity")
  -> Binder handle 0
  -> servicemanager
  -> 返回 AMS Binder 引用
  -> App 后续直接通过 Binder 调 system_server 里的 AMS

普通 App 自定义 Binder 服务通常不注册到全局 servicemanager，而是通过 Service.onBind() 和 bindService() 交给 AMS 管理发现、权限和生命周期。两者底层都经过 Binder driver，区别在服务发现机制：系统服务靠 servicemanager 的名字表，App 服务靠 AMS 的组件绑定模型。

Launcher 启动与链路总结

Launcher：系统可交互入口

核心 Framework 服务启动完成后，AMS/ATMS 会启动桌面 Launcher。Launcher 本质也是一个 App，只是它响应 HOME Intent。

text
Intent.ACTION_MAIN
CATEGORY_HOME
CATEGORY_DEFAULT

启动链路可以简化为：

text
system_server 启动完成
  -> AMS / ATMS ready
  -> PMS 解析 HOME Intent
  -> 找到 Launcher Activity
  -> 如果 Launcher 进程不存在，请求 Zygote fork
  -> ActivityThread 创建 Launcher Activity
  -> WMS / SurfaceFlinger 显示桌面

所以“看到桌面”说明多条主链路已经跑通：PMS 能解析包和组件，AMS/ATMS 能启动 Activity，Zygote 能 fork App 进程，WMS 能接入窗口，SurfaceFlinger 能完成图层合成。

关键结论

  1. init 是 PID 1，是 Android 用户空间起点。

  2. init 拉起 Zygote 和一批 native 服务，例如 servicemanager、surfaceflinger、netd。

  3. Zygote 初始化 ART 和预加载资源，随后 fork system_server 和普通 App 进程。

  4. system_server 运行 AMS、PMS、WMS 等 Java Framework 系统服务，维护系统全局状态。

  5. SystemServiceManager 是 system_server 内部的服务生命周期管理器。

  6. servicemanager 是 Binder 服务目录，负责系统服务名到 Binder 引用的发现。

  7. Launcher 是系统启动后的 HOME Activity，是 Android 进入可交互状态的标志。
