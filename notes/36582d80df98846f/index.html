云游戏

云游戏优化

云游戏优化的核心目标不是单纯提高画质，而是在实时交互约束下同时控制延迟、卡顿和稳定性。普通直播可以接受秒级延迟，云游戏需要让用户的输入尽快反馈到画面变化上，因此每一帧都要关注“从远端游戏出帧到客户端上屏”的完整链路。

本文整理云游戏性能指标、关键链路、优化策略和效果。

核心指标

云游戏最核心的两个用户体验指标是：

  1. 操作延迟：用户输入到感知画面变化的时间，体现操作跟手性。

  2. 100ms 卡顿率：渲染间隔超过 100ms 的卡顿时长占比，体现画面稳定性。

这两个指标分别对应不同问题：

  • 操作延迟偏高，通常说明链路里存在固定耗时或排队，例如网络 RTT、JitterBuffer、编解码、渲染排队。

  • 100ms 卡顿率偏高，通常说明链路里存在抖动，例如网络丢包、乱序、解码波动、渲染阻塞。

只看这两个大盘指标还不够，它们只能说明用户体验变差，不能直接说明瓶颈在哪。因此需要把一帧拆成更细的环节。

一帧全链路拆解

云游戏一帧可以拆成上行、网络、下行三段。

text
远端 Android 游戏渲染
  -> 抓屏 / 颜色空间转换
  -> 编码前处理
  -> 送入编码流水线
  -> 硬件编码
  -> Pacer 分 RTP 包和平滑发送
  -> 网络传输
  -> 客户端组包 / FEC / NACK / 乱序重排
  -> JitterBuffer 抗抖
  -> 硬件解码
  -> 解码后处理
  -> 渲染上屏

全链路指标可以拆成 15 个环节，覆盖采集、编码前处理、送编、编码、Pacer、网络组帧、JitterBuffer、解码、渲染等阶段。这样做的价值是：端到端延迟变差时，可以定位到具体是采集、网络、解码还是渲染环节，而不是只看到一个总耗时。

指标体系设计

帧级数据量很大，线上通常不会把每一帧的所有明细都全量上报，而是在本地按时间窗口预聚合。这里采用 2s 窗口聚合，再把聚合结果落表。

每个关键环节可以同时看几类指标：

指标说明用途
平均耗时某环节窗口内平均值判断基础耗时水平
最大耗时窗口内最差帧发现尖刺问题
P90 / P95分位耗时更接近大盘用户体验
达标帧数低于阈值的帧数量计算环节稳定性
Jitter相邻帧或窗口内波动判断抖动而不是固定耗时
无效帧 / 丢帧原因某环节没有完整数据或发生丢帧做链路归因

RTT 也可以拆成更接近视频帧的定义：

text
帧级网络 RTT
  = Pacer 耗时
  + 等待发送耗时
  + 组帧耗时
  + 纯网络往返耗时

这个定义比单纯 socket 层 RTT 更适合云游戏，因为它把一帧真正经过的网络发送、接收和重组成本纳入了评估。

优化方向一：抓屏和编码前处理

抓屏耗时可以理解为：

text
游戏渲染 + VSYNC 调度 + Layer 合成 + VirtualDisplay 输出 + 送编码前处理

常见路径有三种：

方案链路优点问题
OES -> YUV / NV12OES 纹理转 YUV，再走 CPU Buffer 送编码兼容性好，方便前处理多一次格式转换和 CPU/GPU 数据流转
OES 纹理OES 纹理经 OpenGL 绘制到编码 Surface少一次 YUV 转换，数据更多留在 GPU 链路需要处理 SurfaceTexture / 离屏缓冲阻塞
编码直通VirtualDisplay 或游戏画面直接写入编码器输入 Surface理论链路最短分辨率、旋转、裁剪、背压和兼容性复杂

OES 纹理路径相比老的 NV12/YUV 路径，编码前处理和送编环节约优化 2ms。

更激进的方向是游戏画面直通编码：通过代理 Surface 或 hook 游戏获取 Surface 的流程，让游戏画面直接绘制到编码器输入 Surface，减少 VirtualDisplay、SurfaceTexture、OpenGL 绘制等中间环节。这个方向的理论收益更高，但兼容和生命周期风险也更大。

更细的抓屏方案见 Android 容器抓屏实现。

优化方向二：编码

编码优化主要解决两个问题：编码耗时和硬编覆盖率。

可落地策略包括：

  1. 提高硬编覆盖率，减少因为推帧过快、编码吐帧慢等原因导致的硬编降级。

  2. MediaCodec 切 NDK 实现，减少 Java 层调用和 buffer 操作成本。

  3. 同步 API 改异步 API，减少取 buffer 等待和线程阻塞。

  4. 针对特定设备或芯片指定更合适的编码器。

相关效果包括：

  • 硬编覆盖率提升到 99% 以上。

  • 编码器切 NDK 实现约优化 0.777ms。

  • 编码异步化带来约 2% CPU 优化。

编码优化要避免只看平均值。云游戏更怕尖刺和波动，所以 P90/P95、最大值、编码前排队、编码吐帧慢导致的背压都要一起看。

优化方向三：网络传输

网络链路对云游戏影响很大，因为它同时影响操作延迟和画面卡顿。相比直播，云游戏一般使用 P2P 或低延迟链路，且是双向实时：

  • 下行：远端视频帧到客户端。

  • 上行：客户端输入指令到远端游戏。

主要优化策略：

  1. 提高同省、同运营商调度率，减少物理网络距离和跨网波动。

  2. 从 100ms 反馈推进到帧级、包级反馈，更快感知拥塞。

  3. 拥塞时更快压低码率，减少丢包和重传。

  4. 好网恢复时，通过连续窗口内 RTT 和 Loss 判断，更快拉升预估带宽和码率。

  5. 结合 FEC、NACK、乱序重排，降低弱网下组帧失败和卡顿。

同省调度率从 55% 提升到 90.37%，操作延迟下降约 6ms，卡顿率下降约 0.05%。网络相关优化合计约 9ms。

优化方向四：JitterBuffer

JitterBuffer 的作用是抗网络抖动，但它本质上是在主动囤帧，所以会引入额外延迟。

传统策略的问题：

  1. 能抗网络抖动，但无法覆盖解码、渲染等后续环节抖动。

  2. 主动囤帧会增加端到端延迟。

  3. 囤帧过多会影响解码器效率，让实时性变差。

优化方向包括：

  1. 基于历史卡顿信息做奖惩式爬升，弱网时增加缓冲，好网时降低缓冲。

  2. 请求关键帧时清空 JitterBuffer，避免旧帧继续排队。

  3. 把部分抗抖能力后移到解码输出缓冲区，通过渲染时间戳控制上屏。

关键原理是：MediaCodec.releaseOutputBuffer 支持传入渲染时间戳，SurfaceFlinger 合成上屏时会根据时间戳判断是否显示到当前帧。这样可以用解码器输出缓冲区统一吸收网络和解码抖动，减少前置 JitterBuffer 的主动延迟。

JitterBuffer 约优化 2ms，P90 约优化 5ms；请求关键帧清空 JB 策略使操作延迟 P90 从 208ms 优化到 203ms。

优化方向五：解码

解码优化主要关注硬解覆盖率、机型参数适配、同步/异步 API 和错误治理。

可落地策略：

  1. 提高硬解占比，避免因为负载策略过保守降级到软解。

  2. 补充硬解错误上报，按机型、编码格式、分辨率、低延迟参数下钻。

  3. 处理特定机型低延迟参数兼容问题，例如华为机型。

  4. MediaCodec 切 NDK 解码实现。

  5. 同步 API 改异步 API，减少解码线程等待。

相关效果包括：

  • 硬解占比从 97.84% 提升到 99% 左右。

  • 华为低延迟参数治理后，大盘解码均值从 14.44ms 优化到 13.87ms，单华为机型用户解码耗时约优化 8ms。

  • NDK 解码约优化 0.7ms。

  • 解码异步化使 client 总耗时约优化 1.3ms，其中包含解码、JitterBuffer、dec2sink 等环节收益。

优化方向六：解码后处理和渲染

客户端解码后上屏常见三种路径：

方案链路成本
OES 输出到 FBO解码到 SurfaceTexture -> OpenGL 绘制到 FBO -> 再绘制上屏链路最长，方便复杂前处理
OES 纹理输出解码到 SurfaceTexture -> OpenGL 绘制上屏少一次 FBO，但仍有 SurfaceTexture 和 OpenGL draw
渲染直通解码器直接输出到 Surface 上屏链路最短，延迟最低

渲染直通的主要收益是减少解码后处理和送渲染链路，对解码送渲染环节约优化 3~4ms。

但它也有现实限制：云游戏需要适配手机分辨率、横竖屏、裁剪和旋转。普通直播可以接受黑边或裁剪，云游戏为了交互体验更希望画面和手机分辨率一致。

因此渲染直通需要解决两个方向的问题：

  1. 编码侧处理：让抓屏输出直接对齐目标分辨率，例如 HWC client 输出对齐 wm size，或统一 VirtualDisplay 抓屏方案。

  2. 解码侧处理：使用 SurfaceControl 的 crop 能力控制 Surface 对应 Layer 的裁剪，让 SurfaceFlinger / HWC 完成裁剪合成。不同 Android 版本接口不同，例如 Android 10~12 的 setWindowCrop、Android 13 的 setCrop，Android 9 可通过 Layout 裁剪兜底。

整体收益总结

整体收益可以总结为：

维度优化前优化后收益
Android 100ms 卡顿率2.18%1.93%-11.47%
操作延迟143ms96ms-47ms，约 -32.51%

部分单项收益：

事项收益
OES 纹理送编编码前处理/送编约优化 2ms
网络传输优化约优化 9ms
JitterBuffer 策略优化约优化 2ms，P90 约优化 5ms
解码链路优化约优化 3ms
渲染直通解码送渲染环节约优化 3~4ms
解码异步化client 总耗时约优化 1.3ms

一句话总结

云游戏性能优化要先把用户感知的“操作不跟手”和“画面卡顿”拆成帧级链路指标，再分别压缩抓屏、编码、网络、JitterBuffer、解码和渲染环节的固定耗时与抖动。真正有效的优化往往不是单点调参，而是减少一次格式转换、一次 buffer 排队、一次 SurfaceTexture 中转、一次 OpenGL 绘制，或者让网络和编解码策略更快响应实时状态。
