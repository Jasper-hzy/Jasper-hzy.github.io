应用启动优化

启动优化先用监控和 Trace 找到关键路径，再判断耗时属于计算、I/O、依赖等待还是资源竞争，最后决定少做、推迟、拆分并行或加速复用。任务、配置、SO、Provider 都是这套方法的具体案例。

Mermaid · 流程图源码
flowchart LR
    A[监控确定慢在哪个阶段] --> B[Trace 追踪关键路径]
    B --> C[归因<br/>计算 / I/O / 等待 / 竞争]
    C --> D[处理<br/>少做 / 晚做 / 拆分 / 加速]
    D --> E[复测耗时与副作用]

目标是缩短用户等待的路径，而不是只减少主线程执行时间。系统拉起流程见 ATMS 与 AMS，编译优化见 ART：JIT / AOT / Profile / GC。

一、先确定启动终点与关键路径

首帧慢，重点看进程拉起、初始化、布局和渲染；页面已经出现但内容迟迟不展示，则继续追踪数据请求、处理和绑定。本文的“首刷”指首屏业务内容展示完成，具体埋点口径需由业务明确，不能与首帧混用。

Mermaid · 流程图源码
flowchart LR
    A[Zygote fork] --> B[ActivityThread.main]
    B --> C[attachApplication]
    C --> D[Application<br/>attachBaseContext]
    D --> E[安装 ContentProvider]
    E --> F[Application<br/>onCreate]
    F --> G[Activity 创建]
    G --> H[首帧]
    H --> I[首刷]

    E -.治理.-> P[FileProvider / ContentProvider]
    F -.治理.-> T[任务创建 / 存储读取<br/>Router / SO]
    G -.治理.-> V[布局与首屏数据]

启动优化不能只看 Application.onCreate()。ContentProvider 位于它之前，任务对象创建、类加载、配置读取、SO 校验也可能在真正执行任务之前就已经进入关键路径。首屏数据也可能提前请求，与初始化或渲染并行；图中是启动里程碑，不代表所有工作串行执行。

关键路径是决定目标时刻何时到达的依赖链，可能跨主线程、后台线程和系统进程。不能把所有线程的耗时直接相加，也不能只优化 Trace 中最长但与首屏无依赖的任务。

二、通过监控和 Trace 判断耗时原因

先用线上分段埋点发现异常阶段、用户群和长尾，再用对应场景的 Trace 追踪调用、线程状态及依赖。普通 Trace 不会自动给出每个方法的内部耗时，必要时补充自定义 trace 区间、调用栈采样和 I/O 事件。

text
启动阶段 / 任务耗时异常
    → 在 Trace 中找到对应区间
    → 看线程状态、调用栈与依赖
        ├─ Running：正在执行，继续查计算或系统调用
        ├─ Runnable：可运行但未获得 CPU，查调度竞争
        └─ 等待 / 阻塞：查 I/O、锁、Binder、后台任务等
    → 确认它是否延后首帧 / 首刷

四类耗时

方向需要确认的证据常见场景
计算量大CPU 执行时间、调用栈热点解压、CRC、解析、类与对象初始化、布局计算
I/O 慢或量大文件读写、缺页、阻塞区间及相关 I/O 事件配置加载、数据库、SO 读写
依赖等待等待方与完成方的关联、锁持有者、Binder 调用链Future、Latch、锁、同步 Binder
资源竞争Runnable 时间、CPU 调度、频率及并发负载线程池过载、后台计算和 I/O 抢占资源

这些不是互斥分类。SO 解压可能同时包含读盘、解码计算和写盘；文件读取可能命中 Page Cache，不能看到 read() 就认定在等待磁盘。

维度用途
Wall Time用户实际等待的时间
Thread CPU Time线程真正占用 CPU 执行的时间
任务排队时间从提交到真正开始执行，区分线程池排队与线程 Runnable 等待 CPU
依赖等待等待锁、Future、Latch、Binder 或其他任务的时间
线程与阶段判断任务是否占用主线程、首帧前或首刷前资源
启动类型区分新安装、覆盖安装、普通冷启动、温启动和热启动
系统状态线程数、GC、内存、磁盘 I/O 和 CPU 竞争情况
text
Wall Time 接近 CPU Time
  -> 更可能是任务本身计算量大

Wall Time 远大于 CPU Time
  -> 更可能在排队、等待锁、等待 I/O、同步 Binder 或被抢占

主线程 CPU 利用率低，不代表应该继续往主线程添加任务。它也可能说明主线程正在等待后台任务、锁、I/O 或 Binder 返回。

三、通用处理方法

先判断工作是否必要、最晚何时需要，再决定如何执行。“打散”指拆分依赖、错峰和受控并行，不是把任务一股脑扔进线程池。

Mermaid · 流程图源码
flowchart TD
    A[关键路径上的耗时工作] --> B{是否必要}
    B -->|否| C[删除无用或重复工作]
    B -->|是| D{目标首帧 / 首刷前必须完成吗}
    D -->|否| E[推迟创建与执行<br/>首屏后或首次使用前]
    D -->|是| F[缩小到最小必要工作集]
    F --> G[拆开依赖<br/>可独立部分提前 / 受控并行]
    G --> H[优化剩余成本<br/>算法 / I/O / 缓存 / 增量 / AOT]
    C --> I[验证关键路径是否缩短]
    E --> I
    H --> I
方法解决什么问题关键边界
不做 / 少做无用初始化、少量需求触发全量加载保留首屏必需能力与业务正确性
晚点做非首屏依赖过早占用资源对象与依赖的创建也要后移；首次使用时必须就绪
拆分与并行串行依赖过粗、工作集中在同一阶段主线程继续等待就仍在关键路径；并发过多会争抢资源
加速 / 复用必须执行的工作本身昂贵或重复缓存有失效条件，增量有版本边界；编译收益见 ART 文档

不要把首屏前的阻塞变成首屏后的集中卡顿，也不要用错误默认值换取启动速度。优化后仍要验证首次使用延迟、数据正确性和资源竞争。

四、具体案例：把通用方法落到耗时环节

1. 启动任务：创建和执行一起后移

任务在首刷后执行，不等于它在冷启动阶段没有成本。构造任务时仍可能发生类加载、依赖注入、反射、对象创建、配置读取和监听注册。

text
优化前：Application.onCreate
          -> 创建全部 Task
          -> 首刷前只执行 MAIN / BACKGROUND
          -> BOOT_FINISH / IDLE Task 等待以后执行

优化后：Application.onCreate
          -> 只保存轻量 TaskFactory
          -> 首刷完成
          -> 创建并执行 BOOT_FINISH / IDLE Task

对应方法：晚点做。延迟任务需要保留原有依赖顺序，轻量工厂也不能提前创建重依赖再捕获进去。

2. 后台任务：拆分依赖，消除主线程等待

把任务提交到线程池不代表完成了异步化。如果主线程最终调用 Future.get()、join()、CountDownLatch.await() 或启动框架的 Ensure 接口，后台任务仍然处于启动关键路径。

Mermaid · 流程图源码
flowchart TB
    subgraph Bad[伪异步]
        M1[主线程继续启动] --> W[等待后台结果]
        B1[后台执行完整任务] --> W
        W --> U1[继续首帧]
    end

    subgraph Good[拆分依赖]
        B2[尽早执行<br/>无依赖的大块工作] --> S[少量依赖收尾]
        D[AB / 配置准备完成] --> S
        S --> U2[使用结果]
    end

对应方法：拆分与并行。原文中的路由初始化任务将不依赖 AB 的大块工作提前执行，依赖 AB 的少量工作在条件满足后收尾，减少主线程最终等待的时间。是否获益要看完成时刻，而不是后台线程是否启动得更早。

3. 配置存储：少量需求不触发全量初始化

KV 存储即使支持后台初始化，也可能在主线程首次读取时完成初始化；如果后台加载尚未结束，主线程还可能反向等待后台线程。

text
主线程首次读取配置
  -> Repo 是否已加载？
       ├─ 是：直接读取
       └─ 否：初始化或等待后台加载
                  -> 冷启动耗时 / ANR 风险

可按配置用途处理：

  • 首帧必需的极少量值：提前生成轻量启动快照，启动时只读取所需字段。

  • 启动高频 Repo：使用白名单在后台前置加载。

  • 非关键配置：延迟到首刷后或业务首次使用时读取。

  • AB 实验：避免为了读取一个实验值而在主线程打开完整 Repo。

对应方法：少做 + 晚做。不是简单地把 KV 存储替换成 SharedPreferences，而是减少为了一个值而触发的全量加载。默认值、旧值是否允许使用必须由业务语义决定；后台预加载也不能让主线程反向等待。

4. SO 准备：减少重复校验与解压范围

此案例针对自定义 SO 压缩管理流程，不是所有 App 启动都要解压 SO。原文记录的 SO 准备任务 P50：新安装首启约 183 ms、覆盖安装首启约 295 ms、普通启动约 48.5 ms。问题是重复准备、增量范围不合理，以及解压 I/O 占用主线程，不是已证明的 linker 重定位瓶颈。

Mermaid · 流程图源码
flowchart TD
    A[启动时检查 SO] --> B{启动类型}
    B -->|新安装| C[准备需要解压的 SO]
    B -->|覆盖安装| D[只处理发生变化的 SO]
    B -->|普通启动| E[校验已有结果]
    C --> F{首帧是否依赖}
    D --> F
    F -->|依赖| G[只保证最小必要集合]
    F -->|不依赖| H[后台解压<br/>首次加载前确认]

对应方法：复用与增量 + 拆分与错峰。原文包括 CRC 缓存、将 43 个 SO 按易变动性拆成两个压缩 block，以及 init / decode / install 阶段解耦；没有披露校验、解码、写盘各自的耗时占比。

可归纳的工程处理包括：

  • 将初始化、解码和安装阶段解耦，减少串行执行。

  • 缓存 SO 的版本、大小和 CRC/Hash，避免每次启动重复计算。

  • 覆盖安装只处理发生变化的 SO。

  • 按变更频率和启动依赖对 SO 分块，降低升级时的解压范围。

  • 非启动依赖 SO 在后台准备，真正加载前确认状态。

  • 使用临时文件写入和原子 rename，避免加载到半成品文件。

  • 处理跨进程文件锁、磁盘空间不足、解压中断和版本回滚。

冷启动依赖的 SO 也不应默认在主线程解压。优先考虑安装阶段、升级阶段或启动早期后台准备；无法避免时，才在关键路径保证最小必要集合。

5. Provider：治理隐式的提前初始化

ActivityThread.handleBindApplication() 的关键顺序是：

text
Application.attachBaseContext()
  -> installContentProviders()
       -> Provider.attachInfo()
       -> Provider.onCreate()
  -> Application.onCreate()

FileProvider

原文所分析的 FileProvider 实现在启动时解析 <paths> XML，并对目录执行规范化处理。多数启动并不使用文件分享，这部分工作可能成为无效前置耗时；具体发生时机需核对所用 AndroidX 版本。

优先进行低风险治理：

  1. 删除无用或重复的 FileProvider。

  2. 精简 <paths>，避免声明过大的目录范围。

  3. 把真正的文件分享准备推迟到功能入口，并在首刷后适度预热。

极致方案可以反射替换 AndroidX FileProvider 的 sCache，返回代理 PathStrategy，直到首次调用时才执行 parsePathStrategy()。该方案依赖 AndroidX 内部字段和方法，需要版本白名单、混淆配置、异常降级和远程开关，不应作为默认方案。

ContentProvider

先检查合并后的 Manifest，确认自有和 SDK Provider。对应方法：少做 + 晚做。删除无用 Provider、关闭 SDK 非必要自动初始化，或将重工作改成按需执行。AndroidX App Startup 可以合并入口、管理依赖，但不会自动消除初始化工作；挪到 Application.onCreate() 里同步执行，也没有退出首帧关键路径。

原文还提出 Hook ActivityThread 暂缓 Provider 安装，再分类初始化。它依赖系统内部实现，涉及 Provider 发布、外部访问等待、多进程、Direct Boot 和首次访问竞态，不应概括为“任意 Provider 都能后台或懒加载”；需要专项兼容与失败恢复，不能作为默认优化手段。

五、验证关键路径，而不是按案例顺序优化

text
固定启动类型、设备条件与首帧 / 首刷口径
    → 找关键路径上收益明确、风险可控的瓶颈
    → 单项改动，对比优化前后的 Trace
    → 看目标时刻是否提前，等待是否转移到别处
    → 线上分层验证收益与副作用

任务、存储、SO、Provider 没有固定的优化先后顺序，取决于实际证据。每项优化同时观察冷启 P50/P90/P99、首帧、首刷、ANR 和丢帧，并按新安装、覆盖安装、普通启动及设备性能分层。不同实验的收益不能直接相加；延迟初始化还要关注首次使用耗时、后台资源竞争和功能成功率。
