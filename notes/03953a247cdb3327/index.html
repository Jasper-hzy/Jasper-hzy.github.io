Binder 要解决的核心问题是：让一个进程像调用本地方法一样，调用另一个进程中的对象。

text
Client Proxy
  -> Binder Driver
  -> Server Binder Thread
  -> Stub.onTransact()
  -> Service 实现

本文关注 Binder 的系统主线，不展开 AIDL、Messenger 和 bindService() 的使用教程。源码基线为本地 frameworks/native 的 d1735f8（Android 13 tm-qpr2-release）。

架构、对象身份与服务发现

Binder 分为四层

text
业务接口
  -> AIDL 生成的 Proxy / Stub
  -> libbinder：BinderProxy、BpBinder、IPCThreadState
  -> Binder Driver：node、ref、transaction、线程唤醒
  -> 服务端 Binder 线程池

  • AIDL：生成参数序列化、方法编号、Proxy 和 Stub，本身不是 Binder 驱动。

  • libbinder：把方法调用转换成 Binder 命令和 Parcel。

  • Binder Driver：跨进程定位对象、复制数据、转换 Binder 引用并调度目标线程。

  • Binder 线程池：接收事务并进入服务端的 onTransact()。

同进程调用是例外。Stub.asInterface() 如果发现 Binder 对象就在当前进程，会直接返回本地实现，不经过驱动。

node、ref 和 handle 如何关联两端

Binder 驱动不会使用 Java 对象地址直接跨进程寻址，而是维护三层关系：

text
服务端进程
  Binder 实体
    -> binder_node
         ↑
客户端进程
  handle -> binder_ref

binder_node

binder_node 代表真正的服务端 Binder 实体，记录它属于哪个进程，以及服务端用于还原本地 Binder 对象的信息。

一个 binder_node 可以同时被多个进程引用。

binder_ref

binder_ref 表示某个进程对目标 binder_node 的引用。不同客户端引用同一个服务端 Binder 时，各自拥有自己的 binder_ref。

handle

handle 是 binder_ref 在当前进程内的整数编号，Java 层通常由 BinderProxy 持有。

text
客户端 A：handle 3 -> ref A -> node X
客户端 B：handle 7 -> ref B -> node X

handle 只在所属进程内有效，不是 Binder 对象的全局地址；相同数字在不同进程里可以指向不同对象。

调用时，驱动执行的核心查找是：

text
调用进程 + handle
  -> binder_ref
  -> binder_node
  -> 服务端进程和 Binder 实体

ServiceManager 只负责服务发现

在 Framework 使用的 Binder context 中，servicemanager 是 context manager，客户端通过特殊的 handle 0 获得它的代理。

text
ProcessState.getContextObject()
  -> getStrongProxyForHandle(0)
  -> ServiceManager Proxy

注册实名系统服务

以 system_server 注册 AMS、WMS 等服务为例：

text
SystemServer 中的 Binder Stub
  -> ServiceManager.addService(name, binder)
  -> 驱动为本地 Binder 建立 binder_node
  -> ServiceManager 保存 name -> Binder 引用

客户端查询服务

text
客户端 getService(name)
  -> 调用 handle 0 对应的 ServiceManager
  -> ServiceManager 返回目标 Binder 引用
  -> 驱动在客户端建立 binder_ref 和 handle
  -> Java 层得到 BinderProxy

ServiceManager 不参与后续每一次业务调用。客户端取得目标服务的 handle 后，后续事务由 Binder Driver 直接发送到服务端进程。

匿名 Binder

Binder 对象不一定要注册到 ServiceManager。bindService() 返回的 Binder、回调接口和 Binder 连接池，本质上都是把一个 Binder 对象放进已有事务中传给对方：

text
已有 Binder 通道
  -> Parcel 中携带新的 Binder 对象
  -> 驱动转换为接收进程的 binder_ref / handle

因此，ServiceManager 管理的是“通过名字发现的 Binder 服务”，Binder Driver 管理的是所有 Binder 对象和事务。

一次事务的数据与调用路径

一次同步事务如何执行

以客户端调用 AIDL 方法为例：

text
Client
  -> AIDL Proxy：参数写入 Parcel
  -> BinderProxy / BpBinder.transact()
  -> IPCThreadState.transact(handle, code, data)
  -> BC_TRANSACTION
  -> ioctl(BINDER_WRITE_READ)

Binder Driver
  -> handle 找到 binder_ref
  -> binder_ref 找到 binder_node
  -> 准备目标进程的 Binder buffer
  -> 复制并转换事务数据
  -> 将事务加入目标线程或进程待办队列
  -> 唤醒服务端 Binder 线程

Server
  -> 收到 BR_TRANSACTION
  -> IPCThreadState.executeCommand()
  -> BBinder.transact()
  -> Stub.onTransact(code, data, reply)
  -> Service 方法
  -> reply 原路返回客户端

code 标识调用哪个接口方法，Parcel data 保存参数，Parcel reply 保存返回值或异常。

Binder 调用看起来像普通方法调用，但执行线程已经从客户端调用线程切换成服务端 Binder 线程。服务端如果需要修改自己的主线程状态，还要再通过 Handler 等机制切换线程。

mmap 为什么能减少一次复制

每个使用 Binder 的进程都会打开 Binder 设备，并通过 mmap() 建立一块用于接收事务的虚拟地址空间：

text
ProcessState
  -> open("/dev/binder")
  -> mmap(..., PROT_READ, ..., binderFd, 0)

发送事务时，数据路径可以概括为：

text
发送端用户空间 Parcel
  -> copy_from_user()
  -> 驱动为接收进程准备的 Binder buffer
  -> 接收端通过 mmap 地址直接读取

mmap() 本身不负责复制数据，也不是让发送端和接收端直接共享同一块普通内存。它让驱动管理的接收 buffer 映射到接收进程地址空间，因此接收端不需要再执行一次 copy_to_user()。

所以 Binder 通常被称为“一次拷贝”，不是“完全零拷贝”。回复数据同样会复制到原调用进程的 Binder 接收区。

Binder 对象不能只复制地址

Parcel 除了普通字节，还可以携带 Binder 对象和文件描述符。驱动复制数据时会根据对象偏移表逐个处理：

  • 本地 Binder 对象跨进程传输后，转换成接收进程中的 handle。

  • 已有远程 Binder 再次传输时，驱动维护新的 binder_ref 关系。

  • 文件描述符需要复制成接收进程可用的 fd。

这也是 Binder Driver 不能被普通共享内存完全替代的原因：它不仅搬运数据，还维护对象身份、引用计数和调用方身份。

线程模型、死亡通知与调用身份

同步调用、oneway 和线程池

同步调用

普通 Binder 事务是同步的：客户端调用线程发送事务后等待 BR_REPLY。

text
Client Thread：发送 -> 阻塞等待
Server Binder Thread：执行 -> 返回 reply
Client Thread：被唤醒 -> 继续执行

因此，在主线程发起耗时 Binder 调用仍可能造成卡顿或 ANR。Binder 只解决跨进程调用，不会自动把客户端工作切到后台线程。

oneway

AIDL 中标记为 oneway 的方法不等待服务端执行结果：

text
Client：事务交给驱动后返回
Server：稍后从 Binder 队列中取出并执行

oneway 不是“丢了也没关系”，也不代表服务端不执行。发往同一个 Binder node 的异步事务会保持串行顺序；如果发送速度长期高于消费速度，仍会形成积压。

Binder 线程池

服务端进程需要 Binder 线程等待驱动命令：

text
ProcessState.startThreadPool()
  -> Binder Thread
  -> IPCThreadState.joinThreadPool()
  -> 等待 BR_TRANSACTION

多个 Binder 线程意味着服务端可能并发执行多个事务，共享状态必须自行保证线程安全。某个 Binder 线程被耗时任务长期占用，也会降低整个服务的并发处理能力。

死亡通知与调用身份

DeathRecipient

客户端可以对远程 BinderProxy 调用 linkToDeath()。服务端进程退出后，驱动根据 binder_ref 和 binder_node 的关系通知客户端，最终回调 binderDied()。

DeathRecipient 只能说明远端 Binder 所在进程已经死亡，不能保证服务自动恢复，也不能替代业务层重连。

调用身份

驱动会把调用方的 PID、UID 等身份随事务交给服务端。系统服务可以通过 Binder.getCallingUid() 等接口做权限判断。

如果系统服务收到客户端请求后，再以自己的代码调用其他系统接口，需要明确当前操作应该沿用客户端身份还是服务端身份；clearCallingIdentity() 用错可能造成越权或权限异常。

适用边界与常见误区

与 Linux 基础 IPC 的区别

从最基础的常用通信模型看，Linux 进程间通信主要有字节流、共享页和异步通知：

text
管道 / Socket：数据经内核管理的端点或缓冲区传递
共享内存：不同进程的页表项指向同一批物理页
信号：内核向进程发送异步通知

Linux 还提供 System V / POSIX Message Queue、信号量、eventfd 等独立机制，但它们没有改变 Binder 选型的核心问题：Android 系统服务需要的不只是传输数据，而是受控的本机对象 RPC。

方式提供的基础能力用于系统服务时还缺少什么
Pipe / FIFO单向或半双工字节流消息协议、请求响应、多客户端和对象生命周期
Unix Domain Socket双向流或数据报，可传 fd 并获取对端凭据需自行实现服务发现、远程对象、引用管理和 RPC 线程模型
共享内存共享物理页，适合大数据不提供通知、消息边界、同步、权限和生命周期
Signal进程级异步通知载荷很小，不适合复杂请求和返回值
Binder对象 RPC、身份传递、引用转换、死亡通知和线程调度不适合直接承载图像、音视频等大块数据

Binder 不是对 Pipe、Socket 的简单封装，而是通过专用内核驱动组合多种基础能力：

text
用户进程
  -> open("/dev/binder")
  -> mmap() 映射接收缓冲区
  -> ioctl(BINDER_WRITE_READ) 提交或接收事务

Binder Driver
  -> copy_from_user() 复制事务数据
  -> binder_node / binder_ref 维护跨进程对象
  -> todo 队列和 wait queue 调度目标 Binder 线程

Android 不会用 Binder 替代所有 IPC，而是根据数据特征组合使用：

text
系统服务的小型控制命令  -> Binder
图像、音频等大块数据  -> 共享内存 / dma-buf
共享缓冲区的 fd 和控制信息 -> Binder
Zygote fork 命令             -> Unix Domain Socket

ServiceManager 与 Binder 安全边界

ServiceManager 的安全价值是受控的服务命名空间，但它不是通用的防 Hook 机制：

text
服务注册：拒绝 App UID + SELinux add 权限 + 名称/声明合法性
服务查询：SELinux find 权限
Binder 调用：驱动提供真实调用方 UID / PID
业务方法：系统服务继续检查 Permission / AppOps / User

当前 ServiceManager 会直接拒绝 App UID 注册服务，并通过 SELinux 分别检查 add 与 find 权限。因此普通 App 无法随意注册或替换 AMS 等系统服务，也无法伪造 Binder 驱动提供的 UID。高权限进程对同名服务的处理细节会随 Android 版本变化，安全边界不应建立在“同名一定无法替换”上。

如果攻击者已经获得 Root、内核控制权、system_server 代码执行权或目标进程内注入能力，Binder 本身不能阻止 Java / Native / 内核层 Hook。

因此 Binder 的安全模型是：

text
ServiceManager 注册与查询控制
  + Binder 引用隔离和真实调用身份
  + SELinux binder / service_manager 规则
  + 服务方法的业务权限检查

常见误区

1. ServiceManager 是所有 Binder 事务的中转站

错误。ServiceManager 只负责实名服务的注册和查询。获得目标 Binder 后，客户端与服务端通过驱动直接通信。

2. handle 是 Binder 服务的全局编号

错误。handle 是当前进程内 binder_ref 的编号，只有 handle 0 具有 context manager 的特殊语义。

3. mmap 完成了进程间数据复制

错误。复制由驱动完成，mmap() 提供接收 buffer 的用户空间映射，从而省掉接收端的第二次复制。

4. oneway 等于开了一个新线程

错误。它只改变客户端是否等待 reply，服务端仍通过 Binder 线程池执行。

5. Binder 适合传输大块数据

错误。Binder 接收缓冲区由进程内并发事务共享，事务过大可能触发 TransactionTooLargeException。图片、视频帧等大数据通常只通过 Binder 传递 fd、共享内存句柄或 Surface，而不是直接塞进 Parcel。

应用层封装示例

这些工具没有引入新的 IPC 机制，底层仍然是 Binder，只是对接口形式和线程模型做了不同封装。

1. AIDL：生成 Proxy 和 Stub

aidl
interface IBookService {
    Book getBook(int id);
}

服务端实现 Stub：

java
private final IBookService.Stub binder = new IBookService.Stub() {
    @Override
    public Book getBook(int id) {
        return repository.get(id);
    }
};

@Override
public IBinder onBind(Intent intent) {
    return binder;
}

客户端取得 Binder 后转换成接口：

java
public void onServiceConnected(ComponentName name, IBinder service) {
    IBookService bookService = IBookService.Stub.asInterface(service);
}

如果两端在同一进程，asInterface() 返回本地 Stub；如果跨进程，则返回 Proxy。远程方法调用最终仍是：

text
Proxy.transact() -> Binder Driver -> Stub.onTransact() -> getBook()

Book 这类复杂参数需要实现 Parcelable 并在 AIDL 中声明。跨进程后得到的是重新反序列化的数据对象，不再是服务端原对象的 Java 引用。

2. Messenger：把 Binder 调用转换成 Message

java
Messenger server = new Messenger(new Handler(looper) {
    @Override
    public void handleMessage(Message message) {
        // 处理客户端消息
    }
});

服务端通过 server.getBinder() 暴露 Binder，客户端再使用 Messenger.send() 发送消息。

Messenger 底层仍使用 Binder，但请求会进入指定 Handler，因此天然串行，适合简单消息通信；它不适合需要大量强类型方法和并发调用的接口。

3. RemoteCallbackList：管理跨进程回调

客户端把回调 Stub 传给服务端，本质上是把一个新的 Binder 对象放进 Parcel。服务端通常使用 RemoteCallbackList 保存这些回调：

java
RemoteCallbackList<IListener> callbacks = new RemoteCallbackList<>();

callbacks.register(listener);

int count = callbacks.beginBroadcast();
for (int i = 0; i < count; i++) {
    callbacks.getBroadcastItem(i).onChanged();
}
callbacks.finishBroadcast();

它以底层 Binder 身份区分客户端，并结合死亡通知清理已经退出进程的回调，避免直接用普通 List 管理远程接口。

4. Binder 连接池：通过一个 Binder 返回其他 Binder

aidl
interface IBinderPool {
    IBinder queryBinder(int serviceId);
}

客户端先获得 IBinderPool，再通过 queryBinder() 得到其他业务 Binder。返回的业务 Binder 不需要注册到 ServiceManager，而是通过这次已有事务传给客户端。

它说明了 Binder 的一个重要能力：Binder 对象本身可以作为 Parcel 数据继续跨进程传输，驱动会为接收进程建立对应的 binder_ref 和 handle。

源码入口与结论

源码入口

  • frameworks/native/libs/binder/ProcessState.cpp：打开驱动、mmap()、handle 0、线程池。

  • frameworks/native/libs/binder/BpBinder.cpp：客户端代理、transact()、linkToDeath()。

  • frameworks/native/libs/binder/IPCThreadState.cpp：事务命令、ioctl()、等待 reply、处理 BR_TRANSACTION。

  • frameworks/native/libs/binder/Binder.cpp：BBinder.transact() 和 onTransact()。

  • drivers/android/binder.c：binder_node、binder_ref、事务路由与引用管理。

  • AOSP Binder overview

  • AOSP Binder threading

核心结论

text
服务发现：name -> ServiceManager(handle 0) -> BinderProxy(handle)
对象关联：handle -> binder_ref -> binder_node -> 服务端
事务调用：Proxy -> Driver -> Binder Thread -> Stub.onTransact
数据传输：发送端一次复制 -> 接收端 mmap buffer
选型边界：小型对象 RPC -> Binder，大数据 -> 共享内存 / dma-buf
安全边界：服务发现控制 + 驱动身份 + SELinux + 业务权限校验

Binder 的重点不是记住 AIDL 模板，而是理解驱动如何维护跨进程对象身份，以及一次事务如何从客户端线程进入服务端 Binder 线程。
