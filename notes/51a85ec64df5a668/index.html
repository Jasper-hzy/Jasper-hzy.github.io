客户端开发/ Android/ 系统原理

ART：JIT / AOT / Profile / GC

核心结论：提前提供 Profile，让设备提前编译关键代码

启动优化方案是：开发阶段采集启动和高频路径，构建时生成与最终 DEX 匹配的二进制 Profile 并随包发布，让支持它的安装链路在首次运行前完成针对性 AOT 编译，减少解释执行和 JIT 预热。

text
执行关键场景，采集类和方法的热点清单
    → 构建时生成与最终 DEX 匹配的 baseline.prof
    → 打包进 assets，随 APK / AAB 发布
    → 支持的安装链路获取有效 Profile
    → 设备上的 dex2oat 按策略提前编译目标代码
    → App 运行时使用可用机器码

assets 中保存的是二进制热点信息，不是机器码；机器码由设备侧 dex2oat 生成。放进 assets 也不等于安装时必然自动编译：

  • assets/art-profile/baseline.prof：内嵌 Profile 方案，需要系统支持并启用，且安装编译策略允许；AOSP 的相关入口限制为 Android 15 / API 35 及以上。

  • assets/dexopt/baseline.prof：常规 Baseline Profile 路径，商店可配合安装期分发；仅靠 App 内的 ProfileInstaller，则是在 App 运行后写入 Profile，供后续 dexopt 使用，不能据此保证这次首次启动已获 AOT 优化。

收益是减少运行时编译与解释开销，代价是提前编译的 CPU、时间和产物空间；它不能替代主线程 I/O、初始化任务和首帧渲染优化。分发与版本边界详见下文“DF 的 Profile 如何在安装期生效”。

一、ART 运行与优化闭环

ART 决定 DEX 代码如何执行，也负责 Java 堆的对象分配与回收。它对启动速度的影响主要来自两条链路：代码是否需要解释或现场编译，以及启动阶段的对象分配是否触发 GC。

这套机制的核心不是在 JIT 和 AOT 之间二选一，而是让不同执行方式协同工作：

机制作用对启动的影响
Interpreter直接解释 DEX 字节码无编译等待，但执行速度较慢
JIT运行时编译当前进程的热点方法当前运行变快，但会消耗 CPU 和时间
AOT运行前把选中的 DEX 方法编译为机器码启动时可直接执行，但会增加编译耗时和磁盘占用
Profile记录值得优化的类和方法帮助 ART 只编译高价值代码
GC回收 Java 堆中不再使用的对象启动阶段分配过多时可能增加暂停和 CPU 开销

JIT 解决“当前这次运行尽快变快”，Profile 驱动的 AOT 解决“后续启动一开始就快”。热点代码与 dex2oat 并不冲突，热点 Profile 正是后台 AOT 选择编译目标的重要输入。

二、一次方法调用如何选择执行方式

主图中间部分展示了方法执行入口的选择：存在可用 AOT 代码时直接执行机器码；不存在时先进入解释器，达到热点阈值后再由 JIT 编译。

JIT 生成的机器码通常保存在当前进程的 JIT Code Cache 中，进程结束后不会直接成为下次启动可复用的 AOT 产物；但 ART 会把热点类和方法写入 Runtime Profile，供后续 dexopt 使用。

三、Profile 如何改善首次启动和后续启动

Runtime Profile

Runtime Profile 来自真实运行。目标方法第一次没有 AOT 代码时，可能先解释执行并在变热后被 JIT 编译；热点信息持久化后，设备可以在合适时机进行后台 dexopt，使后续启动使用 AOT 代码。

Baseline Profile

Baseline Profile 随应用发布，提前描述启动和高频路径。系统拿到 Profile 后，可以在用户运行这些代码之前就对目标方法进行 AOT 编译，减少首次启动中的解释执行和 JIT 预热。

Cloud Profile

Cloud Profile 通常来自应用商店聚合的真实用户热点数据。它与 Baseline Profile 的目标相同，都是提前告诉 ART 哪些代码值得编译；区别是 Baseline Profile 由开发者随版本维护，Cloud Profile 依赖商店分发和历史用户数据。

Profile 本身不保存机器码，它保存的是类和方法的选择信息。真正生成机器码的是 ART 编译链路中的 dex2oat。

四、Baseline Profile 与 Startup Profile

Profile主要使用者优化对象主要收益
Baseline ProfileART / dexopt哪些类和方法进行 AOT 编译减少解释执行和 JIT 预热
Startup ProfileR8 / D8启动代码在 DEX 中的排列提高代码局部性，减少启动阶段的缺页和随机读取

Baseline Profile 决定“哪些代码提前编译”，Startup Profile 决定“启动代码在 DEX 中如何排列”。两者并不冲突，可以同时使用。

五、热点清单如何变成二进制 Profile

开发者维护的是“哪些类和方法值得优化”，设备消费的是与具体 DEX 匹配的二进制 Profile，不是提前生成的机器码。

text
测试设备执行启动、页面进入等关键场景
    │ ART 自动记录运行信息，采集工具导出 Profile
    ▼
运行 Profile + 同一构建的 APK / split APK + 混淆 mapping
    │ 解析类、方法，必要时还原混淆名称
    ▼
可读热点清单（Human-readable Profile，HRP）
    │ 随源码维护；场景、代码变化时更新
    │
    ├── 新版本最终 DEX（完成混淆、拆分、代码改写）
    └── 新版本 mapping
    ▼
构建工具重新匹配 DEX 中的类 / 方法索引及校验信息
    ▼
二进制 baseline.prof → 随包发布 → 设备侧 dex2oat

标准 Baseline Profile 工具链可以自动化采集与生成；自定义 Dynamic Feature（DF，动态功能模块）方案需要在采集和构建阶段接入脚本或插件。业务代码不需要逐个方法手动上报热点。可读清单可以跨版本复用，但不能直接把旧版本二进制 Profile 塞进新 APK：它必须匹配最终 DEX。

H / S / P 标记的含义

text
Lcom/example/editor/EditorActivity;
HSPLcom/example/editor/EditorActivity;->onCreate(Landroid/os/Bundle;)V
HLcom/example/editor/FilterEngine;->applyFilter(I)V

第一行是类规则，后两行是方法规则；方法名前的字母描述执行特征。

标记含义用途与边界
H：Hot方法被标记为热点speed-profile 选择 AOT 方法的重要依据
S：Startup方法在启动阶段执行提供启动路径信息；是否选入 AOT 还受 ART 版本、内存模式等策略影响
P：Post startup方法在启动之后执行提供启动后使用信息；仅有 P 不代表一定生成 AOT 机器码

三者是可组合的标记，不是三档优化级别。HSP 表示一个方法同时具备这些特征；S 也不等于构建期的 Startup Profile 文件。

例如 AOSP main 的 ShouldCompileBasedOnProfile() 先检查 H，非低内存模式下还会考虑 S，因此不能把规则简化成“只有 H 才编译”。后续仍有其他编译资格判断。源码：CompilerDriver

baseline.prof 内部保存什么

以应用 Profile 的 015 格式为例，它是 ART 自定义二进制格式，不是文本清单、JSON 或 OAT。不同版本格式可能不同。

text
baseline.prof
├── 文件头：magic = "pro\0"、version = "015\0"、分区数量
├── 分区表：类型、偏移、存储大小、解压后大小
├── DEX_FILES：DEX key、checksum、类 / 方法索引数量
├── CLASSES：需要记录的类索引
├── METHODS：方法索引、H/S/P 标记、可选 inline cache 信息
└── 其他可选分区

概念上的一条记录：
classes.dex + checksum → method_idx 123 → H | S
                              │
                              └── 结合对应 DEX 才能定位方法定义与字节码

实际格式使用索引、位图等紧凑表示，部分分区可以压缩；不是反复保存每个方法的完整签名。DEX 标识和 checksum 用于匹配代码，Profile 本身没有方法实现。源码：ProfileCompilationInfo

六、DF 的 Profile 如何在安装期生效

关键是让系统为实际安装的 split DEX 找到有效 Profile。只覆盖 base APK 的热点清单，不能保证 DF 内的代码也得到优化。

不同分发路径由谁读取

载体读取方与时机首次启动边界
安装时提供的 .dm（DEX metadata）安装 / dexopt 链路使用其中的 Profile安装策略允许时可在首次运行前编译
assets/dexopt/baseline.prof（按工具链需要配合 .profm）AndroidX ProfileInstaller 在 App 运行后安装本地 Profile；商店也可提取转换后在安装时分发仅靠 App 内 ProfileInstaller 写入，不等于这次首次启动已经完成 AOT
assets/art-profile/baseline.prof支持 embedded profile 的系统 ART 链路从 APK 提取能否安装期使用取决于系统版本、Profile 来源选择和编译策略

embedded profile 的完整链路

text
构建阶段
DF 热点清单 + 最终 split DEX + mapping
    → 生成与该 DEX 匹配的 baseline.prof
    → 放入 AAB 的 <模块>/assets/art-profile/baseline.prof
    → 完成打包、签名、发布
    → 分发生成的 split APK（DEX 与 Profile 在同一 APK 中）

设备安装该模块
    → 系统触发安装 dexopt
    → ART Service 选择可用 Profile 来源
    → 若采用 embedded profile：artd 提取 APK 内的 Profile 到临时 fd
    → profman 校验并按已安装 APK 重写 DEX location key
    → dex2oat 按有效 Profile 和编译策略生成本机产物
    → 后续加载该模块时使用可用 AOT 代码

这里的“注入”是签名前加入打包资源，不是运行时 Hook。系统已有可用 Profile 或外部 .dm 等来源时，不一定选择 APK 内嵌版本；放进 assets 也不等于强制执行 speed-profile。

版本边界：AOSP 后续将 embedded profile 的入口限制为 enableEmbeddedProfile && SdkLevel.isAtLeastV()，即配置允许且 Android 15 / API 35 及以上。不能因为 Android 14 的 ART 中已有相关代码，就认为它已启用；具体设备仍应核对实际系统实现。AOSP：限制 embedded profile 到 V+

按需下载的 DF 在首次安装主包时尚不存在，其编译发生在模块安装等后续时机。

工程验证要连起来看：最终 split 中是否包含正确 Profile、Profile 是否匹配 DEX、安装 dexopt 实际采用什么来源和 compiler filter、目标方法是否有可用编译代码，以及首次启动耗时是否改善。仅检查 .art 是否存在不足以证明方案生效。

七、.odex / .vdex / .art 如何加速运行

text
APK / split APK 中的 DEX + 有效 Profile + 编译策略
                         │
                      dex2oat
                         │
          ┌──────────────┼────────────────┐
          ▼              ▼                ▼
        .odex          .vdex            .art（可选）
     AOT 机器码     校验相关元数据      App Image
          │              │                │
          ▼              ▼                ▼
     执行已编译方法  复用有效校验结果   复用部分运行时对象表示
          └──────────────┴────────────────┘
                         ▼
                  ART 加载并使用产物
产物主要内容加速的环节
.odex通常是 ELF/OAT 格式，包含已编译方法的机器码及相关元数据对可用的已编译方法，直接执行机器码，减少解释执行与 JIT 预热
.vdexDEX 校验相关元数据；部分版本或配置还包含 DEX依赖等条件仍有效时复用校验工作，减少重复处理
.art可选 App Image，保存部分字符串、类等 ART 内部对象表示加载、映射并接入运行时后，减少部分对象准备工作

三者是互补产物，不是 .odex → .vdex → .art 的顺序转换，也不与 H/S/P 一一对应。扩展名、内容和是否生成会随 Android 版本及配置变化。AOSP：ART 产物说明

.art 不是整个 App 的运行快照，不保存任意登录状态或 Activity 状态，也不是安装时执行业务 onCreate() 后存档。.odex 文件存在同样不代表所有目标方法已编译，仍需确认实际编译策略与内容。

JIT 的机器码则通常在当前进程的内存 Code Cache 中；落盘的热点 Profile 是后续 AOT 的输入，不是把 JIT Code Cache 原样保存成 .odex。普通应用分发 Profile，由设备生成与其指令集和 ART 环境匹配的产物，不宜直接跨设备下发 .odex/.art/.vdex。

八、为什么不对所有 DEX 做全量 AOT

全量 AOT 会让安装和系统升级时编译更久、占用更多磁盘，并为大量低频代码付出没有收益的编译成本。Profile-guided AOT 只提前编译启动和热点代码，运行中新热点交给 JIT，低频冷代码继续由解释器执行。

因此常见的 speed-profile 策略，是在启动速度、运行性能、安装时间和磁盘空间之间做折中。

九、GC 与编译链路的边界

ART 内部链路主要环节
代码执行DEX 加载与校验、Interpreter、JIT、Profile、AOT / dex2oat
Java 堆管理对象分配、GC Roots、标记、回收或整理、暂停与并发阶段

GC 不参与方法选择 Interpreter、JIT 还是 AOT。它影响启动速度，是因为 Application、Activity、依赖注入、反射和 View 创建可能在短时间内产生大量对象：

主图右下角展示了这条链路：大量对象分配使 Java 堆快速增长，达到条件后触发 GC；GC 的并发工作会竞争 CPU，必要的线程暂停则可能直接影响首帧。

所以启动优化需要分别观察：启动路径的代码有没有得到正确编译，以及启动阶段是否存在不必要的对象分配和 GC。

十、与 App 启动速度的关系

完整的 App 启动还包括 Zygote fork 与进程 attach、Application / Provider / Activity 初始化、文件与网络 I/O，以及首帧 measure / layout / draw / 上屏。

ART 主要影响类加载、代码执行和 Java 堆管理，不等于完整的 App 启动链路。即使关键方法已经 AOT，主线程 I/O、复杂初始化或首帧渲染仍然可能拖慢启动。

Application、Provider、配置存储、启动任务和 SO 准备等进程内关键路径见 应用启动优化。

十一、源码阅读主线

Android 14 及以后，设备侧 dexopt 主要由 ART Service 协调；Android 13 及以前主要由 Package Manager 相关流程协调。具体源码分析时需要先确定 Android 版本。
