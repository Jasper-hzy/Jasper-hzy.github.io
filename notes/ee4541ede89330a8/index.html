WindowManagerService 窗口管理流程

WindowManagerService，简称 WMS，是 system_server 里的窗口管理服务。它决定屏幕上有哪些窗口、谁在上层、谁有焦点、输入事件发给谁，并通过 SurfaceControl 控制对应图层。它不负责执行业务 View 的 draw()，也不负责最终像素合成。

一句话定位：

示意
ATMS 决定 Activity 能不能启动、放哪个 Task；
WMS 决定这个窗口怎么显示、层级、焦点、输入给谁；
SurfaceFlinger 决定各层 buffer 怎么合成上屏。

先区分 Activity、Window 与 Layer

WMS 关注的核心信息

WMS 不持有 App 的真实 View，它维护的是每个窗口的系统侧记录。

对象作用
WindowToken窗口归属令牌，标识窗口属于哪个 Activity 或系统实体
WindowState一个具体窗口在 WMS 里的运行时记录
DisplayContent一块 Display 上的窗口树
RootWindowContainer所有 Display 和窗口容器的根
SurfaceControl控制 SurfaceFlinger 图层的句柄
InputChannel窗口和输入系统之间的事件通道

需要重点掌握的几类状态：

  • 窗口层级（z-order）：由窗口类型和层级规则决定，系统窗口通常在应用窗口之上，最终反映到 Layer 顺序。

  • 焦点窗口：决定按键和输入法目标；touch 更多按可触摸区域命中窗口，key/IME 更依赖焦点窗口。

  • 可见性：窗口是否显示由 WMS 记录并通过 SurfaceControl 同步给图层。

  • 输入目标：InputDispatcher 依赖 WMS 的窗口信息决定事件发给哪个窗口。

Activity / Window / Layer 三个维度

窗口相关其实有三个独立维护、需要互相同步的维度。

维度负责什么归属服务唯一标识
Activity / Task任务栈、返回关系、生命周期、前后台ATMSActivityRecord + token(IBinder)
Window窗口秩序、层级、焦点、输入目标WMSWindowState（关联 IWindow）
Layer图层合成顺序、上屏SurfaceFlingerLayer（外部用 SurfaceControl 寻址）

三者不是严格一一对应：

  • 一个 Activity 可能有多个窗口：主窗口、Dialog、PopupWindow。

  • 很多窗口不属于任何 Activity：状态栏、导航栏、输入法、壁纸、Toast、悬浮窗。

  • 一个窗口可能对应一个或多个 SurfaceControl / Layer。

关联方式

示意
ActivityRecord(ATMS)
   │ token: IBinder
   ▼
WindowToken / WindowState(WMS)
   │ SurfaceControl
   ▼
Layer(SurfaceFlinger)

  • ATMS 启动 Activity 时创建 ActivityRecord 并生成 token；addToDisplay 时带上 token，WMS 据此把窗口挂到对应 Activity。

  • WMS 的 WindowState 持有 SurfaceControl，指向 SurfaceFlinger 中唯一的 Layer。

  • 用 token 而不是直接传 Activity 对象，是因为跨进程隔离：Activity 在 App 进程，WindowState 在 system_server，只能用 Binder token 作为身份凭证。这也解释了用非 Activity 的 Context addView 会报 token 错误。

通信通道

示意
App ↔ ATMS：IActivityTaskManager / IApplicationThread
App ↔ WMS：IWindowSession（App→WMS）/ IWindow（WMS→App）
WMS → SurfaceFlinger：SurfaceControl 事务（图层属性）
App → SurfaceFlinger：Surface / BufferQueue（像素）

为什么要分三个维度

把 Activity/Window/Layer 拆开，是被多进程窗口系统的约束逼出来的，不是为了复杂。

  1. 屏幕是多进程共享的：状态栏、输入法、其他 App 的悬浮窗都在同一块屏幕上，窗口秩序必须由系统统一仲裁，不能让某个 App 自己决定。

  2. 窗口不等于 Activity：很多窗口没有对应 Activity，需要独立建模。

  3. 进程隔离与稳定性：Activity 在 App 进程，会崩溃会被杀；窗口秩序、焦点、输入目标必须放在 system_server，避免一个 App 影响全局。

  4. 合成是独立系统：SurfaceFlinger 面对所有 App 的图层，按统一 z-order 和 VSYNC 合成，不可能塞进单个 Activity。

因此三个维度只能各自在责任进程里维护权威状态，靠 token 和 SurfaceControl 关联，靠 Binder 和事务同步。代价是可能短暂不一致，换来的是多应用共享、进程隔离、系统窗口统一管理和灵活显示能力（多屏、分屏、画中画等）。

窗口从创建到显示的流程

Activity resume 后，App 侧发起添加窗口，最终由 WMS 登记并接入图形系统。

示意
Activity -> PhoneWindow -> DecorView
  -> WindowManager.addView
  -> WindowManagerGlobal.addView
  -> new ViewRootImpl
  -> ViewRootImpl.setView
  -> IWindowSession.addToDisplay
  -> WMS.addWindow            // 登记窗口
  -> ViewRootImpl.relayout
  -> IWindowSession.relayout
  -> WMS.relayoutWindow       // 分配 Surface
  -> measure / layout / draw
  -> Surface.queueBuffer
  -> SurfaceFlinger 合成上屏

几个关键分界：

  • addWindow 只是登记窗口，创建 WindowState，还没有可绘制 Surface。

  • relayout 才通过 SurfaceControl 给窗口分配 Surface，App 拿到后才能绘制。

  • WMS 管窗口属性和层级，SurfaceFlinger 负责把各层 buffer 合成输出。

ViewRootImpl 是窗口在 App 侧的客户端，WMS 是窗口在系统侧的管理者，二者通过 IWindowSession（App→WMS）和 IWindow（WMS→App）通信。

用状态不一致定位显示问题

因为三个维度靠同步保持一致，一旦某个维度状态没更新到，就会出现“看起来矛盾”的现象。

典型案例：Dialog 残留。

示意
现象：dialog.hide() 后切后台再回前台，Dialog 窗口又显示在前台

原因链：

  • hide() 通常只改内容可见性，不一定移除窗口；dismiss() 才会走 removeView -> WMS.removeWindow。

  • 从 Window 维度看，窗口（WindowState）还在，可见性记录仍是“可见”。

  • 切后台再回前台时，系统按窗口维度的“可见”状态重新显示，于是 Dialog 又出现。

本质：Window 维度和 Activity 前后台没对齐，是状态同步问题，不是分层设计问题。

dumpsys 排查

把三个维度分别 dump 出来对比：

示意
adb shell dumpsys activity activities   # Activity / Task 前后台
adb shell dumpsys window windows        # 窗口列表、层级、可见性、焦点
adb shell dumpsys SurfaceFlinger        # Layer 和合成

排查思路：

  1. dumpsys window 看该 Dialog 的 WindowState 是否还在，visibility 是什么。

  2. 窗口仍在且可见，说明是 hide 未 remove 或可见性没同步。

  3. 对比 Activity 前后台状态与窗口可见性是否一致。

  4. 必要时看 SurfaceFlinger 里对应 Layer 是否还在合成。

修复方向：该销毁就 dismiss；让依附窗口的生命周期跟随宿主 Activity；避免在错误的生命周期时机操作窗口。

结论

  1. WMS 是系统侧窗口管理者，App 侧窗口客户端是 ViewRootImpl，二者通过 IWindowSession / IWindow 通信。

  2. addWindow 登记窗口，relayout 才分配 Surface；WMS 管窗口秩序，SurfaceFlinger 管合成。

  3. Activity / Window / Layer 是三个独立维度，靠 token 和 SurfaceControl 关联，不是一一对应。

  4. 分三维度是多进程窗口系统的必然选择：屏幕共享、窗口非 Activity 独有、进程隔离、独立合成。

  5. 三维度靠同步保持一致，Dialog 残留等问题多是某个维度状态没同步，用 dumpsys 三件套对比排查。
