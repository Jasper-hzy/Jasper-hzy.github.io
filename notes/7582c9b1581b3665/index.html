这篇文档回答一个问题：Android 本地 App 的一帧，是怎么从业务代码里的刷新请求，变成最终屏幕上的像素的。

云游戏场景会复用这套图形系统，但它的链路更长：远端游戏先完成 Android 原生渲染，再被抓屏、编码、传输、解码并在客户端上屏。云游戏相关内容放在 Android 容器抓屏实现 中，这里先讲 Android 系统自己的渲染主链路。

一帧的整体流程

示意
业务触发刷新
  -> View.invalidate / requestLayout
  -> ViewRootImpl 安排 traversal
  -> Choreographer 等待下一次 VSYNC
  -> doTraversal
  -> measure / layout / draw
  -> 硬件加速下更新 RenderNode
  -> RenderThread 执行渲染命令
  -> Buffer 入队到 Surface
  -> SurfaceFlinger 合成各 Layer
  -> HWC / GPU 输出到屏幕

核心理解是：应用并不是直接把内容画到屏幕上。应用侧只负责在自己的 Surface 对应的缓冲区里生产一帧，系统侧的 SurfaceFlinger 再把多个窗口、SurfaceView、状态栏、导航栏等 Layer 合成为最终画面。

刷新请求与帧调度

触发刷新：invalidate 和 requestLayout

常见刷新入口有两类：

  1. invalidate()：当前 View 内容变了，需要重新绘制。

  2. requestLayout()：尺寸或位置可能变了，需要重新测量和布局。

这两个入口最后都会沿着 View 树向上通知到 ViewRootImpl。ViewRootImpl 不会立刻执行完整绘制，而是通过 scheduleTraversals() 把本次 traversal 安排到下一次合适的帧节奏里。

这里的关键点是：UI 刷新受 VSYNC 节奏约束。业务频繁调用 invalidate() 不等于屏幕会无限刷新，系统会在一帧周期内合并刷新请求。

Choreographer：把刷新对齐到 VSYNC

Choreographer 负责接收 VSYNC 信号，并在一帧里按顺序执行输入、动画、布局绘制等回调。

一次典型的帧回调里，会处理几类任务：

  1. 输入事件：优先处理用户触摸、按键等输入。

  2. 动画：推进属性动画、补间动画等基于帧的状态变化。

  3. traversal：执行 ViewRootImpl#doTraversal()，完成测量、布局、绘制。

  4. commit：提交本帧后置任务。

如果主线程在 VSYNC 到来时还在执行耗时业务逻辑，doFrame 就会延迟。延迟超过一个刷新周期后，用户看到的就是掉帧或卡顿。

从 View 树到图形缓冲

ViewRootImpl：从 DecorView 到 RenderNode

ViewRootImpl#doTraversal() 是 View 系统进入绘制主流程的入口，内部大致分为三步：

  1. performMeasure()：从根 View 开始测量每个 View 的尺寸。

  2. performLayout()：确定每个 View 在父容器中的位置。

  3. performDraw()：遍历 View 树，生成绘制结果。

软件绘制和硬件加速的区别在这里会开始变明显：

  • 软件绘制：主线程通过 Canvas 直接执行绘制逻辑，CPU 参与更多。

  • 硬件加速：View 的绘制命令会记录为 RenderNode，后续由渲染线程消费，最终通过 OpenGL/Vulkan 写入图形缓冲区。

所以“View 的 draw 执行了”并不等于“屏幕已经显示了”。它只是把这一帧的绘制命令或绘制结果提交到了后续图形链路。

RenderThread：把 UI 绘制命令变成图形缓冲

开启硬件加速后，主线程主要负责 View 树遍历和绘制命令记录，RenderThread 负责执行这些命令。

这能减少主线程直接做图形工作的压力，但不代表主线程就不重要。主线程如果被业务逻辑、布局计算、频繁刷新阻塞，RenderThread 拿不到新的绘制命令，同样会掉帧。

这里可以把一帧拆成两个阶段看：

  1. UI 线程阶段：输入、动画、测量、布局、记录绘制命令。

  2. 渲染线程阶段：执行绘制命令，把结果写入 buffer。

缓冲提交与系统合成

Surface：应用和系统合成的边界

Surface 可以理解为应用向系统提交画面的出口。应用绘制完成后，会把一块 GraphicBuffer 入队给对应的 Surface。

几个容易混淆的概念：

  • Window：应用侧描述窗口能力的抽象。

  • DecorView：应用窗口里 View 树的根节点。

  • ViewRootImpl：连接 View 树和窗口系统，负责调度 traversal。

  • Surface：承载像素缓冲的生产消费边界。

  • Layer：SurfaceFlinger 侧参与合成的图层。

普通 Activity 窗口、SurfaceView、TextureView 都会进入图形系统，但它们的合成方式和 View 树的关系不同。SurfaceView 通常有独立 Surface，适合视频、相机、游戏这类高频画面；TextureView 更像 View 树的一部分，便于变换和动画，但可能多一次纹理合成成本。

更详细的 Surface / BufferQueue / SurfaceFlinger 关系见 Android 渲染上屏流程。

SurfaceFlinger：合成最终屏幕画面

SurfaceFlinger 是系统合成服务。它从各个 Layer 拿到最新 buffer，根据窗口层级、裁剪、透明度、旋转、缩放等信息，决定每个 Layer 如何出现在最终屏幕上。

合成方式通常有两类：

  1. HWC 合成：交给硬件合成器处理，功耗和性能更好。

  2. GPU 合成：复杂变换或硬件不支持时，由 GPU 合成。

最终合成结果会提交给显示设备。对应用来说，这意味着：即使应用侧已经完成绘制，如果 SurfaceFlinger 合成、HWC 提交或显示链路发生排队，也会影响最终上屏时间。

延迟来源与卡顿定位

三缓冲和延迟

Android 图形链路常见生产者-消费者模型：

示意
App / RenderThread 生产 buffer
  -> BufferQueue
  -> SurfaceFlinger 消费 buffer
  -> 显示设备扫描输出

双缓冲时，如果消费者还没释放上一块 buffer，生产者可能阻塞。三缓冲可以降低阻塞概率，让生产和消费更平滑，但代价是链路里可能多排队一帧。

这也是为什么云游戏这类实时场景会非常关心“多一次 buffer、多一次 SurfaceTexture、多等一个 VSYNC”。普通 UI 更关心稳定帧率，云游戏还要同时压低端到端操作延迟。

卡顿通常卡在哪里

从这条链路看，卡顿不一定只发生在 draw：

  1. 主线程消息太重：输入、动画、traversal 没法按时执行。

  2. 布局层级复杂：measure/layout/draw 耗时过长。

  3. 频繁刷新：短时间内大量无效 invalidate() 造成帧压力。

  4. GPU 负载高：RenderThread 执行绘制命令或纹理处理过慢。

  5. Buffer 排队：生产和消费节奏不匹配，出现等待。

  6. SurfaceFlinger/HWC 合成压力高：多 Layer、复杂裁剪、透明混合或缩放导致合成耗时。

常用观测手段可以结合 卡顿与丢帧排查：

  • adb shell dumpsys gfxinfo <包名>：看每帧 UI 线程、RenderThread、GPU 等阶段耗时。

  • FrameMetrics：在线上或实验环境采集窗口级帧耗时。

  • Choreographer 回调：统计 FPS、掉帧和主线程帧调度延迟。

  • Systrace / Perfetto：分析 VSYNC、traversal、RenderThread、SurfaceFlinger、HWC 的跨进程链路。

云游戏中的链路复用

云游戏里的“渲染”至少包含两段 Android 图形链路：

  1. 远端 Android 容器内，游戏 App 渲染到 Surface，再由 SurfaceFlinger 合成或输出给抓屏链路。

  2. 客户端收到视频帧后，MediaCodec 解码输出到 SurfaceTexture 或 Surface，再由本机 SurfaceFlinger 合成上屏。

因此云游戏优化里常见的 OES、YUV、VirtualDisplay、SurfaceTexture、编码 Surface、渲染直通，本质上都是在调整这条图形链路中的 buffer 流转方式。优化目标不是“让 View 少画一点”，而是减少格式转换、内存拷贝、串行阻塞和额外合成。
