AI 与大模型

AI 工程分层与面试回答

这篇文档用于沉淀面试中关于 AI 使用、AI Agent、研发自动化流程和传统开发经验迁移的回答框架。目标不是背工具名，而是能系统说明：AI 如何进入真实工程流程，人和 Agent 如何分工，以及传统开发经验为什么仍然重要。

1. 为什么关注 AI Agent

可以从“传统场景的新落地”和“工作模式变化”两个角度回答。

面试回答：

我关注 AI Agent / 大模型应用方向，主要是因为它已经不只是一个问答工具，而是开始和很多传统软件场景结合，产生新的工程落地方式。比如研发提效、代码理解、自动化测试、知识库问答、故障排查、业务流程自动化，这些场景过去都需要大量人工检索、判断和执行，现在可以通过 Agent 把一部分标准化流程自动化起来。

我觉得 AI Agent 带来的变化，不是 AI 直接替代工程师，而是人和 AI 的分工变化。以前很多工作需要人手动完成每个步骤；以后更像是人定义目标、提供上下文、设置约束和验收标准，AI Agent 执行其中可标准化、可验证的任务。人仍然负责关键判断、结果验证，以及复杂工作流的协作和编排。

可以压缩成一句话：

人从手动完成所有步骤，逐渐转向定义目标、上下文、约束和验收标准；AI Agent 执行可标准化、可验证的任务；人负责判断、验证和复杂工作流编排。

2. 传统开发经验在 AI 方向的价值

AI 应用开发不是简单调用大模型 API，而是把模型作为一个能力组件接入真实工程系统。传统开发经验的价值在于：能判断 AI 输出是否符合业务逻辑、系统边界、代码规范、稳定性要求和线上风险。

面试回答：

传统开发经验在 AI Agent 方向很重要，因为 Agent 不是单纯模型问题，而是工程系统问题。它需要接入代码仓库、文档、任务系统、CI、日志平台，还要处理权限、状态、重试、验证和人工确认。传统开发背景能帮助我把 Agent 从 demo 做成可控、可验证、可维护的系统。

可以展开为几个能力：

  • 需求拆解：把模糊需求拆成可执行、可验证的子任务。

  • 系统设计：把 LLM、RAG、工具调用、状态管理和业务系统组合起来。

  • 质量判断：判断 AI 生成内容是否符合真实工程约束。

  • 风险控制：识别权限、线上影响、发布、数据安全等边界。

  • 验证闭环：通过测试、CI、日志、监控和人工 review 验证结果。

3. AI 工程分层

这是一套用于面试表达的工程分层，不是严格行业标准。它的价值是帮助说明 AI 应用从“会问答”到“能进入研发流程”的能力演进。

层级核心问题典型内容
Prompt Engineering如何让模型按稳定方式理解任务和输出角色、目标、约束、输出格式、拒答条件
Context Engineering给模型什么上下文才有资格回答源码、日志、文档、业务背景、历史记录、证据排序
Memory Engineering如何复用跨任务和跨项目经验用户偏好、项目约定、历史排障、稳定知识与过期信息区分
Tool EngineeringAI 如何连接真实工程系统文件、Shell、Git、CI、Issue、文档、监控、MCP/API
Agent Harness单个 Agent 如何可靠执行任务工具调用、沙箱权限、状态、日志、重试、验证、人工介入
Lead Agent谁来理解需求、拆任务和汇总结果需求理解、任务拆解、worker 分派、风险判断、结果收敛
Workflow Orchestration多个任务/Agent/系统如何协作完成需求Issue 到 PR、Review Gate、CI、状态回写、文档沉淀
Governance团队如何长期、安全、可控地使用 AI质量指标、权限、成本、审计、安全、责任边界

面试里可以这样解释：

底层是 prompt 和 context，让模型理解任务；再往上是 memory 和 tool calling，让它能复用经验并操作真实系统；然后是 agent harness，保证单个 Agent 可控执行、可验证、可恢复；再往上是 lead agent 和 workflow orchestration，把需求、任务拆解、Agent 执行、CI、review 和状态回写串成研发闭环。团队级还需要 governance，保证质量、安全、权限、成本和审计可控。

4. Agent Harness、Lead Agent 和 Workflow Orchestration 的区别

这三个概念容易混淆，可以按关注对象区分。

概念关注对象关键问题
Agent Harness单个 Agent / 单项任务的一次执行能不能安全、可靠、可验证地完成任务
Lead Agent多个子任务之间的智能协调角色需求怎么拆、任务怎么派、结果怎么收敛
Workflow Orchestration一个需求下的多任务、多系统协作Issue、Agent、CI、PR、Review、状态回写如何串起来

一句话：

Harness 保证一个 Agent 把一件事做好；Lead Agent 决定多件事怎么拆、怎么派、怎么收敛；Workflow Orchestrator 把 Lead Agent、Worker Agent、CI、PR、Issue 和人工 Review 串成完整研发闭环。

Agent Harness 包含什么

Agent Harness 可以理解成单个 Agent 的运行底座，常见模块包括：

  • 任务契约：目标、输入、约束、验收标准、禁止事项。

  • Agent Loop：plan、act、observe、evaluate、revise、stop。

  • Prompt 策略：系统角色、输出格式、安全边界、工程规范。

  • Context Builder：选择、压缩、排序当前任务所需上下文。

  • Memory Access：接入项目经验、用户偏好、历史任务，但不把历史记忆当当前事实。

  • Tool Registry / Executor：注册并安全执行文件、Shell、Git、CI、文档、监控等工具。

  • Sandbox & Permission：控制读写、网络、删除、push、发布等权限。

  • State Management：记录计划、进展、失败、修改文件和未完成事项。

  • Runtime Evaluation：判断测试是否通过、diff 是否符合需求、是否需要人工介入。

  • Retry & Recovery：失败后读取错误、调整方案、重试或报告 blocker。

  • Observability：记录工具调用、命令输出、文件变更、测试结果和决策依据。

  • Human-in-the-loop：在需求不清、风险较高或涉及外部写操作时停下来让人确认。

5. 面试常见问法与回答模板

问题：你为什么关注 AI Agent / 大模型应用方向？

回答重点：不要只说“AI 火”，要说传统场景结合 Agent 后产生新的工程落地，并且工作模式会变化。

参考回答：

我关注这个方向，是因为 AI Agent 正在从问答工具变成工程协作能力。很多传统研发场景，比如代码理解、自动化测试、知识库问答、故障排查、流程自动化，都可以借助 Agent 把一部分标准化、可验证的步骤自动化起来。我认为未来工作模式会变成：人定义目标、上下文、约束和验收标准，AI Agent 执行其中可拆解的任务，人负责关键判断、验证和复杂工作流编排。

问题：传统开发经验在 AI 方向有什么价值？

回答重点：强调 AI 系统仍然是工程系统，传统开发负责判断、接入、验证和风险控制。

参考回答：

传统开发经验非常重要，因为 AI 产出不是天然可靠的。真正落地时，需要判断它是否符合业务逻辑、系统边界、代码规范、性能稳定性和线上风险。AI Agent 也需要接入代码仓库、CI、日志、文档、任务系统，并处理权限、状态、重试、验证和人工确认。这些都是传统工程经验能发挥价值的地方。

问题：Agent 和普通 Chatbot 有什么区别？

回答重点：Agent 不是一次问答，而是“模型 + 工具 + 状态 + 反馈循环”。

参考回答：

普通 Chatbot 主要是一次输入输出，回答问题为主。Agent 则是有状态的多步骤执行系统，它可以根据目标规划步骤、调用工具、观察结果、修正计划，并在满足验收标准或遇到风险时停止。所以 Agent 更接近一个能操作真实系统的工程执行者，而不是单纯聊天助手。

问题：你怎么理解 AI 研发自动化流程？

回答重点：不要说 AI 自动完成一切，而是强调可标准化部分自动化，人负责关键 gate。

参考回答：

我理解 AI 研发自动化不是让 AI 绕过工程流程，而是把需求到交付里可标准化、可验证、可记录的部分交给 Agent 加速。比如需求进入 Issue 后，Lead Agent 可以做上下文收集和任务拆解，Coding Agent 做局部实现，Test Agent 补测试，Review Agent 做风险检查，最后通过人工 Review、CI 和状态回写形成闭环。人仍然负责需求判断、架构取舍、风险控制和最终验收。

6. 结合简历怎么讲 AI 工作流帮助

简历里可以承接这条经历：

参与 AI 研发工作流建设，将组件版本发布、宿主集成构建、代码合入等重复性流程抽象为可复用的 Agent Skill，结合工具调用、流程编排、状态回读与结果校验，实现研发流程自动化。

面试时不要只讲“我写了几个脚本”或“让 AI 帮我发版”，而是讲清楚：我们把原本分散、重复、容易漏步骤的研发操作，抽象成可复用、可验证、可追踪的 AI 工作流。

我们具体做了什么

可以按四层来讲：

  1. 抽象重复流程

    把组件版本发布、宿主集成构建、代码合入这类高频研发动作，从一次次手工操作抽象成稳定流程。每类流程都明确输入、执行步骤、依赖系统、产物输出和验收条件。

  2. 封装 Agent Skill

    将具体流程沉淀成可复用 Skill，而不是临时 prompt 或一次性脚本。Skill 里包含任务边界、工具调用方式、关键参数、执行顺序和结果判断规则，让 Agent 在相似任务里可以复用同一套工作方式。

  3. 接入工具调用和流程编排

    Agent 不只是生成文字，而是能调用真实工程工具，串联版本查询、分支或 MR 信息、构建任务、产物地址、任务状态等环节。对于异步构建和发布类任务，需要持续读取状态，而不是只触发一次命令就结束。

  4. 做状态回读和结果校验

    这类流程的关键不是“触发成功”，而是确认最终结果真的完成。比如构建是否结束、产物是否存在、MR 状态是否符合预期、版本或依赖是否已更新。Agent 输出结论前必须有回读证据，不能只根据工具调用成功就判断完成。

AI 工作流带来的帮助

这段经历可以强调三个价值。

  • 降低重复操作成本：把发布、构建、合入前检查等重复步骤交给 Agent 编排，减少人工在多个平台之间切换和复制信息。

  • 降低流程遗漏风险：通过 Skill 固化执行顺序、必要参数、状态检查和验收条件，减少漏跑构建、漏看产物、漏确认状态这类问题。

  • 提升交付闭环质量：Agent 不只执行动作，还负责回读状态、整理结果、暴露失败原因和下一步处理建议，让研发流程从“人工记忆驱动”变成“流程和证据驱动”。

人和 AI 的分工

这段回答要把边界讲清楚。AI 负责可标准化、可验证、可重复的流程执行；人负责目标定义、风险判断和关键确认。

可以这样表达：

在这类 AI 工作流里，我不会把 AI 定位成完全自动替人发版或合代码，而是把它定位成研发流程执行助手。它适合处理重复、规则明确、结果可回读的环节，比如查版本、触发构建、读取 Job 状态、整理产物、检查 MR 状态。人负责定义目标、确认范围、判断风险，以及在发布、合入、失败重试这类关键节点做最终决策。

面试回答模板

如果面试官问“你们 AI 工作流具体做了什么”，可以回答：

我们主要做的是把一些重复但容易漏步骤的研发流程，抽象成可复用的 Agent Skill，比如组件版本发布、宿主集成构建、代码合入前后的检查。这里不是简单写脚本，而是把流程里的输入、工具调用、状态流转、产物回读和验收条件都固化下来。

比如构建类任务，Agent 不能只负责触发构建，还要持续读取任务状态，拿到产物或失败原因，再把结果整理出来。版本发布或代码合入类任务，也要确认当前分支、版本、MR 状态和必要校验结果，避免只执行动作但没有闭环。

这类 AI 工作流的价值主要是减少重复操作、降低流程遗漏，并把交付过程变成可追踪、可校验的证据链。人仍然负责目标定义、风险判断和关键节点确认，AI 负责标准化流程执行和结果整理。

Skill 如何持续优化

Skill 的优化不能只理解成“把 prompt 写得更好”，更像是对一个领域工作流做工程化迭代。可以围绕四个环节展开。

  1. 单独优化意图路由

    先把用户自然语言里的目标终点识别清楚。比如“打组件”“更新宿主依赖”“创建 MR”“基于 MR 打包”“查询构建结果”是不同意图，不能互相隐含。路由层要持续补充容易混淆的说法和边界规则，避免 Agent 把一个只需要查询或构建的请求扩展成写操作。

  2. 定制输入输出 Schema

    Skill 需要定义稳定的输入输出格式，而不是让 Agent 自由组织结果。输入侧要明确必填字段、可默认字段、枚举值、平台类型和高风险参数；输出侧要明确必须返回哪些交付物和状态，例如组件版本、Maven 可查询状态、Job/Pipeline 终态、MR URL、构建产物地址、失败阶段和错误原因。

  3. 基于规则做校验和匹配

    有了 Schema 之后，需要用规则验证输入输出是否符合预期。比如组件构建不能只校验“Job 已触发”，而要校验最终版本号存在，并能在 Maven 或组件仓库查到；APK 构建不能只校验 Pipeline 成功，而要拿到构建产物地址；MR 创建不能只校验接口返回成功，还要回读 source/target branch、author 和依赖版本。

  4. 构造测试集并持续评估

    可以基于真实历史请求和 AI 生成的变体构造测试集，覆盖正常说法、模糊说法、边界说法和容易误判的说法。然后用规则评估意图命中率、参数抽取准确率、输出 Schema 合规率、完成证据覆盖率和错误恢复表现。每次发现路由错误、字段缺失或完成标准不充分，就把它沉淀回 Skill 的路由规则、Schema、示例和校验逻辑里。

可以总结为一条优化闭环：

text
真实请求 / AI 生成变体
  ↓
意图路由测试
  ↓
输入参数 Schema 校验
  ↓
工具输出 Schema 校验
  ↓
完成证据规则匹配
  ↓
统计命中率和失败类型
  ↓
反向优化路由、Schema、示例和校验规则

面试回答可以这样说：

Skill 的优化不是只调 prompt，而是把它当成一个领域工作流系统来优化。首先要单独优化意图路由，确保用户说“打组件”“打包”“创建 MR”“查询状态”时能命中正确流程；其次要定义输入输出 Schema，避免 Agent 生成无法被下游工具消费的格式；然后基于规则做校验，比如组件构建必须拿到真实版本号并能在 Maven 查到，APK 构建必须拿到构建产物地址；最后可以用历史请求和 AI 生成的变体构造测试集，评估意图命中率、参数抽取准确率、Schema 合规率和完成证据覆盖率，再持续反哺路由规则和校验逻辑。

一句话：

Skill 优化的核心，是把自然语言任务变成可路由、可校验、可评估、可持续迭代的工程协议。

Skill 测试集怎么设计

如果面试官追问“怎么评估 Skill 有没有优化好”，可以从两个测试方向回答。

  1. 意图识别测试

    先明确这个 Skill 支持几个核心意图，以及每个意图的边界。以发布类 Skill 为例，至少要区分：查询状态、打组件、打 Demo、更新宿主依赖、创建 MR、基于 MR 打包、关闭 MR、删除分支等。测试集需要覆盖每个意图的常规说法、同义说法、模糊说法、组合说法和边界说法。

    评估重点是：用户请求是否路由到正确 intent，是否误触发写操作，是否把上游动作和下游动作错误合并。例如“打一个组件”不能命中创建 MR，“基于 MR 打包”不能重新创建 MR，“查一下构建结果”不能触发新构建。

  2. Schema 规范化输入输出测试

    每个意图都需要定义给处理器的中间输入规则，以及处理器返回后的最终输出规则。测试集不仅要看 Agent 是否识别出意图，还要看它抽取出的平台、分支、版本、MR ID、构建类型、是否需要等待终态等字段是否符合 Schema。

    输出侧则要验证最终交付物是否符合业务完成标准。比如打组件最终必须有组件版本号，并且能在 Maven 或组件仓库查到；打 APK 最终必须有构建产物地址或安装链接；创建 MR 必须回读到 MR URL、source branch、target branch、author 和依赖版本；失败场景必须返回失败阶段、关键错误和是否可重试。

可以把测试集设计成三层：

测试层验证对象示例指标
意图层自然语言是否命中正确 intent意图命中率、误路由率、高风险动作误触发率
输入层intent 对应的中间参数是否符合 Schema参数抽取准确率、必填字段缺失率、默认值披露率
输出层处理器结果是否满足业务完成标准Schema 合规率、完成证据覆盖率、产物可用率

面试回答可以这样说：

我会把 Skill 测试集分成两个主要方向：一类是意图识别测试，一类是 Schema 规范化输入输出测试。先明确这个 Skill 需要路由到哪些意图，比如查询、打组件、打包、创建 MR、更新依赖等，然后为每个意图构造正常表达、模糊表达、组合表达和边界表达，验证 intent 是否命中正确、有没有误触发写操作。接着看每个 intent 生成给处理器的中间输入是否符合 Schema，比如平台、分支、版本、MR ID、构建类型是否抽取正确。最后再验证处理器输出是否满足业务完成标准，比如打组件必须拿到组件版本并能在 Maven 查到，打 APK 必须拿到构建产物地址。这样就能用意图命中率、参数抽取准确率、Schema 合规率和完成证据覆盖率来持续优化 Skill。

业界常见的 Skill / Agent 优化思路

更完整地看，业务型 Skill 的优化可以借鉴现在 LLM 应用和 Agent 平台里常见的 eval-driven development 思路：先定义任务合同和评测标准，再基于真实 trace、离线测试集和线上反馈持续迭代。

  1. Eval-driven development

    不把 Skill 优化当成凭感觉调 prompt，而是先定义可量化指标。对发布类 Skill 来说，核心指标可以包括：意图命中率、参数抽取准确率、Schema 合规率、工具调用成功率、完成证据覆盖率、人工介入率、误触发高风险动作次数、端到端任务成功率、平均完成时间和成本。

  2. Golden set 与 synthetic set 结合

    测试集最好分两类：一类是从真实历史请求、失败案例、线上 trace 中沉淀出的 golden set；另一类是 AI 生成的 synthetic set，用来扩展同义表达、模糊表达、组合任务和异常输入。真实样本保证贴近业务，生成样本扩大覆盖面。

  3. Trace replay / 回放评测

    对 Agent 来说，只看最终回答不够，还要能回放完整执行轨迹。每次 Skill 调用都应记录用户输入、路由结果、抽取参数、工具调用、工具返回、状态回读、最终输出和人工介入点。优化后可以用历史 trace 回放，确认新版本没有破坏旧场景。

  4. Contract test / 工具协议测试

    Tool calling 的稳定性依赖协议。每个工具都要有输入输出契约测试：输入字段是否合法、枚举值是否正确、错误码是否稳定、异步句柄是否能继续查询、失败时是否返回可诊断信息。这样可以避免 Agent 本身没问题，但工具输出格式变了导致下游失效。

  5. Deterministic check + LLM judge 结合

    能用规则校验的地方优先用确定性校验，比如 JSON Schema、版本号格式、MR URL、构建产物地址、Maven 可查询、Job 终态。只有主观质量判断才考虑 LLM judge，例如总结是否完整、失败原因是否解释清楚。发布、构建、合入这类工程任务不能只依赖 LLM judge。

  6. Error taxonomy / 失败分类

    需要给失败建立分类，而不是只记录“失败”。常见分类包括：意图误路由、参数缺失、Schema 不合规、工具调用失败、平台任务失败、状态回读不足、完成标准缺失、权限阻塞、用户信息不足、Agent 越权尝试。分类越清楚，后续优化越容易定位到路由、Schema、工具、校验还是业务规则。

  7. Guardrail 与权限分级

    业务 Skill 要把动作分级：只读查询、低风险写入、高风险写入、不可自动执行动作。查询状态、读取产物可以自动化；创建 MR、修改依赖、触发构建需要明确意图；关闭 MR、删除分支、正式发布、合入代码必须有人工确认。这个维度通常和测试集一起验证，重点看高风险动作有没有被误触发。

  8. Online feedback / 线上反馈闭环

    离线测试只能覆盖已知样本，线上还要看真实使用效果。例如用户是否接受结果、是否要求重跑、是否手动纠正参数、是否因为结果不完整继续追问、是否需要人工介入。可以把这些反馈沉淀回测试集和规则库。

  9. Versioning / 灰度和回滚

    Skill、prompt、路由规则、Schema、工具协议和测试集都应该有版本概念。优化不能直接覆盖线上稳定流程，最好先在离线回放和小流量场景验证，通过后再扩大使用；如果误路由或误触发风险升高，需要能回滚到上一版。

可以把完整优化闭环总结成：

text
业务流程建模
  ↓
定义 intent / schema / completion criteria
  ↓
构造 golden set + synthetic set
  ↓
离线评测：路由、参数、Schema、完成证据
  ↓
Trace replay：验证旧场景不回退
  ↓
线上观测：成功率、人工介入、误触发、成本和耗时
  ↓
失败分类：定位路由 / Schema / 工具 / 校验 / 权限问题
  ↓
灰度发布并可回滚

面试回答可以这样升级：

更完整地看，我会用 eval-driven development 的方式优化 Skill。首先把业务流程建模成明确的 intent、Schema 和完成标准；然后用真实历史请求构造 golden set，再用 AI 生成同义、模糊、组合和边界表达扩充 synthetic set；离线评估意图命中率、参数抽取准确率、Schema 合规率和完成证据覆盖率；同时记录完整 trace，支持新版本回放旧任务，避免改 prompt 或规则后引入回归。线上再看任务成功率、人工介入率、误触发高风险动作、平均耗时和成本。每次失败都归类到路由、参数、工具、状态回读、权限或完成标准，再反向优化规则、Schema、示例和工具协议。

这套说法的重点是：

业务 Skill 优化不是只优化模型回答，而是优化“自然语言到业务交付物”的整条链路。
