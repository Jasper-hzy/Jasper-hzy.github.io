客户端开发/ Android/ 系统原理

Input 输入系统流程

输入系统负责把硬件输入事件送到正确的窗口，再由 App 分发到 View。它的核心组件跑在 system_server 的 native inputflinger 里，并依赖 WMS 提供窗口信息。本文按“时间线”组织：从初始化，到窗口通道建立、窗口秩序同步、事件派发、App 接收、对齐帧处理，最后到 finish 回执。

全链路总览

text
硬件中断 -> 触摸驱动 -> 内核 input 子系统 -> /dev/input/eventX
  -> EventHub(读原始事件)
  -> InputReader(加工成规范事件)
  -> InputDispatcher(按窗口/焦点选目标)
  -> InputChannel(socketpair 跨进程)
  -> App: InputConsumer -> InputEventReceiver -> ViewRootImpl
  -> Choreographer 对齐帧 -> DecorView/View.dispatchTouchEvent
  -> finishInputEvent 回执

两个进程边界：读事件、加工、派发在 system_server（native）；View 分发在 App 进程。WMS 也在 system_server，所以窗口信息是同进程同步给 InputDispatcher。

阶段 0：初始化（开机一次）

text
SystemServer.startOtherServices()
  -> new InputManagerService(context)     // Java 门面
  -> JNI 进入 native NativeInputManager
  -> 创建 EventHub / InputReader / InputDispatcher
  -> 启动 InputReaderThread / InputDispatcherThread

各组件职责：

  • EventHub：用 inotify 监听 /dev/input 设备增删，open 设备，用 epoll 等待可读，读出原始 input_event。

  • InputReader：把原始事件加工成规范的 MotionEvent / KeyEvent。

  • InputDispatcher：维护连接表和窗口快照，负责分发和超时判定。

注意分工：读设备的 epoll 在 EventHub（Reader 侧），InputDispatcher 只负责分发，不直接 epoll 驱动设备。

阶段 1：IMS 与 WMS 建立联系

WMS 启动后持有 IMS 引用，负责把窗口信息喂给 InputDispatcher。此时还没有应用窗口，窗口快照为空或只含系统窗口。

阶段 2：窗口创建时建立 InputChannel（每次 addWindow）

text
App: ViewRootImpl.setView
  -> IWindowSession.addToDisplay(...)
WMS:
  -> 创建一对 InputChannel(socketpair)，带 token
  -> server 端注册到 InputDispatcher：token -> Connection(socket)
  -> client 端回传给 App
App:
  -> ViewRootImpl 用 client InputChannel 构造 WindowInputEventReceiver
  -> native 把 channel fd 注册进主线程 Looper 的 epoll，创建 InputConsumer

关联关系（用 token 对齐，不互相持有对象）：

text
WindowState(WMS)          持有 InputChannel(token = T)
InputDispatcher           连接表 token T -> Connection(socket)
InputWindowHandle         描述窗口，内含 token T
App ViewRootImpl          持有 client 端 InputChannel

一个可接收输入的窗口对应一对 InputChannel；窗口销毁时注销通道、关闭 socket、释放 fd。

阶段 3：窗口秩序同步（窗口变化时，低频）

InputDispatcher 不自己算窗口秩序，它读 WMS 推送的窗口快照。触发同步的变化包括：

text
addWindow / removeWindow
窗口层级 z-order 变化
焦点窗口变化
可见性变化
位置/大小/可触摸区域变化
窗口 flags 变化(NOT_TOUCHABLE / NOT_FOCUSABLE 等)
display 变化(旋转/分屏/多屏)

WMS 在布局重算后生成 InputWindowHandle 列表并同步给 InputDispatcher，每个 handle 含 token、可触摸区域、z-order、焦点、flags、display。

为什么这样设计：输入事件高频、窗口变化低频，所以由 WMS 在变化时推送快照，派发时 InputDispatcher 只读本地快照，保证低延迟。

阶段 4：事件产生与派发（每个事件，高频）

text
硬件中断 -> 触摸驱动 input_report_* / input_sync
  -> 内核 input 子系统 -> evdev -> /dev/input/eventX
EventHub 读原始 input_event
InputReader 加工成规范事件(处理多点触控、坐标转换、按键映射)
InputDispatcher:
  touch：按坐标 + z-order 命中第一个可触摸且区域命中的窗口
  key/IME：发给焦点窗口
  -> 取目标窗口 token
  -> 连接表找到 Connection(socket)
  -> 直接写事件

触摸手势有序列绑定：DOWN 命中的窗口决定后续 MOVE/UP 都发给它，所以一个手势不会中途换窗口。

阶段 5：App 接收（每个事件，经 InputChannel）

text
socket 可读 -> 主线程 Looper 的 epoll 唤醒
  -> native InputConsumer.consume 从 InputChannel 读事件
  -> NativeInputEventReceiver
  -> InputEventReceiver.onInputEvent(绑定该窗口 InputChannel)
  -> ViewRootImpl.enqueueInputEvent(入 pending 队列)

这里不能省略 InputChannel：onInputEvent 的事件正是从该窗口 InputChannel 的 socket 读出来的，InputEventReceiver 是绑定在这个通道上的。

阶段 6：对齐帧处理（关键事件尽快，高频事件对齐 VSYNC）

text
DOWN / UP：通常尽快 doProcessInputEvents 处理，保证响应
MOVE(batched)：
  -> Choreographer.postCallback(CALLBACK_INPUT, consumeBatchedInput)
  -> VSYNC 到来 -> Choreographer.doFrame
  -> CALLBACK_INPUT 阶段消费 pending 输入
  -> InputStage 责任链
  -> DecorView/View.dispatchTouchEvent
同一帧后续: CALLBACK_ANIMATION -> CALLBACK_TRAVERSAL(measure/layout/draw)

关联点：socket 决定事件“何时到达”，Choreographer 决定事件“在哪一帧处理”。ViewRootImpl 的 pending 队列 + CALLBACK_INPUT 回调把两者串起来，让输入、动画、绘制对齐到同一帧，保证输入→状态→动画→绘制自洽。

主线程只有一个 Looper，同时承载普通 Message、Choreographer 帧回调、InputChannel 的 fd 唤醒。主线程被耗时任务卡住会同时导致输入延迟（ANR）和掉帧。

阶段 7：回执与 ANR（处理完）

text
处理完 -> finishInputEvent
  -> 通过同一 InputChannel 回执给 InputDispatcher
  -> Dispatcher 从 wait queue 移除该事件
未在超时内 finish -> input dispatching timeout ANR

这个“长连接 + 回执”模型既保证高频、低延迟、有序，也是 ANR 判定的基础。

时间线与频率总表

时机频率做了什么
初始化开机一次启动 EventHub / InputReader / InputDispatcher，EventHub epoll 监听设备
addWindow每次建窗口建 InputChannel+token，注册 Connection，App 侧 fd 入 Looper
窗口变化低频WMS 推送 InputWindowHandle 快照(token/region/层级/焦点)
事件派发高频Reader 加工，Dispatcher 命中窗口，token 找 socket 写事件
App 接收高频InputChannel -> InputConsumer -> onInputEvent -> 入队
对齐帧高频DOWN/UP 尽快，MOVE 走 Choreographer INPUT 回调对齐 VSYNC
回执每个事件finishInputEvent 回执，超时则 ANR

排查工具

text
adb shell getevent -lt /dev/input/eventX  # 驱动/evdev 层原始事件
adb shell dumpsys input                   # 设备、InputReader、Dispatcher、窗口/焦点、pending
adb shell dumpsys window                  # WMS 窗口层级/焦点/可触摸区域
/data/anr/traces.txt                      # input dispatching timeout 时主线程堆栈

关键结论

  1. InputReader / InputDispatcher 都在 system_server 的 native inputflinger，由 Java 层 IMS 通过 JNI 启动。

  2. 一个可接收输入的窗口对应一对 InputChannel，addWindow 时建立并以 token 注册到 InputDispatcher。

  3. 窗口秩序按“状态变化”由 WMS 推送快照，派发时 Dispatcher 只读本地快照，保证低延迟。

  4. 派发目标：touch 按坐标+层级命中窗口，key/IME 按焦点窗口；用 token 找 socket 直接写事件。

  5. App 侧经 InputChannel -> InputConsumer -> InputEventReceiver -> ViewRootImpl 入队，不能省略 InputChannel。

  6. socket 决定“何时到达”，Choreographer 决定“哪一帧处理”，两者用 pending 队列和 CALLBACK_INPUT 串联。

  7. finish 回执是背压和 input dispatching timeout ANR 判定的基础。
