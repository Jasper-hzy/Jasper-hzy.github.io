ABI 问题

ABI 是二进制层面的调用约定和对象布局约定。源码看起来兼容，不代表编译出来的二进制一定能互相调用。

常见症状

  • dlopen 成功但 dlsym 找不到入口。

  • Java/JNI 或 C 层按函数名查找失败。

  • 只有某些 ABI、机型或编译配置崩溃。

  • 跨动态库传递 std::string、std::vector、异常或 C++ 对象后崩溃。

  • 替换一个 .so 后，调用方没有改代码也开始异常。

常见原因

  1. C++ name mangling 导致导出的符号名不是预期的 C 风格名称。

    int add(int, int) 可能导出为类似 _Z3addii。外部如果通过 dlsym("add") 查找，就会失败。跨语言或插件入口通常应使用 extern "C"。

  2. 不同编译器、STL、编译选项或 NDK 版本导致对象布局和运行时行为不一致。

    稳定 ABI 边界不要直接传递 std::string、std::vector、C++ 异常、含虚函数的 C++ 对象，或由另一侧释放的 C++ 对象指针。

  3. 调用约定、结构体对齐或字段顺序不一致。

    跨语言结构体要固定字段类型、大小、对齐和版本号，避免依赖平台默认布局。

  4. 符号可见性被隐藏。

    编译参数可能默认隐藏符号，需要明确导出对外入口。

排查方法

  • 查看导出符号：nm -D libxxx.so、readelf -Ws libxxx.so。

  • 查看依赖库：readelf -d libxxx.so、ldd libxxx.so。

  • macOS/iOS 可用：nm -gU libxxx.dylib、otool -L libxxx.dylib。

  • 确认线上崩溃包对应的 Build ID、符号文件和实际加载的 .so 版本一致。

修复原则

  • 对外 ABI 尽量使用 C ABI：extern "C" + handle。

  • 跨库边界优先传递句柄、基础类型、固定布局结构体和明确长度的 buffer。

  • 谁申请谁释放，或提供成对释放函数，不让调用方猜释放方式。

  • 接口结构体带 size、version 字段，便于兼容扩展。

  • 不跨 ABI 边界抛 C++ 异常。
