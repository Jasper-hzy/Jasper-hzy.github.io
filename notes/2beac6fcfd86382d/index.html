Android 热更新

热更新是补丁级止血能力，不是常规业务发布系统。模块级动态加载见 Android 插件化。

一、实现原理

1. Java / Kotlin 代码热更新

Java / Kotlin 热更新主要修业务逻辑问题，例如空指针、条件判断、返回值、局部流程错误。常见两类方案：Dex 插入和方法插桩。

1.1 Dex 插入

Dex 插入的核心是修改宿主 BaseDexClassLoader 的查找顺序。Android 类加载器内部大致是：

text
PathClassLoader
  -> BaseDexClassLoader.pathList
     -> DexPathList.dexElements

类查找会按 dexElements 顺序遍历，所以补丁要插到宿主 dex 前面：

text
原始：dexElements = [host.apk classes.dex]
修复：dexElements = [patch.dex, host.apk classes.dex]

具体流程：

  1. 校验补丁包里的 dex 列表、md5、宿主版本。

  2. 对补丁 dex 做优化，准备 oat/odex 输出目录。

  3. 反射拿宿主 PathClassLoader.pathList。

  4. 通过 makePathElements / makeDexElements 生成 patch elements。

  5. 把 patch elements 插到宿主 dexElements 前面。

  6. 写回宿主 pathList.dexElements。

Tinker 主链路可以对应成：TinkerDexLoader.loadTinkerJars -> TinkerDexOptimizer.optimizeAll -> SystemClassLoaderAdder.installDexes -> 反射修改 dexElements。

伪代码：

java
ClassLoader hostLoader = context.getClassLoader();
DexClassLoader patchLoader = new DexClassLoader(
    patchDexPath, optimizedDir, null, hostLoader
);

Object hostPathList = getField(hostLoader, "pathList");
Object patchPathList = getField(patchLoader, "pathList");

Object[] hostElements = getField(hostPathList, "dexElements");
Object[] patchElements = getField(patchPathList, "dexElements");

Object[] newElements = concat(patchElements, hostElements);
setField(hostPathList, "dexElements", newElements);

能力边界：Dex 插入是类级别补丁，可以携带新类，也可以替换还没被加载的原有类，类内部新增 helper 方法也可以随补丁类一起下发。

限制：它不能可靠地对已经加载过的类动态生效，所以通常要求在冷启动早期加载补丁；字段结构、父类变化、方法签名变化、复杂 Kotlin inline/lambda/协程状态机也有风险。

1.2 Robust 方法插桩

编译期在方法入口插入 PatchProxy 判断，命中补丁时转发到补丁实现。抖音仓库里能看到 Robust / Frankie-Robust 相关依赖和符号。

能力边界：方法插桩可以在类已经加载后动态生效，因为原方法入口已经提前埋了代理判断。它适合修改现有已插桩方法内部逻辑。

限制：它不能新增类、字段或方法签名，也不适合改构造函数、静态初始化、继承关系。没有被插桩的方法入口也无法通过这套机制分发到补丁。

2. C++ / Native 热更新

Native 热更新主要修 so 里的 C++/JNI 逻辑。常见方式是下发新 so，并在下次启动或模块未加载前选择新路径加载。

已加载同名 so 不能在进程内可靠卸载替换。更复杂的方案会涉及自定义 loader、linker namespace、依赖 so 可见性和 ABI 兼容。

3. 资源热更新

资源热更新主要修图片、文案、部分 layout、drawable、style。核心是通过 AssetManager / Resources 接入补丁资源。

难点不在 add path，而在资源 ID、Theme、Configuration、DisplayMetrics、AppCompat/Tint 缓存一致性。

4. 补丁下发治理

标准链路：

配置 -> 下载 -> 签名/hash/版本/ABI 校验 -> 安装到私有目录 -> 生效 -> 监控 -> 禁用/回滚。

补丁加载成功不等于问题修复，还要看命中率、crash、ANR 和业务指标。

二、业务使用中的真实问题

1. 补丁动态生效能力容易被误用

Dex 插入和方法插桩的生效模型不同，容易被混用：Dex 插入可以带新类，但不适合要求“立刻替换已加载类”的场景；方法插桩可以动态生效，但只能改已有插桩方法内部逻辑，不能新增类、字段、方法签名。

所以业务止血前要先判断：这次修复是“类级替换”还是“现有方法逻辑修改”。如果选错方案，补丁可能加载成功但不命中。

2. Kotlin 编译产物会影响命中路径

Kotlin inline、lambda、默认参数、协程状态机都会改变实际执行位置。修原方法不一定能影响已经 inline 到调用方的逻辑，协程状态机也可能让补丁点和源码认知不一致。

3. Native 补丁通常不能覆盖已加载 so

dlopen 完成后，JNI_OnLoad、全局变量、线程、单例、符号解析都已经生效。运行中替换 so 容易导致重复加载、全局状态拆裂、ABI 或符号不兼容。

Native 热修更适合设计成下次冷启动或模块未加载前生效。涉及 Android 8+ linker namespace 时，还要确认依赖 so 的可见性。

4. 资源补丁不是只替换文件

资源热修容易被缓存坑住：资源 ID、Theme、Configuration、DisplayMetrics、AppCompat/Tint 缓存都可能导致补丁不生效或错生效。

补丁资源如果依赖新增代码逻辑，旧代码不一定能识别。复杂 layout 结构和 theme 体系重构不适合资源热修。

5. 安全和回滚必须先设计

补丁必须放 App 私有目录，并通过签名、hash、宿主版本范围、ABI 校验。不能从外部可写目录直接加载 dex/so。

没有灰度、禁用、bad patch 标记和回滚，不应该上线热更新。补丁本身可能扩大事故。
