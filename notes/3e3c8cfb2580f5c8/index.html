云游戏触摸的本质是：客户端采集本地触摸事件，转换为与设备分辨率无关的输入数据，通过网络发往云端，再由云端重建触摸事件并注入 Android 输入系统。

链路目标与 Android 多指模型

整体链路

示意
本地触摸采集
  -> 坐标转换与多指快照
  -> 事件编码
  -> 网络传输
  -> 云端触摸状态机
  -> 重建 Android 触摸事件
  -> 注入系统输入链路
  -> 目标应用收到触摸事件

这条链路需要同时保证三件事：

  • 手指身份正确：多根手指不会在传输过程中串号。

  • 坐标映射正确：本地手指位置能对应到云端画面的同一位置。

  • 事件顺序正确：按下、移动、抬起不会乱序或长时间积压。

Android 的多指模型

MotionEvent 中有两个容易混淆的概念：

  • pointerIndex：手指在当前事件数组中的下标，可能随事件变化。

  • pointerId：一根手指从按下到抬起期间保持稳定的身份。

ACTION_POINTER_DOWN 和 ACTION_POINTER_UP 的完整 action 不只包含动作类型，高位还编码了本次变化的 pointerIndex：

示意
action = actionMasked | (actionIndex << ACTION_POINTER_INDEX_SHIFT)

以双指操作为例：

阶段action事件中的指针
第一指按下ACTION_DOWNp0
第二指按下ACTION_POINTER_DOWN + indexp0, p1
双指移动ACTION_MOVEp0, p1
第二指抬起ACTION_POINTER_UP + indexp0, p1
最后一指抬起ACTION_UPp0

因此，多指传输不能只传「发生变化的手指」。在移动、新增手指和抬起手指时，应把当前事件中的所有指针当作一个完整快照，并保留指针顺序。

Android 对多指数据的定义见 MotionEvent API。

输入消息设计与云端状态重建

多指事件如何传输

一个触摸消息应表示一个完整的多指事件，基本信息包括：

示意
action
actionIndex
pointerCount
points[] = { pointerId, normalizedX, normalizedY }
eventTime
gestureSequence

其中：

  • pointerId 用于跨事件追踪同一根手指。

  • actionIndex 表示本次哪一根手指按下或抬起。

  • points[] 保存当前时刻的完整指针快照。

  • eventTime 用于还原事件的发生时间，而不是到达云端的时间。

  • gestureSequence 用于识别重复、乱序或跨连接的旧事件。

按下、新增手指、抬起、取消等事件会改变触摸状态，必须保证到达和顺序。移动事件更关心「最新位置」，在网络积压时可以合并过时的中间点，避免云端追赶已经失去意义的轨迹。

云端如何重建事件

云端需要维护一个按手势划分的触摸状态机：

  1. 第一根手指按下时创建手势，记录统一的 downTime。

  2. 每次按收到的顺序重建指针属性和坐标数组。

  3. 新增或抬起手指时，保留完整 actionIndex 语义。

  4. 手指抬起事件注入完成后，才从活跃指针集合中删除该手指。

  5. 所有手指抬起后结束手势；取消、断线或状态异常时清空整个手势。

重建后的事件交给 Android 系统输入注入接口，再按正常输入链路分发给目标窗口。这类系统级注入需要容器或系统进程具备相应权限，普通应用无法任意向其他应用注入事件。

坐标、时间与感知精度

1. 坐标系精度

客户端与云端分辨率通常不同，因此应传输画面内的归一化坐标：

示意
normalizedX = (touchX - contentLeft) / contentWidth
normalizedY = (touchY - contentTop) / contentHeight

remoteX = normalizedX * remoteWidth
remoteY = normalizedY * remoteHeight

这里的 content 必须是实际视频画面矩形，而不是外层容器的尺寸：

  • 等比适配产生黑边时，需要先扣除画面偏移。

  • 等比填充产生裁剪时，需要恢复被裁剪区域对应的坐标。

  • 画面发生旋转时，需要对触摸坐标执行显示变换的逆变换。

多数「画面显示正常但点击偏移」问题，本质上是画面坐标系和触摸坐标系没有使用同一组变换参数。

2. 数值精度

坐标应在归一化和网络传输阶段保留浮点值，到云端恢复逻辑像素时再根据目标分辨率转换。过早转为整数会引入量化误差，在高分辨率画面上更明显。

坐标越界检查应在完成黑边、裁剪和旋转变换之后进行。如果过早将坐标截断到 [0, 1]，可能会隐藏坐标系错误。

3. 时间与采样精度

云游戏的触摸准确性不只是最终坐标是否正确，还包括轨迹是否平滑、事件是否及时：

  • 传输 eventTime，区分事件发生时间和网络到达时间。

  • 对绘画、摇杆等场景，保留必要的历史采样点。

  • 对已积压的移动事件，可以丢弃过时中间点，但不能丢失会改变手势状态的按下、抬起和取消事件。

  • 断线或长时间无后续事件时，云端应主动取消手势，避免出现「手指一直按住」的状态残留。

4. 降低本地触摸采集延迟

Android 默认可以将连续的 MOVE 事件暂存起来，在下一次 VSYNC 的输入阶段批量交给应用。云游戏收到触摸回调后还要把事件发送到云端，这段等待会直接增加端到端操作延迟。

云游戏画面 View 可以在手势开始时调用 requestUnbufferedDispatch(event))：

kotlin
override fun onTouchEvent(event: MotionEvent): Boolean {
    if (event.actionMasked == MotionEvent.ACTION_DOWN) {
        requestUnbufferedDispatch(event)
    }

    sendTouchEvent(event)
    return true
}

请求由 View 发起，实际由该 Window 的 ViewRootImpl 调整输入接收策略。它不会绕过 InputChannel 和 View 事件分发，只是不再让当前触摸流的后续移动事件继续等待 VSYNC 合批；手势在 UP 或 CANCEL 后结束。其他 Window、Activity 或进程的输入链路不受影响。

这项优化最多可以减少接近一个刷新周期的本地等待，主要收益发生在连续 MOVE。代价是触摸回调、线程唤醒和发送次数可能增加，因此需要同时观察：

  • MotionEvent.eventTime 到事件发送的延迟。

  • 每秒触摸回调数和网络消息数。

  • 主线程 CPU、掉帧和功耗。

它只优化「本地触摸进入发送链路」这一段，不能消除网络、云端处理、编码和画面显示延迟。

延伸思考：用短期预测隐藏移动事件丢包

连续 MOVE 发生短暂丢包或重传等待时，可以根据最近的真实采样点预测一个很短时间后的坐标，临时填补输入空档；下一条真实事件到达后立即丢弃预测结果并校正状态。也可以由发送端在消息中携带短期预测点，接收端仅在检测到序号缺口或事件超时后使用。

这属于丢包隐藏，不是恢复真实轨迹。预测只适用于短时间、方向稳定的连续移动，不能用于 DOWN、UP、CANCEL 和多指状态变化；超过预测窗口或置信度下降时应停止外推。可靠有序传输仍需负责关键动作和状态一致性，预测只能遮盖等待重传期间的操作停顿。

预测坐标一旦作为普通 MotionEvent 注入云端就无法回滚，因此更适合摇杆、视角滑动等可连续修正的场景。它应作为实验方案，重点验证丢包条件下的跟手性收益、预测误差和误操作率。

5. 感知精度

用户是根据客户端正在显示的视频帧进行点击，但该帧在云端已经是过去状态。因此，即使坐标转换完全准确，视频编码、网络、解码和渲染延迟仍可能让用户感觉「点击跟手性差」。

所以触摸精度应拆成两个指标：

  • 坐标误差：触摸位置与云端注入位置之间的偏差。

  • 触摸到画面反馈延迟：从本地触摸到包含处理结果的新视频帧显示出来的时间。

结论

云游戏多指的核心不是「同时发送多个坐标」，而是在客户端和云端之间维持同一个多指状态机。

完整设计需要同时保证：pointerId 稳定、指针快照完整、关键动作有序、画面与触摸共用同一套坐标变换，以及移动事件在轨迹保真和低延迟之间取得平衡。
