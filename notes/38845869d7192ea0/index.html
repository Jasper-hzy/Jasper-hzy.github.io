云游戏/ 技术实现

Android 容器抓屏实现

云游戏里的抓屏不是简单截图，而是把远端 Android 容器中游戏渲染出来的连续画面，稳定、低延迟地送入编码链路。它连接了 Android 图形系统、VirtualDisplay、SurfaceFlinger、OpenGL 纹理和 MediaCodec。

云游戏抓屏在全链路中的位置

text
远端游戏 App 渲染
  -> 游戏 Surface / Layer
  -> SurfaceFlinger 合成
  -> 抓屏输出到 VirtualDisplay / HWC / 截屏接口
  -> OES / YUV / 编码 Surface
  -> MediaCodec 编码
  -> 网络传输
  -> 客户端解码渲染

抓屏耗时一般包含：游戏自身渲染、VSYNC 调度、Layer 合成、画面写入抓屏目标 Surface，以及后续送编码前的格式转换或纹理搬运。

常见抓屏方案

方案实现方式优点问题适用判断
MediaProjection + VirtualDisplayAPK 侧通过系统 API 创建 VirtualDisplay 抓取屏幕接入成本低，系统 API 支持会有权限提示，不适合无人值守容器普通录屏、调试验证
JNI 创建 VirtualDisplayNative 层直接走系统录屏链路，类似 screenrecord效率高，可绕过前台授权弹窗依赖系统权限和容器环境云游戏 Android 容器更常用
ScreenshotClient::capture / /dev/graphics/fb0直接抓主屏数据，类似 screencap实现直观性能低，不适合高帧率实时串流截图、低频诊断
厂商 HWC / 图形接口从厂商提供的合成数据或硬件链路拿帧理论链路更短强依赖厂商实现，适配成本高板卡、ArmServer、深度定制场景

历史源码参考：

  • Android screenrecord：frameworks/av/cmds/screenrecord/

  • Android screencap：frameworks/base/cmds/screencap/

VirtualDisplay 抓屏的核心链路

VirtualDisplay 的本质是给系统一个目标 Surface，让系统把显示内容渲染到这个虚拟显示上。云游戏可以把这个目标接到后续编码或纹理处理链路。

text
DisplayManager / SurfaceControl 创建虚拟显示
  -> 配置目标 Surface
  -> SurfaceFlinger 将目标 Layer 合成到 VirtualDisplay
  -> 抓屏服务拿到 OES 纹理或图像 buffer
  -> 送入编码前处理

这里的性能瓶颈通常不只在“抓屏 API”本身，而在抓到画面后怎么送编码。

送编码前的三种数据路径

编码前处理可以拆成三种路径，按“是否发生 GPU/CPU 往返、是否多一次 OpenGL 绘制”来理解。

1. OES -> YUV / NV12：老方案

text
VirtualDisplay 输出 OES 纹理
  -> OpenGL 采样转 YUV / NV12
  -> GPU 拷贝到 CPU 内存
  -> CPU Buffer 送入编码器
  -> 编码器内部再上传到硬件编码路径

优点是兼容性相对好，容易做图像前处理；缺点是链路重，有纹理采样、格式转换和 CPU/GPU 数据流转。

在部分 Android 板卡上，CPU 和 GPU 共享内存，实际拷贝成本没有从架构图上看起来那么夸张，所以这个方案能长期在线上使用。但在 GPU/CPU 分离更明显的 ArmServer 或独显架构上，这条路径的带宽和拷贝成本会更敏感。

2. OES 纹理 GPU 路径：少一次 YUV 转换

text
VirtualDisplay 输出 OES 纹理
  -> SurfaceTexture 接收纹理
  -> OpenGL draw 到编码器输入 Surface
  -> MediaCodec 硬编

这个方案减少了 OES -> YUV 和 CPU 传输，主要让数据留在 GPU/图形 buffer 链路里。编码前处理/送编链路相对老方案约优化 2ms。

它的限制是：SurfaceTexture 或离屏缓冲管理不好时，下游编码阻塞会反向影响上游送帧，所以需要纹理池、buffer 管理和背压策略配合。

3. 编码直通：目标最短路径

text
游戏画面 / VirtualDisplay
  -> 直接写入编码器输入 Surface
  -> MediaCodec 硬编

编码直通的目标是让 VirtualDisplay 或游戏画面直接进入编码器输入 Surface，减少 SurfaceTexture 绑定和 OpenGL 再绘制。理论上它是抓屏编码的最短路径。

难点在于：

  1. 要在正确时机拿到或替换目标 Surface。

  2. 要保证分辨率、旋转、裁剪、色彩空间等前处理能力仍然可用。

  3. 要处理编码器背压，避免编码吐帧慢时阻塞游戏渲染或抓屏线程。

  4. 如果通过 hook 游戏获取 Surface，需要处理不同游戏、不同系统版本、不同图形路径的兼容性。

游戏画面直通编码

更进一步的思路是：不等游戏画面先进入普通显示合成链路，而是在游戏获取 Surface 时注入代理 Surface，动态替换为编码器输入 Surface，让游戏画面直接写入编码 Surface。

text
游戏请求 Surface
  -> hook / 代理 Surface
  -> 动态切到编码器输入 Surface
  -> 游戏绘制结果直接进入编码链路

这个方向能减少 VSYNC 调度、Layer 合成、VirtualDisplay 再输出等环节，但工程风险也更高：游戏兼容、Surface 生命周期、分辨率变化、横竖屏、异常恢复都必须处理完整。

抓屏链路的观测指标

只看端到端操作延迟或 100ms 卡顿率，不足以判断抓屏问题。更适合把一帧拆成以下指标：

  1. 游戏渲染耗时。

  2. VSYNC 等待和调度耗时。

  3. SurfaceFlinger / HWC 合成耗时。

  4. VirtualDisplay 输出耗时。

  5. OES 转 YUV 或 OpenGL 绘制耗时。

  6. 送入编码器前的排队耗时。

  7. 编码器输入 Surface 的阻塞时间。

当某个方案收益不明显时，要区分是“少了一次处理但增加了排队”，还是“理论链路更短但被兼容逻辑抵消”。
