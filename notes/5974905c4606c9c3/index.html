WebRTC 连接建立：SDP、ICE 与 DTLS/SRTP

本文说明媒体发送前的能力协商、路径探测和加密握手，并讨论一种云游戏接入方案。

讨论范围与建连目标

讨论范围

本文只讨论连接建立阶段：SDP、ICE、DTLS/SRTP，以及云游戏连接建立的对照。

不展开 RTP/RTCP 媒体包、拥塞控制、Pacer、JitterBuffer、NACK、FEC、DataChannel，这些不在本文范围内。

核心机制

WebRTC 连接建立解决三件事：

text
SDP：谈清楚“用什么媒体能力和传输参数”
ICE：找出“一条真正能通的网络路径”
DTLS/SRTP：在这条路径上完成身份校验、密钥协商和媒体加密

它的设计目标是在未知设备能力、未知 NAT 环境、未知业务信令的前提下，尽量建立一条安全、低延迟、可传 RTP/RTCP 的通路。

协议分工：协商、探路与密钥建立

SDP：谈媒体能力和传输参数

SDP 是 Session Description Protocol，可以理解成“会话说明书”。它不是发媒体包的协议，而是用来描述和协商后续媒体怎么传。

SDP 里通常会描述这些信息：

  • 媒体类型：音频、视频、数据通道。

  • 媒体方向：sendrecv、sendonly、recvonly、inactive。

  • 编解码能力：H264、VP8、VP9、AV1、Opus，以及对应的 fmtp 参数。

  • RTP 扩展：例如 TWCC、abs-send-time、audio-level、video-orientation。

  • ICE 参数：ice-ufrag、ice-pwd，用于后续 ICE 连通性检查认证。

  • DTLS 指纹：fingerprint，用于后续 DTLS 握手时校验证书。

  • BUNDLE / RTCP mux：把多路媒体复用到同一条传输连接上，减少端口和 ICE 检查成本。

Offer / Answer 的含义是：一端先提出自己能支持和想使用的能力，另一端在自己的能力范围内选择双方交集并返回结果。

text
A createOffer
  → A setLocalDescription(offer)
  → 通过业务信令发给 B
  → B setRemoteDescription(offer)
  → B createAnswer
  → B setLocalDescription(answer)
  → 通过业务信令回给 A
  → A setRemoteDescription(answer)

这里有一个关键点：WebRTC 只定义 SDP 内容和 PeerConnection 行为，不定义信令通道本身。SDP 可以通过 WebSocket、HTTP 或业务自己的信令系统传递。

ICE：做连通性检查和路径选择

ICE 解决的是 NAT 环境下“到底哪条网络路径能通”的问题。它不是简单的 IP 优选，而是对一组候选地址做连通性检查。

常见 candidate 类型：

类型含义特点
host本机网卡地址同局域网可能直连，公网不可直接访问内网地址
srflxSTUN 看到的公网映射地址普通 NAT 下可能可用
relayTURN 中继地址成功率最高，但延迟和成本最高

ICE 的基本过程：

text
收集本端 candidate
  → 通过业务信令交换 candidate
  → 双方 candidate 两两组成 candidate pair
  → 对每个 pair 发送 STUN binding request
  → 检查是否可写、可收、RTT 和优先级
  → 选出最终的 selected candidate pair

现代 WebRTC 通常使用 Trickle ICE：SDP 先交换，candidate 边发现边通过信令发送给对端。这样不用等所有 candidate 收集完再开始检查，可以降低建连等待。

DTLS/SRTP：握手、验身份、加密媒体

ICE 选出路径后，媒体还不能明文传。WebRTC 强制加密，所以需要 DTLS/SRTP。

准确分工是：

text
DTLS：在 UDP 路径上握手、验证 SDP fingerprint、协商密钥
SRTP：使用 DTLS 导出的密钥，加密真正的 RTP/RTCP 媒体包

为什么不是直接用 DTLS 加密每个 RTP 包？因为实时媒体包频率高、延迟敏感，SRTP 更贴合 RTP/RTCP 的格式和开销模型。DTLS 主要负责握手和密钥导出，媒体传输阶段由 SRTP/SRTCP 承担。

图里要注意两点：第一，云游戏不是抛弃 SDP/ICE/加密，而是把它们封装进私有信令、接入调度和推拉流流程里；第二，云游戏多了一步业务前置调度，并倾向先 P2S 保底，再 P2P 升级。

标准 WebRTC 的建连耗时在哪里

低延迟场景最关心的是这条链路里产生了多少 RTT。常见耗时来自：

  • 业务信令往返：offer/answer、candidate 交换。

  • candidate 收集：尤其需要 STUN/TURN 时。

  • ICE connectivity check：candidate pair 探测需要网络往返。

  • DTLS handshake：在选出的路径上再次握手。

  • 首帧媒体准备：编码、打包、发送、解码、渲染。

因此 WebRTC 低延迟优化常见方向是：Trickle ICE、复用连接、BUNDLE/RTCP mux、预热 STUN/TURN、优化信令 RTT、减少首帧等待。

云游戏接入方案与适用边界

云游戏连接建立为什么要改造

云游戏和普通 WebRTC 通话不一样。普通 WebRTC 是两个对等端实时通话；云游戏更接近“客户端连接一个云端实例/媒体服务”，并且强关注首帧和操作跟手。

以下以包含业务调度、P2S 保底和 P2P 升级的云游戏接入方案为例；这不是所有云游戏平台的统一实现：

text
业务请求（例如 pod_start / launch）
  → 分配云端实例或接入节点
  → 返回 room_id、token、pod_user_id、媒体/信令接入信息
  → 客户端基于这些信息进入 RTC 建连与推拉流

这一步不是 WebRTC 标准的一部分，而是云游戏为了资源调度和首帧路径准备引入的业务前置步骤。

云游戏与标准 WebRTC 的关键差异

环节标准 WebRTC云游戏低延迟连接
连接对象对等端之间协商客户端连接云端实例/媒体接入服务，非对称
信令WebRTC 不定义，由业务自建私有信令/接入服务承载 room、token、startpush/startpull 等
SDPoffer/answer 协商媒体能力仍有 offer/answer，但封装进推拉流信令里
ICE对等端 candidate pair 检查本例先 P2S 保底，再择机 P2P 升级
DTLS/SRTPDTLS 握手导出 SRTP 密钥仍需媒体安全，工程上可能结合预置信息减少等待
目标通用连通性和安全实时通信首帧快、操作低延迟、连接成功率高

这里要注意：云游戏不是完全抛弃 WebRTC 机制。它仍然可能使用 SDP、ICE、SRTP 这些基础能力，只是把业务调度、接入服务、P2S/P2P 选择、预置信息和推拉流信令做了工程化封装。

结论

这条连接建立链路可以压缩成一句话：

text
SDP 谈参数，ICE 找路径，DTLS 协商密钥，SRTP 保护媒体。

云游戏在这条链路上的优化目标不是改变 WebRTC 的基本物理问题，而是把“找谁连、怎么更快连上、首帧怎么更快到、后续能否升级更低延迟路径”这些业务和传输决策前置、工程化。
