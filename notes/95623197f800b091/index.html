Android 云游戏免安装启动机制

云游戏里的“免安装”通常不是绕过 Android 的包管理和进程模型，而是把游戏文件集中存储，在游戏启动前动态映射到云端 Android 实例，并复用或快速补齐 PMS 所需的包状态。用户不需要在本地下载安装，云端实例也不需要长期保存所有游戏。

这套能力可以先概括为：

text
中心游戏存储
  -> NFS 或 FUSE 将游戏文件暴露为本地目录
  -> OverlayFS 为当前实例生成合并视图
  -> 映射到 PMS 记录的 /data/app 路径
  -> PMS 提供包和组件信息
  -> AMS/ATMS 启动游戏进程
  -> ART、linker 和游戏引擎按需读取远端文件

相关 Android 基础见 PackageManagerService 包扫描与安装流程。

一、传统安装和云游戏启动的区别

传统安装一般包含：

text
下载完整 APK
  -> PackageInstaller 创建安装会话
  -> 复制 APK 到 /data/app
  -> PMS 解析 Manifest、校验签名和版本
  -> 分配 uid / appId、写入包状态
  -> 准备应用数据和 dex/oat
  -> 启动应用

云游戏要避免的是每个实例都重复下载和复制整个游戏：

text
系统已经运行
  -> 启动脚本选择游戏版本
  -> 动态挂载游戏目录
  -> 映射到 /data/app 的固定 codePath
  -> 必要时恢复、启用或重新扫描包状态
  -> 启动游戏

因此，“免安装”更准确的含义是：

游戏安装文件集中保存，实例启动时通过文件系统挂载快速获得可访问的游戏目录，并复用或快速建立 Android 包状态，从而省略重复的完整下载、复制和编译过程。

二、整体分层

text
PMS / ART / linker / 游戏进程
              ↓
     open / read / mmap / stat
              ↓
          Linux VFS
              ↓
         OverlayFS merged
          ↙             ↘
实例本地 upperdir    远端只读 lowerdir
                       ↓
                  NFS 或 FUSE
                       ↓
              游戏存储 / CDN / 对象存储

各层职责不同：

层主要职责
PMS保存包、组件、签名、uid、权限和 codePath 等结构化信息
VFS向上提供统一文件接口，向下路由到具体文件系统
NFS将 NFS 服务器目录挂载为本地目录
FUSE由用户态程序实现一个可挂载的虚拟文件系统
OverlayFS将共享只读层和当前实例可写层合并为一个目录
启动脚本/守护进程负责停止进程、挂载、权限处理、包状态处理和启动游戏

三、VFS：为什么游戏不需要适配存储方案

VFS 全称是 Virtual File System，是 Linux 内核提供的统一文件系统抽象。游戏、PMS 和 ART 只调用普通文件接口：

text
open()
read()
write()
mmap()
stat()

VFS 根据挂载表把请求交给 ext4、NFS、FUSE 或 OverlayFS。游戏访问：

text
/data/app/<game-dir>/base.apk

底层可能经过：

text
游戏 / PMS / ART
  -> VFS
  -> OverlayFS
  -> NFS
  -> 网络存储

或者：

text
游戏 / PMS / ART
  -> VFS
  -> OverlayFS
  -> FUSE
  -> 用户态文件系统服务
  -> 缓存 / CDN / 对象存储

只要挂载到游戏原本使用的路径，并完整支持 read、mmap、随机读取等语义，游戏侧通常不需要修改代码。

四、NFS：把远端目录映射到本地

NFS 是标准网络文件系统协议。服务端集中保存游戏，例如：

text
NFS Server：10.0.0.10

/srv/games/
  ├─ game-a/
  │   ├─ base.apk
  │   ├─ split_config.arm64_v8a.apk
  │   ├─ lib/
  │   └─ oat/
  └─ game-b/

宿主机或有挂载权限的容器管理服务执行：

bash
mount -t nfs -o ro,vers=4.1 \
  10.0.0.10:/srv/games/game-a \
  /mnt/current-game

挂载完成后：

text
/mnt/current-game/base.apk

实际对应 NFS 服务器上的：

text
10.0.0.10:/srv/games/game-a/base.apk

mount 不会默认把完整游戏复制到容器。第一次读取且缓存未命中时，才发生远端 I/O：

text
open / read / mmap
  -> VFS
  -> 内核 NFS 客户端
  -> NFS RPC
  -> NFS Server
  -> 数据进入宿主机 Page Cache

再次读取相同数据时可能直接命中 Page Cache，不再访问网络。热门游戏还可能通过节点本地 SSD 缓存和启动预热进一步降低首启延迟。

五、FUSE：由用户态程序提供游戏文件

FUSE 全称是 Filesystem in Userspace。它不是一种固定的远端存储协议，而是让用户态程序实现文件系统的机制。

使用上同样先得到一个挂载目录：

bash
game-fuse \
  --game-id game-a \
  --mount-point /mnt/current-game

游戏读取文件时：

text
游戏 / PMS / ART
  -> VFS
  -> FUSE 内核模块
  -> game-fuse 用户态进程
  -> 内存缓存 / SSD 缓存 / CDN / 对象存储

FUSE 服务可以按文件块实现平台自己的策略：

  • 先拉取 Manifest、dex/oat、启动 so 和首屏资源。

  • 其余地图、纹理和音频按访问顺序拉取。

  • 通过内容哈希去重多个游戏版本中的相同数据块。

  • 对数据进行解压、解密和完整性校验。

  • 使用内存、SSD 和远端存储组成多级缓存。

  • 根据容量和热度淘汰本地数据。

传统 FUSE 请求需要在内核和用户态守护进程之间切换，通常比内核 NFS 路径多一层开销；优势是能实现更细的游戏资源调度、预取和缓存策略。

NFS 与 FUSE 对比

维度NFSFUSE
本质标准网络文件系统协议用户态文件系统框架
数据来源NFS Server可由平台自行定义
访问实现主要由内核 NFS 客户端完成由 FUSE 用户态服务处理
接入成本较低，方案成熟较高，需要开发文件系统服务
定制能力相对有限可实现分块、预取、去重、解密等策略
传统路径开销内核路径相对直接多一层内核与用户态交互
游戏侧改动通常不需要文件语义完整时通常不需要

NFS 和 FUSE 都是访问驱动：PMS、ART、linker 或游戏第一次访问某段数据且缓存未命中时，才触发实际远端读取。但内核 read-ahead、FUSE 主动预取或平台预热可能提前读取后续数据。

六、OverlayFS：共享游戏层和实例写入层

OverlayFS 将多个目录合并成一个视图：

text
lowerdir：NFS/FUSE 提供的共享只读游戏层
upperdir：当前实例的可写修改层
workdir：OverlayFS 内部工作目录
merged：最终对 Android 暴露的目录

示例：

bash
mount -t overlay overlay \
  -o lowerdir=/mnt/current-game,upperdir=/local/game-a/upper,workdir=/local/game-a/work \
  /local/game-a/merged

再将合并目录映射到 PMS 记录的固定路径：

bash
mount --bind \
  /local/game-a/merged \
  /data/app/<game-dir>

OverlayFS 的查找规则是：

text
访问文件
  -> 先查 upperdir
  -> upperdir 没有，再查 lowerdir

读取 lowerdir 文件时不会自动复制完整文件；第一次修改 lowerdir 文件时才执行 Copy-up，将文件复制到 upperdir 后再修改。删除 lowerdir 文件时，upperdir 使用 whiteout 标记在 merged 视图中隐藏它。

对于 /data/app 中通常保持只读的 APK、split 和 so，upperdir 可以是一次性的。游戏结束后先卸载 merged，再删除 upperdir 和 workdir：

text
停止游戏
  -> 卸载 /data/app 的 bind mount
  -> 卸载 OverlayFS merged
  -> 删除 upperdir / workdir
  -> 卸载 NFS 或停止 FUSE 服务

玩家存档不能默认跟这个临时层一起删除。需要持久化的数据应独立保存：

text
游戏程序：共享只读层 + 临时 upperdir
玩家数据：独立持久卷或云端同步
热点数据：Page Cache 或容量受控的节点 SSD 缓存

OverlayFS 能否直接使用某个 NFS/FUSE 挂载作为 lowerdir，取决于内核版本、文件系统能力和厂商实现，实际平台可能修改内核或由自定义文件系统直接实现合并和 Copy-on-Write。

七、PMS 在动态覆盖中的边界

已知场景是 Android 系统已经运行，游戏启动前脚本动态覆盖 App 目录。此时必须区分两种情况。

1. PMS 已经认识这个包

PMS 内存中已经有：

text
packageName
uid / appId
ActivityInfo 等组件索引
签名和权限状态
sourceDir=/data/app/<game-dir>/base.apk

脚本把真实游戏文件挂载到同一个 codePath：

text
挂载前：/data/app/<game-dir>/base.apk
挂载后：/data/app/<game-dir>/base.apk

路径没有变化，变化的只是该路径背后的文件系统。此时脚本可能不需要触发 PMS 扫描，完成挂载后直接启动游戏。

覆盖内容仍应保持包名、签名、组件、split 结构和 native library 路径兼容。如果 Manifest 已变化但 PMS 没有重新扫描，就会出现 PMS 内存状态与磁盘 APK 不一致的问题。

2. PMS 原本不认识这个包

仅把一个全新 APK 挂到 /data/app，不足以保证当前 PMS 自动建立组件索引。启动脚本还必须走以下某一种路径：

  • 通过 pm install 或 cmd package install 进入标准安装入口。

  • 对 PMS 已全局认识但当前用户未启用的包执行 install-existing。

  • 调用厂商新增的 PackageManager Binder/Shell 接口，对指定挂载目录热扫描。

  • 在旧版本系统中制造目录文件事件，由 AppDirObserver 触发 scanPackageLI()。

  • 挂载完成后重启 Framework/system_server，使 PMS 重新初始化。

install-existing 只能为用户启用一个 PMS 已知包，不能把未知 APK 注册成新包。am start 也不会负责扫描 APK；它只能使用 PMS 已有的 ActivityInfo 解析并启动组件。

旧版 AOSP 的目录监听入口可参考：

  • AppDirObserver 与 scanPackageLI

  • PackageManagerShellCommand

目前没有启动脚本和对应 Android 版本，不能确定实际平台属于“预注册后只覆盖文件”还是“挂载后调用私有热扫描”。

八、启动脚本可能执行的流程

下面是概念流程，不代表具体平台命令：

text
1. 获取 packageName、游戏版本和远端存储位置
2. 查询 PMS 中是否已有目标包
3. 停止旧游戏进程，释放 APK、so 和资源文件句柄
4. 挂载 NFS，或启动 FUSE 服务
5. 创建当前实例的 upperdir 和 workdir
6. 挂载 OverlayFS merged
7. bind mount 到 PMS 记录的 /data/app/<game-dir>
8. 修正目录属主、权限和 SELinux 上下文
9. 必要时执行包启用、热扫描或 Framework 重载
10. 校验 PMS 能解析包和入口 Activity
11. 通过 AMS/ATMS 启动游戏

先停止旧进程非常重要。已经打开的文件描述符仍然指向旧 inode；动态挂载只会影响后续路径查找和新打开的文件。重新启动进程后，ART、linker 和游戏引擎才会从新的 merged 视图打开 APK、dex、so 和资源。

九、怎么验证实际平台走的路线

在执行启动脚本前后分别检查：

bash
pm path <packageName>
dumpsys package <packageName>
pm list packages -u | grep <packageName>
mount
cat /proc/mounts

判断方式：

text
脚本前 pm path 已成功
  -> PMS 已经注册，脚本大概率只覆盖实体文件

脚本前不存在，执行后出现
  -> 脚本触发了安装、热扫描或自定义包注册

脚本前 list packages -u 可见，但普通列表不可见
  -> 包状态仍在，脚本可能为当前用户执行 install-existing/enable

脚本中重点查找：

text
mount -t nfs
mount -t overlay
mount --bind
fusermount / 自定义 FUSE 进程
pm install / cmd package / install-existing
service call package / 自定义 appctl、game manager
stop / start / setprop ctl.restart
restorecon / chown / chmod
am force-stop / am start

还应观察系统日志中的 PackageManager、PackageInstallerSession、installd 和 ActivityTaskManager，确认是否发生了包扫描、安装提交或仅有 Activity 启动。

十、关键结论

  1. NFS 是把远端游戏目录映射为本地目录；读取时由内核 NFS 客户端访问服务器。

  2. FUSE 是由用户态服务提供虚拟目录，可以自行实现分块拉取、预取、去重、解密和缓存。

  3. NFS 和 FUSE 默认都按访问触发远端 I/O，Page Cache、read-ahead 和平台预热会改变实际读取时机。

  4. VFS 屏蔽了底层文件系统差异，所以游戏侧通常不需要改造。

  5. OverlayFS 将远端只读游戏层和实例可写层合并；临时 upperdir 可以在游戏退出后删除。

  6. /data/app 程序层可以临时挂载，玩家存档和账号数据应独立持久化。

  7. PMS 已经注册包时，保持相同 codePath 可以只动态覆盖文件；PMS 未注册时，脚本必须额外触发安装、启用或平台定制的热扫描。

  8. 最终实现应以实际启动脚本、Android 版本、PMS 改动和挂载表为准。
