Android 渲染上屏流程

这篇文档只围绕一条主线：一帧画面从 App 侧产生，到进入 Surface/BufferQueue，再到 SurfaceFlinger 合成，最后输出到屏幕或虚拟显示。

下面这张图是本文的主图，后文按图从左到右解释。

1. 主窗口从 VSYNC 到 ViewRootImpl

主窗口的绘制由 VSYNC 驱动。VSYNC 到来后，Choreographer 触发 doFrame，UI 线程进入 ViewRootImpl 的 traversal 流程。

text
VSYNC 信号
  -> Choreographer#doFrame
  -> UI 线程 / ViewRootImpl
  -> performTraversals
  -> draw

这里的 ViewRootImpl 是 App 进程内连接 View 树和窗口系统的对象。它负责把 requestLayout、invalidate 等刷新请求合并到下一帧，并在合适的 VSYNC 时机执行测量、布局和绘制。

2. View 绘制分为硬件绘制和软件绘制

ViewRootImpl 进入 draw 后，会根据是否启用硬件加速走两条路径。

硬件绘制路径

硬件加速开启时，View 的绘制命令会进入 RenderThread 和 HWUI/OpenGL/EGL 路径。

text
onDraw / canvas.draw
  -> 硬件加速
  -> RenderThread 执行 draw / 收集 DisplayList
  -> OpenGL / EGL GPU 绘制
  -> HardwareRenderer / EGL swap
  -> GraphicBuffer

这里的 GraphicBuffer 是 App 侧最终提交给窗口 Surface 的图形缓冲。硬件绘制并不是直接画到屏幕，而是把 View 树绘制结果写入与窗口 Surface 关联的 buffer。

软件绘制路径

未走硬件加速时，会通过 CPU Canvas 绘制，并通过 Surface.lockCanvas / unlockCanvasAndPost 提交。

text
onDraw / canvas.draw
  -> CPU 执行 draw
  -> Surface.lockCanvas
  -> Surface.unlockCanvasAndPost
  -> GraphicBuffer

软件绘制路径少见于现代复杂 UI，但它能帮助理解：无论硬件绘制还是软件绘制，最终都要产出 buffer，并提交到 Surface 对应的 BufferQueue。

3. ViewRootImpl#mSurface 是主窗口的 producer 入口

主窗口的 Layer 不是每帧绘制后才生成。窗口创建或 relayout 时，WMS 通过 SurfaceControl 在 SurfaceFlinger 侧创建和配置 App Window Layer；App 侧 ViewRootImpl 持有与这个 Layer 关联的 Surface，也就是 ViewRootImpl#mSurface。

窗口和 Layer 建立链路可以理解为：

text
Activity / Window
  -> ViewRootImpl.setView
  -> IWindowSession.addToDisplay / relayout
  -> WMS / WindowState
  -> SurfaceControl
  -> SurfaceFlinger 创建或配置 App Window Layer
  -> ViewRootImpl#mSurface 获得 producer 入口

每帧绘制时，App 只是通过这个 producer 入口提交新的 buffer：

text
ViewRootImpl / RenderThread
  -> ViewRootImpl#mSurface
  -> IGraphicBufferProducer.queueBuffer
  -> BufferQueue
  -> SurfaceFlinger acquireBuffer
  -> 更新 App Window Layer 内容

所以，主窗口里普通 View 的内容最终都合并在 App Window Layer 里。SurfaceFlinger 不理解 TextView、Button、RecyclerView 这些 View 结构，它只消费 Layer 的 buffer。

4. SurfaceView 是额外的独立 Layer

图中下方的 SurfaceView 分支表示：SurfaceView 的内容不先画进 ViewRootImpl 的主窗口 Surface。视频、相机、游戏或解码器可以直接写入 SurfaceView 自己的 Surface。

text
SurfaceView / 游戏引擎 / MediaCodec / Camera
  -> OpenGL / EGL GPU 绘制或解码输出
  -> GraphicBuffer
  -> SurfaceView 自己的 Surface
  -> SurfaceFlinger 中的独立 Layer

View 树主要负责 SurfaceView 的占位、大小、可见性和 Layer 控制；真正的视频或游戏画面作为独立 Layer 参与 SurfaceFlinger 合成。

这也是 SurfaceView 适合视频、相机、游戏和低延迟渲染的原因：producer buffer 可以更直接地成为 SurfaceFlinger 可合成的 Layer，少一次 App 侧纹理采样和合成。

5. SurfaceFlinger 如何合成

SurfaceFlinger 收到 VSYNC 后，会遍历当前所有 Layer，检查每个 Layer 是否有新的 buffer。

text
VSYNC 信号
  -> SurfaceFlinger
  -> 遍历所有 Layer
  -> acquire / dequeue GraphicBuffer
  -> 收集多个 Layer 的 GraphicBuffer、Layer 属性和变换信息
  -> 合成

每个 Layer 不只有 buffer，还包含位置、大小、裁剪、透明度、层级、旋转等合成属性。SurfaceFlinger 会根据这些信息决定合成方式。

6. 合成路径：GPU 合成或 HWC 硬件合成

图右侧展示了两类合成路径。

text
多个 Layer 的 GraphicBuffer + Layer 坐标/变换信息
  -> 软件合成 / OpenGL
  -> 或 HWC 硬件合成
  -> 输出到目标 Surface

如果硬件合成器能够处理当前 Layer 的格式、裁剪、缩放、旋转和混合方式，系统会尽量使用 HWC。否则会回退到 GPU/OpenGL 合成。

7. 输出目标：物理屏或 VirtualDisplay

SurfaceFlinger 合成后的结果不一定只输出到物理屏幕。图中展示的是另一类场景：输出到一个 Surface，再进入 VirtualDisplay，并触发下游编码器。

text
SurfaceFlinger 合成结果
  -> Surface
  -> VirtualDisplay
  -> onFrameAvailable
  -> 编码器

这条路径常见于录屏、投屏、云游戏抓屏等场景。它和普通物理屏显示共用同一套 Layer/BufferQueue/SurfaceFlinger 机制，只是最终 display target 不同。

8. 扩展知识

8.1 SurfaceView 与 TextureView

SurfaceView 和 TextureView 都能承载视频、相机、游戏画面，但它们接入上屏链路的位置不同。

对比项SurfaceViewTextureView
最终是否额外独立 Layer是，SurfaceFlinger 除 App Window Layer 外还会合成 SurfaceView Layer否，先画进 App Window Layer
producer 写入位置SurfaceView 自己的 SurfaceSurfaceTexture 暴露的 Surface
是否参与 View 树绘制不直接参与内容绘制，View 树主要控制位置和可见性参与 View 树绘制，通过 TextureLayer 被采样
性能和延迟路径短，适合低延迟多一次 App 侧纹理采样和合成，灵活但更重

TextureView 的简化链路是：

text
Producer
  -> Surface(SurfaceTexture)
  -> SurfaceTexture 接收 buffer
  -> TextureLayer
  -> TextureView.draw / drawTextureLayer
  -> RenderThread 采样纹理并写入 ViewRootImpl#mSurface
  -> App Window Layer

所以，TextureView “和 ViewRootImpl 共用同一个 Surface”的准确含义是：TextureView 的最终显示结果会被画进 Activity/Window 的 ViewRootImpl#mSurface，和普通 View 一起成为 App Window Layer 的内容。中间的 SurfaceTexture 用于接收 producer buffer，并不作为独立 Layer 直接交给 SurfaceFlinger 合成。

8.2 BufferQueue、Fence 和三缓冲

BufferQueue 负责连接 producer 和 consumer。典型流程是：

text
producer dequeueBuffer
  -> 写入 buffer
  -> queueBuffer
consumer acquireBuffer
  -> 使用 buffer
  -> releaseBuffer

Fence 和三缓冲是 buffer 流转中的同步与排队机制，不是主流程本身。

  • Fence：表达异步读写依赖，避免消费者读到尚未写完的 buffer。

  • 双缓冲：延迟更容易低，但消费者未释放 buffer 时，生产者更容易阻塞。

  • 三缓冲：吞吐更稳，降低生产者阻塞概率，但队列里可能多排一帧，增加端到端延迟。

8.3 低延迟场景里的取舍

视频、相机、云游戏这类场景关心的不是“能不能显示”，而是“画面能不能少排队、少拷贝、少合成一次”。

以云游戏为例，远端抓屏侧可能是：

text
游戏 App Surface
  -> SurfaceFlinger / HWC 合成
  -> VirtualDisplay 或厂商 HWC 抓屏
  -> OES / YUV / 编码 Surface
  -> MediaCodec 编码

客户端渲染侧可能是：

text
MediaCodec 解码
  -> SurfaceTexture / FBO / Surface
  -> SurfaceFlinger 合成上屏

优化时要看清楚每个方案省掉了什么：少一次 SurfaceTexture、少一次 OES 转 YUV、少一次 OpenGL 绘制，或让 MediaCodec 直接消费/生产图形 buffer。
