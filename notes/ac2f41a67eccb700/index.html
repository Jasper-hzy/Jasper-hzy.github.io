WebRTC 拥塞控制：从反馈到发送端闭环

本文沿网络反馈、拥塞判断、带宽分配和执行层调整，说明发送端拥塞控制闭环。

发送端控制闭环总览

核心机制

拥塞控制不是一个单点模块，而是一条从“网络反馈”到“编码器执行”的控制链：

text
RTP 是被观测的媒体数据面
RTCP / TWCC 负责把网络观测回传回来
BWE 表示带宽估计这项职责
GCC 或其他场景化控制器是拥塞控制层内实现 BWE 与码率决策的具体算法
BWA 负责把总带宽分给媒体、FEC、RTX、padding、多路流
Pacer 负责按节奏发包
Encoder 负责根据目标码率调整 QP、分辨率、帧率或丢帧策略

所以要严格区分：

text
RTCP 是反馈协议族
TWCC 是 RTCP 里一种逐包到达反馈
BWE 是带宽估计职责/模块边界
GCC 和场景化控制器是拥塞控制 / BWE 层里的算法实现
BWA 是带宽分配
Pacer 和 Encoder 是执行层

架构层次图

图中的横带才是架构层级，横带里的方框是该层内部的模块：

  • 第 1 层是 RTP 媒体传输数据面，也是被观测对象。

  • 第 2 层负责测量和回传；TWCC 位于 RTCP 反馈协议族内部。

  • 第 3 层负责拥塞控制和带宽估计；BWE 是职责边界，GCC 和场景化控制器是该层的具体算法实现，并不是 BWE 的下一层。

  • 第 4 层把控制结果分配并调度到不同发送对象。

  • 第 5 层由编码器和抗丢包模块执行最终的媒体适配。

图中只保留三类必要连线：蓝灰虚线表示网络观测向上反馈，蓝灰实线表示控制结果向上生效，米棕实线表示编码后的媒体向下进入 RTP 数据面。跨层关系沿层间空隙或左侧通道布线，层内只保留最短的数据流箭头。

观测与估计：RTCP、TWCC、BWE 与 GCC

1. RTCP 是反馈协议族

RTCP 是 RTP 的控制协议，负责回传媒体质量和网络状态。它不是一种具体拥塞控制策略，也不是 RTP 媒体数据本身。

常见 RTCP 反馈包括：

类型主要内容用途
SR / RR收发统计、丢包、jitter、RTT 计算字段粗粒度质量与 RTT 统计
NACK丢失的 RTP sequence number请求 RTX 重传
PLI / FIR请求关键帧解码恢复
REMB接收端估算的最大码率老式带宽反馈
TWCC逐包到达状态和到达时间差给 BWE/GCC 等算法提供高精度输入

所以 RTCP 是反馈大容器，TWCC 只是其中一种反馈类型；RTP 是被这些反馈观测的媒体数据面。

2. TWCC 是逐包到达反馈，不是算法

TWCC 的核心是：发送端给 RTP 包打一个 transport-wide sequence number，接收端记录每个包是否到达、什么时候到，再通过 RTCP Transport-CC feedback 回传。

它提供的是观测数据，例如：

text
seq=1001 arrived at t0
seq=1002 arrived at t0 + 5ms
seq=1003 lost
seq=1004 arrived at t0 + 18ms
seq=1005 arrived at t0 + 40ms

发送端结合自己记录的 send time 和 packet size，可以计算：

  • 到达间隔变化

  • acked bitrate / delivery rate

  • 丢包率

  • RTT 变化

  • queue delay 趋势

  • in-flight 数据量

TWCC 只回传这些数据，不负责判断拥塞，也不直接调码率。

3. BWE 是带宽估计职责

BWE 是 Bandwidth Estimation，表示“估算当前链路还能承受多少发送带宽”这个职责或模块。

BWE 的输入可能来自：

  • TWCC 逐包到达反馈

  • RTCP RR 的丢包、jitter、RTT 信息

  • NACK / RTX 相关信号

  • Pacer 队列

  • 已发送速率、已确认速率、in-flight 数据量

BWE / 拥塞控制层的输出通常是：

  • estimated bitrate

  • target bitrate

  • pacing rate

  • congestion window

  • 带宽状态：过载、正常、欠用等

注意：BWE 不是一个具体策略名称。GCC、BBR-like 或面向特定场景的控制器都可以实现 BWE 与拥塞决策职责。因此架构关系应理解为“具体控制器位于拥塞控制 / BWE 层内部”，而不是先经过一个独立 BWE 层，再进入某个算法层。

4. GCC 是 WebRTC 的拥塞控制算法

GCC / GoogCC 是 WebRTC 常见的媒体拥塞控制算法。它通常结合 delay-based 和 loss-based 信号。

简化理解：

text
如果发送端按稳定节奏发包，但接收端看到包越来越晚到
  → arrival_delta 持续大于 send_delta
  → 网络队列在堆积
  → GCC 判断 overuse
  → 降低 target bitrate / pacing rate

GCC 的输出不是 QP，而是目标码率和发送节奏。QP 是编码器根据目标码率自行调整的结果。

5. 云游戏会叠加场景化控制策略

云游戏的场景化控制器和 GCC 处在同一层级，都属于发送侧拥塞控制算法或策略。区别是云游戏更强调低排队、快速降速和及时恢复，因此通常会组合观察更多实时状态：

  • 当前上行估计带宽

  • 队列延迟、相对队列延迟

  • overuse 状态

  • 上行丢包、反向链路丢包

  • RTT / min RTT

  • pacing rate / pacing gain

  • congestion window / target congestion window

  • estimate rate / target rate

这些信号并不是某一种私有算法的专属概念，而是低延迟拥塞控制常见的设计维度。具体参数需要结合网络条件、媒体负载与端到端时延目标验证。

从可用带宽到媒体与发送执行

BWA：带宽分配

拥塞控制器在 BWE 职责内估出可用总带宽，但发送端实际要发很多东西：

  • 媒体数据

  • FEC 冗余

  • RTX 重传

  • padding / probe

  • 多路音视频流

BWA 负责回答：可用带宽怎么分给这些对象。

例如：

text
BWE 估计可用 3Mbps
  → 视频媒体 2.3Mbps
  → 音频 80kbps
  → FEC 300kbps
  → RTX 200kbps
  → padding/probe 120kbps

不同场景会有不同分配策略，例如低延迟场景更可能压低排队、减少过期重传；平滑播放场景更可能保留更大的恢复和缓冲空间。

Pacer 与 Encoder：执行控制决策

拥塞控制最终要落到两个执行点：

  • Pacer：控制包以什么节奏发出去，避免编码器瞬间吐包打爆网络。

  • Encoder：根据目标码率调整 QP、分辨率、帧率、丢帧策略。

关键点：拥塞控制通常不直接设置 QP。

text
拥塞控制输出 target bitrate
  → 编码器 RateControl 接收目标码率
  → 编码器内部根据画面复杂度、buffer、码控模式调整 QP

因此 QP 是编码器对目标码率的执行结果，而不是 TWCC 或拥塞控制器直接给出的网络判断。

拥塞响应与低延迟场景取舍

拥塞发生后如何调整

这个闭环不是“拥塞算法直接把 QP 改大”，而是网络控制和媒体执行两个阶段：

text
拥塞控制根据反馈产生控制输出
  → Target Bitrate 下降
  → Pacing Rate 下降，发包间隔变大
  → 可选地用 CWND 限制 In-flight
  → 减少或停止 Padding / Probe

发送执行层消费这些输出
  → Encoder 少产生视频数据
  → 分辨率和 FPS 不变时，QP 通常上升
  → Pacer 降低向网络注入数据的速度
  → 瓶颈队列逐步排空

CWND 控制的不是本地发送队列

CWND 是 In-flight 的准入上限：

text
In-flight = 已发出但尚未收到到达反馈的数据

当 In-flight + next_packet_size > CWND
  → Pacer 暂时不再向网络发新包
  → 等 TWCC 反馈释放 In-flight 额度

它不直接修改路由器队列大小，也不等于本地 Pacer 队列。关系可以近似理解为：

text
In-flight ≈ 正在链路上传输的 BDP + 瓶颈处排队的数据
瓶颈队列 ≈ max(In-flight - BDP, 0)

因此，把 CWND 控制在 BDP 附近，意味着尽量填满链路而不额外堆高瓶颈队列。如果 CWND 已满，编码器还在按旧码率产生数据，本地 Pacer 队列反而可能短时增大，所以 CWND 通常要和编码码率反压、Pacing 一起调整。

Padding 为什么要减少

Padding 是为了探测带宽或填满 Pacing 配额而发送的填充流量，不承载有效视频画面。例如：

text
真实媒体数据 = 5 Mbps
Pacing Rate     = 7 Mbps
Padding         = 2 Mbps

拥塞期间继续发 Padding，相当于用探测流量继续占用已经紧张的链路。因此排空阶段会减少或停止 Padding，先把带宽留给有效媒体、音频和必要的恢复流量。

传统 GCC 与低延迟场景化策略的差异

对比维度传统 WebRTC GCC / GoogCC低延迟场景化策略
共同基础都依赖 RTP 发送历史和 TWCC / RTCP 反馈，都在发送侧形成闭环同左
主要观测到达时间趋势、丢包、acked throughput，现代 GoogCC 会融合 delay-based 与 loss / throughput-based 结果在逐包反馈上增加 queue / relative delay、pass ratio、In-flight / CWND、近期链路容量等复合状态
拥塞判断delay-based 识别 overuse / normal / underuse，再结合丢包和吞吐估计调整目标码率增加包级可疑拥塞、mild / aggressive 分级降速和 Burst RTT 恢复判断
降码率主要降低 target bitrate，带宽分配再反压到编码器除 target rate 外，还可以通过 encoding discount 进一步降低视频媒体预算
排空手段Pacing Rate 跟随目标码率下降；部分配置可用 CWND pushback；Probe / Padding 由探测链调度可联动 pacing gain、In-flight drain ratio、CWND / BDP 和 Padding suppression，专门对过高 In-flight 加快排空
误判恢复通过后续 normal / underuse 和探测逐步上调可利用连续无拥塞、近期链路容量和 Burst RTT 分类快速恢复

这个对比的重点不是“GCC 没有 Pacer / CWND / Probe”。它们同样是 WebRTC 发送端拥塞控制链的组成部分。场景化策略的差别主要在于如何组合早期拥塞信号、编码预算、In-flight 排空和短时 Burst 恢复。具体能力仍取决于控制器实现与配置开关，不能把一种实现的行为泛化成所有 GCC 或所有云游戏会话的固定行为。

云游戏为什么更关心这条链

普通直播/RTC 里，拥塞控制主要在“画质”和“流畅”之间折中。云游戏多了“操作跟手”这个目标，因此更怕队列堆积。

云游戏里的危险情况是：

text
视频包没有立刻丢
但到达越来越晚
JitterBuffer 被迫堆得越来越大
用户操作反馈越来越慢

所以云游戏更关心：

  • queue delay 是否上升

  • relative delay 是否异常

  • pacer queue 是否堆积

  • RTT / min RTT 是否变差

  • in-flight 是否过大

  • 过期帧是否还值得等重传

策略取向通常是：

  • 更早识别 overuse

  • 更快降码率

  • 更严格控制 Pacer 队列

  • 更低的 JitterBuffer target delay

  • 更短的重传价值窗口

  • 必要时丢帧保实时

场景化控制器是拥塞控制实现，BWE 是职责，BWA 是带宽分配；三者不是互相替代的同类概念。云游戏还会在控制器和执行模块之上叠加参数、阈值与实时性取舍。

结论

各模块的职责关系如下：

text
RTP 是媒体数据面；RTCP 是反馈协议族；TWCC 是 RTCP 里的逐包反馈；BWE 是带宽估计职责；GCC 是 WebRTC 常见拥塞控制实现；业务可以在同层实现低延迟场景化控制器；BWA 是带宽分配；Pacer/Encoder 是执行层。
